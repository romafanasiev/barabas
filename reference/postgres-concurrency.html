PostgreSQL: конкурентность

Что выбрать, когда две транзакции хотят одну строку. Для быстрого поиска, не для чтения подряд.

Обязательно к запоминанию

На REPEATABLE READ и SERIALIZABLE транзакция может упасть с 40001 serialization_failure. Это не баг — это контракт. Если ты выбрал этот уровень, ты обязан написать ретрай с backoff. Нет ретрая — нет права использовать уровень.

BEGIN ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;

СинтаксисСмыслКого блокирует

Модификаторы ожидания

SELECT ... FOR UPDATE NOWAIT;      -- не ждать, сразу ошибка 55P03
SELECT ... FOR UPDATE SKIP LOCKED; -- пропустить занятые строки
-- SKIP LOCKED — основа очередей задач и выдачи "любых N свободных мест"

Три способа не продать одно место дважды

СпособКакПлюсМинус
Pessimistic SELECT ... FOR UPDATE Просто, детерминированно Очередь и контеншен при популярном концерте
Optimistic Колонка version, WHERE version = $1 Нет ожидания, хорошо при редких конфликтах Нужен ретрай; при частых конфликтах хуже
Constraint UNIQUE / CHECK / EXCLUDE Работает всегда, даже мимо твоего кода Ошибка приходит поздно — надо ловить код 23505
Правило

Constraint — не альтернатива блокировке, а слой под ней. Блокировка даёт нормальный UX (аккуратный 409 вместо исключения), constraint даёт гарантию. Правильный ответ почти всегда — оба.

Когда правило шире одной строки: write skew

Всё выше защищает случай «читаю и пишу одну строку». Если правило считает несколько строк («не больше двух VIP-мест на покупателя», «хотя бы один дежурный»), защита рассыпается: конкуренты читают одно множество, а пишут в разные строки. Конфликта версий нет, REPEATABLE READ молчит, UNIQUE не при чём. Это write skew (в документации PostgreSQL — serialization anomaly).

СпособКак работаетЦена
SERIALIZABLE
SSI		 База запоминает прочитанные диапазоны (predicate locks) и убивает опасную транзакцию Ретраи почти везде; частота отказов зависит от плана запроса
Lock на общую строку SELECT ... FROM buyer WHERE id = $1 FOR UPDATE перед проверкой Ручная дисциплина: забыл в одном эндпоинте — дыра вернулась
Материализация конфликта Количество становится колонкой-счётчиком, правило — CHECK Денормализация: счётчик меняется только в той же транзакции

Только третий способ даёт constraint, то есть работает против кода, который ещё не написан. Первые два защищают лишь того, кто их применил.

Что надо знать про SERIALIZABLE, прежде чем включать

  • Ошибка приходит часто на COMMIT, а не на запросе. Ретраем оборачивается блок вместе с коммитом.
  • 40001 здесь не «не повезло с горячей строкой», а обычный режим работы. Нужен общий механизм ретрая на все транзакции.
  • Sequential scan всегда берёт predicate lock на всю таблицу → всплеск отказов. Индекс под условие чтения — часть решения, а не оптимизация.
  • Predicate locks видны как SIReadLock: SELECT locktype, relation::regclass, mode FROM pg_locks WHERE mode = 'SIReadLock';
  • Мелкие locks сливаются в крупные при нехватке памяти (max_pred_locks_per_transaction, _per_relation, _per_page) — крупнее lock, больше ложных конфликтов.
  • Read-only транзакции помечай BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY — они дешевле.
  • SSI не ждёт и не даёт дедлоков. Он детектит.
Не путать

REPEATABLE READ ловит конфликт записи в одну строку (first-updater-wins). SERIALIZABLE ловит конфликт чтения и записи в одно множество. Первое — про строку, второе — про предикат. Именно поэтому REPEATABLE READ не спасает от write skew.

Атомарное списание без блокировки

UPDATE inventory
   SET available = available - $2
 WHERE ticket_type_id = $1
   AND available >= $2
RETURNING available;
-- 0 строк → мест нет. Проверяй rowCount, а не читай заново.

Работает, потому что чтение, проверка и запись — одно выражение. Окна для гонки нет.

Дедлоки

Возникают, когда A держит строку 1 и ждёт строку 2, а B держит 2 и ждёт 1. PostgreSQL обнаружит и убьёт одну транзакцию с 40P01 deadlock_detected.

  • Профилактика: всегда захватывай строки в детерминированном порядке — например, ORDER BY id в SELECT ... FOR UPDATE.
  • Лечение: ретрай всей транзакции с exponential backoff и jitter.
  • Диагностика: текст ошибки в логе PostgreSQL содержит обе конфликтующие команды. Читай его, а не гадай.

Коды ошибок, которые надо обрабатывать

КодИмяЧто делать
23505unique_violationКонфликт → 409. При идемпотентности — вернуть существующий результат
23514check_violationТвой инвариант сработал. Это баг в коде выше — чинить, а не глушить
40001serialization_failureРетрай с backoff
40P01deadlock_detectedРетрай + проверить порядок захвата блокировок
55P03lock_not_availableПрилетает от NOWAIT → 409 «попробуйте ещё раз»

Чего не делать никогда

  • Держать транзакцию открытой во время сетевого вызова. Платёжный шлюз тормозит секунду — вся очередь стоит секунду.
  • Считать Redis источником истины по остаткам. Redis — ускоритель и TTL-таймер. Гарантия живёт в PostgreSQL.
  • Принимать решение в приложении по данным, прочитанным без блокировки. К моменту записи прочитанное уже неправда.
  • Ловить 23514 и молча продолжать. Constraint выстрелил — значит инвариант нарушен раньше, в логике.
