# M1-01 — ADR: выбор слоя данных

Status: ready-for-human

## Задача

Решить, **чем этот проект ходит в PostgreSQL** — и записать решение как ADR: с аргументами,
с отвергнутыми альтернативами и с ценой. Кандидаты из ROADMAP: TypeORM, Kysely, raw `pg`
(Prisma — см. рекомендацию в [NOTES.md](../../../NOTES.md)).

Решение не про удобство синтаксиса. Оно про то, останется ли достижимой цель проекта: в M4
писать блокировки руками, читать `EXPLAIN ANALYZE` собственного SQL и понимать, какая именно
транзакция где стоит. Слой данных, который прячет эти вещи, экономит неделю сейчас и отнимает
сам смысл проекта потом.

## Definition of Done

- ADR лежит в `docs/adr/` по формату существующих (`Status`, `Date`, Контекст, Решение,
  Следствия) — следующий свободный номер `0004`
- Названы **все** рассмотренные кандидаты и по каждому — почему не он
- Решение опирается на список требований, а не на вкус: требования выписаны и у каждого есть
  issue будущего этапа, который его порождает
- Отдельно решено и записано: **чем накатываются миграции** (это не обязательно тот же
  инструмент) и **откуда берутся типы таблиц**
- Раздел «Следствия» содержит минимум один честный минус выбранного варианта
- `NOTES.md` → «Открытые вопросы»: пункт про data-layer закрыт ссылкой на ADR

## На что смотрю на ревью

- ADR без цены — это реклама. Раздел следствий, в котором всё хорошо, возвращаю
- Аргумент «быстрее писать» принимается только вместе с ответом, что станет дороже
- Проверю на конкретике M4: покажешь, как на выбранном слое пишется транзакция с блокировкой
  строки и что происходит при ошибке сериализации. Если ответ «посмотрю в доках, когда дойдём» —
  решение принято вслепую
- Выбор, который делает `M1-15` невыполнимым (доменная сущность = класс ORM), должен быть либо
  отвергнут, либо закрыт явным планом на мэппер из `M1-18`

## Решено на триаже (2026-09-15)

Ниже — то, что уже верно про **твой** репозиторий, чтобы ADR не начинался с чистого листа.

**Baseline уже в проекте.** `core/infrastructure/postgres/postgres.module.ts` держит пул
`pg@8` с `connectionTimeoutMillis`, его читает health-индикатор из `M0-05` и закрывает
shutdown из `M0-06`. То есть вариант «ничего не добавлять, писать SQL руками» — не гипотеза,
а текущее состояние, и у него нулевая стоимость внедрения. Его цена в другом: типов у
результата нет (`rows` — это `any[]`, пока не опишешь сам), мэппинг руками, миграции придётся
приносить отдельно.

**Репозиторий ESM, и это фильтр кандидатов.** `"type": "module"`, `module: nodenext`, импорты
пишутся с суффиксом `.js`. Половина примеров в доках ORM — CommonJS; механизмы, которые ищут
сущности и миграции по глобам, ломаются в ESM чаще всего именно на этом. **Ловушка:** проверять
кандидата по README недостаточно, спайк должен запускаться в этом репозитории, а не в отдельной
песочнице на `ts-node`.

**Декораторы включены, и это связка, а не мелочь.** `emitDecoratorMetadata: true` в
`apps/server/tsconfig.json` нужен Nest'у для DI. TypeORM опирается на тот же механизм — и
[ADR-0002](../../../docs/adr/0002-oxlint-and-import-boundary.md) уже фиксирует, что из-за него
в `apps/server` нельзя включить `consistent-type-imports`. Если выбираешь TypeORM, назови это
в следствиях.

**Конфликт с `M1-15` — главный технический критерий.** В `M1-15` линтер запретит импорт
фреймворка и слоя данных внутрь `domain/`. Кандидат, у которого доменная сущность — это
декорированный класс ORM, упирается в правило лбом: либо две модели и мэппер (`M1-18`), либо
правило нечем закрыть. Kysely и raw `pg` этой проблемы не создают: они не претендуют на то,
чтобы быть твоей доменной моделью.

**Prisma.** В `NOTES.md` записана рекомендация — не Prisma на первом проекте: она прячет ровно
то, что этот проект должен выучить. Рекомендация не запрет. Если берёшь Prisma, ADR обязан
ответить, как ты будешь учить блокировки, если почти весь такой SQL пойдёт через `$queryRaw`,
и что это делает с типизацией.

**Миграции — отдельное решение.** ORM приносит их в комплекте, query builder и raw — нет.
У Kysely для этого есть официальный CLI `kysely-ctl` (миграции, seeding, кодогенерация типов
из базы); у raw `pg` не будет ничего, инструмент придётся выбрать отдельно. **Требование, о
котором забывают:** в `M7` миграции должен уметь накатить тест на Testcontainers — то есть
нужен **программный** запуск, а не только команда в терминале.

**По чему мерить.** Список требований к слою данных не абстрактный — он весь родом из твоего
же плана:

| Требование | Откуда | Зачем |
| --- | --- | --- |
| `SELECT ... FOR UPDATE`, `SKIP LOCKED` | `M4-01`, `M4-07` | пессимистичная блокировка места |
| Уровень изоляции на конкретную транзакцию | `M4-07` | Read Committed по умолчанию не спасает |
| `lock_timeout` / `NOWAIT` на отдельном запросе | `M4-07`, пункт (3) | перестать ждать осознанно |
| Ретрай на дедлоке и ошибке сериализации | `M4-08` | без доступа к коду ошибки ретрай не написать |
| `INSERT ... ON CONFLICT` по partial unique | `M1-10`, `M4-07` | «одно место — один активный Hold» |
| Сырой SQL с типизированным результатом | `M8-02`, `M8-03` | `EXPLAIN ANALYZE` читается по своему SQL |
| Программный запуск миграций | `M7-02` | Testcontainers поднимает схему сам |
| Доступ к пулу и его настройкам | `M8-06` | размер пула придётся объяснять цифрами |
| Отсутствие в `domain/` | `M1-15` | чистая доменная модель |

Девяти строк достаточно, чтобы решение перестало быть вопросом вкуса: по ним кандидаты
расходятся, а по синтаксису — нет.

## План работ

Отмечай пункты по ходу прямо здесь.

- [x] **1. Ветка.** По твоей схеме имён — `01-adr-data-layer` от актуальной базовой ветки M1.
      *Готово, когда:* `git status` чистый, ветка своя.

- [x] **2. Список требований — своими словами.** Возьми таблицу выше как черновик, вычеркни
      то, с чем не согласен, добавь своё. Это и есть критерии, по которым потом сравниваешь.
      *Готово, когда:* в черновике ADR есть список требований, у каждого — issue-источник.

- [x] **3. Спайк на живой базе, минимум два кандидата.** Один из них — `pg`, который уже есть
      (baseline). Второй — тот, который реально рассматриваешь. Одна временная таблица, и на
      ней три вещи: транзакция с блокировкой строки, вставка с `ON CONFLICT` по partial unique,
      и получение **текста** сгенерированного SQL.
      **Ловушка:** спайк живёт внутри `apps/server` и запускается в ESM-режиме репозитория.
      Песочница на стороне ответит не на тот вопрос.
      *Готово, когда:* для каждого кандидата есть вывод в терминале с текстом SQL, который он
      реально отправил в базу.

- [x] **4. Проверь потолок, а не витрину.** У любого слоя есть запрос, который он не умеет.
      Найди у своего кандидата, как выглядит escape hatch в сырой SQL и что происходит с типами
      результата.
      *Готово, когда:* можешь показать строку кода с сырым SQL и сказать, какого типа `rows`
      и откуда этот тип взялся.

- [x] **5. Миграции — решение отдельным абзацем.**
      **Точка решения:** инструмент миграций может не совпадать со слоем запросов. Проверь
      три вещи: накат, откат и **программный** вызов из теста (`M7`).
      *Готово, когда:* на пустой базе прогнана и откачена одна учебная миграция, и ты можешь
      показать, каким вызовом её накатит тест, а не только команда в терминале.

- [x] **6. Типы таблиц: откуда берутся.**
      **Точка решения:** руками (расходятся молча), кодогенерация из базы (расходятся шумно, но
      нужен шаг в процессе), или схема-DSL как источник правды (тогда база вторична).
      *Готово, когда:* выбор назван и сказано, что происходит, если кто-то поменял схему, а типы
      не обновил.

- [x] **7. Сверка с `M1-15` и `M1-18`.** Ответь письменно: попадёт ли выбранный слой в `domain/`,

      *Готово, когда:* абзац в ADR, из которого видно, что `M1-15` выполним.

- [x] **8. ADR-0004.** Формат — как у существующих трёх.
      *Готово, когда:* файл в `docs/adr/`, в нём все кандидаты, решение и минимум один честный
      минус выбранного.

- [x] **9. Уборка и NOTES.** Спайк удалить (или оставить осознанно и сказать где). В `NOTES.md`

## Что спрошу на ревью словами

- Покажи на выбранном слое транзакцию, которая блокирует строку места, и скажи, что произойдёт
  со вторым запросом, пришедшим в ту же секунду: он ждёт, падает или получает старые данные.
- Через полгода понадобится запрос, который твой слой не умеет. Что ты сделаешь и во что это
  обойдётся — на абзац.
- Одним предложением, без «зато»: в чём твой выбор **хуже** отвергнутого кандидата.

Что спайк нашёл, и что из этого попало в ADR ценой, а не витриной:

1. `check()` и `uniqueIndex().where()` генерируются в SQL — выбор «TS-схема как источник
   правды» выдерживает `M1-06` и `M1-10`.
2. `EXCLUDE`-constraint в DSL нет, отката миграций у `drizzle-kit` нет.
3. Код ошибки PostgreSQL лежит в `error.cause.code`, `error.code` — `undefined`.
4. Предикат partial unique в `ON CONFLICT` задаётся ключом `where` в `onConflictDoNothing`
   и `targetWhere` в `onConflictDoUpdate`; перепутанный ключ роняет предикат из SQL
   (`42P10`). Ловит `tsc`, не ловит vitest.

Пункты 3 и 4 — предсказуемые блокеры `M4-08` и `M1-10`; там они уже не будут сюрпризом.
