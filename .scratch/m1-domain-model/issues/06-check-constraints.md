# M1-06 — `CHECK`-constraints, запрещающие невозможные состояния

Status: needs-triage

## Задача

Пройти по всей схеме и выписать список состояний, которые **не должны существовать физически**:
отрицательный остаток, цена меньше нуля, `expires_at <= created_at`, количество ноль или меньше,
оплаченный заказ без платежа, `held + sold > capacity`.

Для каждого — решить, где стоит защита: `CHECK`, `UNIQUE`, `FK`, `EXCLUDE`, `NOT NULL`, тип
колонки, или (осознанно) только код. Последнее — тоже ответ, но его придётся защитить.

## Definition of Done

- Список невозможных состояний записан в репозитории, не в голове
- У каждого пункта — механизм защиты и строка миграции, где он стоит
- Пункты, оставленные коду, названы явно с причиной
- Ограничения имеют осмысленные имена: имя constraint попадёт в текст ошибки API в M2

## На что смотрю на ревью

- `CHECK` на то, что уже гарантирует тип, — церемония; отсутствие `CHECK` там, где тип не
  спасает, — дыра. Отличить одно от другого и есть задача
- Инвариант `held + sold <= capacity` внутри одной строки закрывается `CHECK`; между строками —
  нет. Понимание этой разницы проверю вопросом
- Имена constraint'ов — не `check_1`, `check_2`
