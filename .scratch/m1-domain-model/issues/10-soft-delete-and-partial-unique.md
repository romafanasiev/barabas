# M1-10 — Soft delete: кому нужен и как он ломает `UNIQUE`

Status: resolved

## Задача

Решить для каждой сущности, удаляется ли она физически или помечается удалённой. Event —
скорее да (на него есть проданные билеты, историю нельзя стирать), Seat — скорее нет. Решение
принимается по признаку, а не по вкусу, и признак надо назвать.

Дальше — ловушка, ради которой issue существует: soft delete **ломает любой `UNIQUE`**.
Удалили место с номером 12, добавили новое с номером 12 — и уникальность не даёт, потому что
старая строка всё ещё лежит в таблице.

## Definition of Done

- Список сущностей с решением «soft / hard» и признаком, по которому решалось
- Все `UNIQUE`, задетые soft delete, переведены на partial index (или другой механизм с
  названной ценой)
- Есть тест: удалил → создал такое же → получилось; и при этом дубликат среди живых строк
  по-прежнему невозможен
- Решено и записано, как soft delete не превратится в `WHERE deleted_at IS NULL`, забытый в
  половине запросов

## На что смотрю на ревью

- Именно последний пункт. Soft delete дешёв в миграции и дорог в эксплуатации: один забытый
  фильтр в отчёте — и удалённый концерт снова продаётся
- `deleted_at timestamptz` против `is_deleted boolean` — выбор назвать словами
- Partial index должен быть проверен тестом, а не «выглядеть правильно»

## Решено на триаже (2026-09-24)

**Источник правды — живая база.** Триаж сверял `pg_constraint` и `pg_index` после миграции
`0006`. Колонок `deleted_at` / `is_deleted` в схеме пока нет ни одной.

**Все `UNIQUE` доменных таблиц делятся на три группы, и трогать нужно только одну.**

| Группа | Ключи | Что с ними при soft delete |
| --- | --- | --- |
| **А. `(id, X)`**: цели составных FK | `section_id_venue_id_uq`, `section_id_type_uq`, `section_id_capacity_uq`, `seat_id_venue_id_uq`, `event_id_venue_id_uq`, `ticket_type_id_event_id_uq`, `event_seat_id_event_id_uq`, `ticket_allocation_id_event_id_uq`, `hold_id_event_id_uq`, `order_id_currency_uq`, `payment_id_status_uq` | **не трогать.** В каждом есть `id`, поэтому двух удалённых и живых с одинаковым ключом быть не может. И вторая причина: FK не может ссылаться на partial index, так что «на всякий случай» переделанный ключ сломает FK |
| **Б. Естественные ключи** | `section_venue_id_label_uq`, `seat_section_id_row_no_seat_number_uq`, `ticket_type_event_id_type_uq`, `ticket_allocation_event_id_section_id_uq`, `event_seat_seat_id_event_id_uq`, `ticket_event_seat_id_uq` | кандидаты на partial «среди живых», **если** таблица получит soft delete. `ticket_event_seat_id_uq` уже решён (см. Comments) |
| **В. Ключи, которые обязаны остаться глобальными** | `ticket_code_uq`, `payment_idempotency_key_uq`, `order_hold_id_uq`, `check_in_ticket_id_uq` | даже если таблица получит `deleted_at`. Код билета напечатан на бумаге: если после возврата его выдадут повторно, на входе пройдёт старый билет. `order_hold_id_uq` и `check_in_ticket_id_uq` следуют за жизнью своего родителя, не своей |

Отсюда вывод, неожиданный для формулировки issue: **у `event` и `venue` естественного ключа нет
вообще.** Их soft delete не ломает ни одного `UNIQUE`. Для них весь вопрос issue — это фильтр
и мёртвый родитель, а не индекс. `UNIQUE` ломается у `section`, `seat`, `ticket_type`, квот и
билета.

`user_email_unique` (таблица auth-библиотеки) — вне issue. Удаление пользователя и повторная
регистрация на тот же email решаются в `M3`, здесь только называются.

**Ловушка из `ROADMAP.md`: «Seat — нет».** На `seat` ссылается `event_seat`, на него — `ticket`,
везде `ON DELETE RESTRICT`. Место, которое хоть раз продавалось, физически удалить нельзя:
база не даст. Значит «hard delete» для `seat` на деле значит «удаляется, только пока ни разу
не выходило в продажу, а после этого — никогда». Это законный ответ, но произнести его надо
именно так. «Удаляется физически» без этой оговорки неверно.

**Мёртвый родитель: вход из `aggregate-map.md`, «Что будет, если ссылка указывает на то, чего
уже нет», п. 3.** FK не видит `deleted_at`. После soft delete секции её квоты, места и
`event_seat` остаются живыми и ссылаются на логически отсутствующую строку. Новый холд на
удалённое событие база тоже пропустит. Issue обязан ответить для каждого soft-родителя, что
происходит с живыми детьми. Иначе «ссылка всегда валидна» верно на уровне базы и ложно на
уровне домена.

**Вход из `states-and-invariants.md` (раздел про `event_seat`, «Снятие места с продажи придёт
в `M1-10`»).** Нужно ли предикату `hold_seat_item_event_seat_id_active_uq` условие по
`deleted_at`? Ответ зависит от того, получит ли `event_seat` soft delete. Записать нужно
в обоих файлах.

**Зависимость от `M1-08`.** DoD требует тест, а первый тест против настоящего PostgreSQL и
способ его поднять — предмет `M1-08` (сейчас `needs-triage`). Пока `M1-08` не сделан,
доказательство в этом issue — проба в psql (как в `M1-09`). Тест ждёт харнесса, и issue без
него не закрывается.

### Из `M1-09` (2026-09-24): `ticket_event_seat_id_uq` и возврат — решение Романа

**Состояние.** `ticket_event_seat_id_uq` держит «одно место — один билет» **безусловно**. В `M1`
это правда: возврата нет, `paid` терминален (решение 25). Безусловность кончится, когда появится
возврат (по решениям 14 и 25 — `M3`, в `ROADMAP.md` — `M5-06`; этап не сведён). Строка
возвращённого билета остаётся — это история, на неё ссылается `check_in`, — а место нужно
продать снова, и ключ этого не даст.

**Решено: недействительный билет помечается soft delete.** Ключ станет partial «среди живых»:
`UNIQUE (event_seat_id) WHERE event_seat_id IS NOT NULL AND deleted_at IS NULL` — тот же приём,
что у остальных `UNIQUE` этого issue, и тест из DoD («удалил → создал такое же → получилось»)
покрывает его без отдельного механизма. Физическое удаление отвергнуто: `check_in` уходит
каскадом, история пропадает. Статус билета (`valid` / `void`) рассматривался и не выбран.

**Цена, которую этот issue обязан закрыть.** У `ticket` «удалён» будет значить «возвращён», а
у `event` или `seat` — «удалён». Фильтр `WHERE deleted_at IS NULL`, правильный для каталога,
в отчёте о продажах спрячет возвраты. Значит, последний пункт DoD («как soft delete не
превратится в забытый фильтр») для `ticket` решается отдельно: кто читает удалённые билеты
намеренно и как это видно в запросе.

#### Пункт 6 — миграция `0007_soft_delete`

Колонка `deleted_at` на восьми таблицах. Шесть ключей группы Б переведены на
`uniqueIndex().where(deleted_at IS NULL)`. Константы переименованы: `*_CONSTRAINT` →
`*_LIVE_INDEX`, к имени добавлен `_live`, потому что изменился смысл. Восемь view `*_live` —
это пункт 9. На диаграмме связь `EventSeat → Ticket` стала `|o..o{`: на место теперь
бывает много билетов, а живой — не больше одного.

**Ловушка 1, проверена до миграции:**

```
UNIQUE (venue_id, label, deleted_at) + две живые 'A'   →  обе вставились, live_duplicates = 2
UNIQUE NULLS NOT DISTINCT (venue_id, label, deleted_at):
  два живых — падает (как надо); удалил → создал — проходит;
  второе удаление той же пары в той же транзакции —
  ERROR: duplicate key … "trap_nnd_uq" (deleted_at одинаковый: now() внутри транзакции один)
```

`NULLS NOT DISTINCT` чинит живых, но делает момент удаления частью ключа. Два удаления одной
пары в одну микросекунду или в одной транзакции падают, и обычно это не тот запрос, который
виноват. Есть и плюс: это constraint, поэтому `ON CONFLICT ON CONSTRAINT` с ним работает.
Отвергнут.

**Ловушка 2** обойдена так: `unique()` → `uniqueIndex().where()`. Для `ON CONFLICT` по этим
ключам нужна форма `ON CONFLICT (колонки) WHERE deleted_at IS NULL`.

Гейты пункта: `\di *live*` показывает 6 индексов с `WHERE (deleted_at IS NULL)`. Накат
`0000`–`0007` на пустую базу прошёл, повторный ничего не сделал (в журнале 8 строк).
`drizzle-kit check` — «Everything's fine».

#### Пункт 7 — мёртвый родитель

Ответ — в `aggregate-map.md`, пункт 3 раздела «Что будет, если ссылка указывает на то, чего
уже нет». Инварианты `I-40` (у удалённой строки нет живых детей) и `I-41` (новый ребёнок не
появляется у удалённого родителя) — группа H. Оба держит код.

**Проба гонки, ради которой `I-41` требует `FOR SHARE`.** Две сессии, событие живое:

```
A: BEGIN; INSERT INTO ticket_type (event_id, …) …; pg_sleep(3); COMMIT;
B (через 1 с, lock_timeout 1s): UPDATE event SET deleted_at = now() …   →  UPDATE 1, не ждал
итог: type = Late | event_deleted = t | type_live = t       ← живой тип у удалённого события

A: BEGIN; SELECT 1 FROM event WHERE id = … AND deleted_at IS NULL FOR SHARE; INSERT …; sleep
B: UPDATE event SET deleted_at = now() …   →  ERROR: canceling statement due to lock timeout
```

Проверка FK берёт `FOR KEY SHARE`, а `UPDATE` неключевой колонки — `FOR NO KEY UPDATE`. Эти
режимы совместимы, поэтому одного FK недостаточно.

#### Пункт 9 — забытый фильтр

**Механизм — view.** У каждой soft-таблицы есть view `<таблица>_live` (в схеме это
`venueLive`, `eventLive`, …). Код читает только view. Базовую таблицу читают три места:

- `*.schema.ts` — определения view;
- `*.report.ts` — намеренное чтение удалённых строк;
- тесты.

**Проверка перенесена в `M1-18`** (решение Романа, 2026-10-06). Кода, который читает
soft-таблицы, пока нет: проверка охраняла бы пустое место. Первый такой код — репозиторий
`Hold`: он проверяет `deleted_at` у места и квоты (`I-41`). Там проверку и пишут, на живом коде.
Grep-скрипт, который был здесь (ловил `.from(<таблица>)`, `…Join(<таблица>`,
`db.query.<таблица>.`, сырой `FROM/JOIN <таблица>` вне разрешённых файлов), удалён. Его минус
остаётся входом в `M1-18`: grep не видит запрос, собранный через переменную.

**`ticket`.** Отчёт о продажах с возвратами читает `ticket`, а не `ticket_live`, и живёт в
`*.report.ts`. От забытого фильтра его отличает имя файла; механически — после `M1-18`.

**Отвергнуто:**

- **Фильтр по умолчанию в репозитории.** Его нарушение ловит только память ревьюера.
- **RLS.** Политика `USING (deleted_at IS NULL)` по умолчанию служит и `WITH CHECK` для
  `UPDATE`. Тогда сам `SET deleted_at = now()` нарушает политику, и нужны раздельные политики
  на чтение и запись. Сверх того нужна отдельная роль, потому что владелец таблицы RLS
  обходит. Для `M1` это слишком дорого.

**Цена выбранного:**

- Запись идёт в базовую таблицу, поэтому `UPDATE` без `deleted_at IS NULL` может задеть
  удалённую строку.
- View перечисляет колонки явно. Новая колонка в таблице означает пересоздание view в
  миграции. Генерирует ли его `drizzle-kit` сам — не проверял.
