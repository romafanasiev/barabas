# M1-15 — Скелет слоёв + правило линтера, запрещающее фреймворк в `domain/`

Status: needs-triage

## Задача

Развести четыре слоя — `domain`, `application`, `infrastructure`, `api` — и закрыть `domain/`
линтером: ни NestJS, ни драйвера базы, ни ORM внутри доменного слоя. Правило нужно не ради
чистоты: домен, который импортирует фреймворк, невозможно протестировать без поднятия
приложения, и через полгода он перестаёт быть доменом.

Механизм в проекте уже есть — `no-restricted-imports` с `patterns` держит границу между
`apps/server` и `apps/web`, см. [ADR-0002](../../../docs/adr/0002-oxlint-and-import-boundary.md).
Здесь та же техника применяется внутрь одного приложения.

## Definition of Done

- Папки слоёв существуют, в каждой — хотя бы один настоящий файл (пустых каталогов не бывает)
- `import { Injectable } from '@nestjs/common'` внутри `domain/` роняет `pnpm lint`
- То же для драйвера базы и любого выбранного в `01` слоя данных
- Направление зависимостей названо словами и проверено: `domain` не знает ни о ком
- Правило проверено мутацией: добавил запрещённый импорт → красный линт; убрал → зелёный

## На что смотрю на ревью

- Правило обязано быть проверено, а не написано. Конфиг линтера, который молча не применился, —
  ровно та ошибка, что уже была с `oxlint.json` в ADR-0002
- `application` не должен импортировать `api`
- Слои ради слоёв в CRUD-части домена (каталог площадок) — обратная ошибка; см. `CONTEXT.md`,
  «Где DDD не применяется»
