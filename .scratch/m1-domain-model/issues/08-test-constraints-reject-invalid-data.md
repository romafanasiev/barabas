# M1-08 — Тест: невалидные данные напрямую в БД **падают** на constraint

Status: resolved

## Задача

Доказать тестом, что схема защищает себя без участия приложения. Тест ходит в базу **напрямую**,
мимо сервисов, DTO и валидации, и пытается записать каждое из невозможных состояний из `06`.
Каждая попытка обязана упасть.

Это первый тест проекта, который работает с настоящим PostgreSQL. Как он поднимается — решение
этого issue (оно же готовит почву для Testcontainers в M7).

## Definition of Done

- Есть тест на **каждый** пункт списка из `06`
- Тест проверяет не только факт падения, но и **какой именно** constraint сработал: иначе
  зелёный тест может означать опечатку в другом месте
- Тест не использует ни один сервис приложения — только соединение с базой
- Тест кусается: убрал constraint из миграции → тест красный

## На что смотрю на ревью

- Проверю мутацией: сниму один `CHECK` и жду красного. Не заметил — возврат
- `expect(...).rejects` без проверки кода ошибки — слабый тест: он зелёный и когда запрос упал
  по синтаксису
- Тест должен работать на чистой базе в CI, а не только на локальной с seed-данными

## Решено на триаже (2026-10-06)

**Что считается «списком из `06`».** Разделы 1 и 2 `impossible-states.md`. К ним
добавляются **все внешние ключи домена**. Составные FK держат связи (`I-13`, `I-14`, `I-23`,
`I-28`, `I-37`), а `M1-03`, `M1-04` и `M1-05` записывали свои пробы как «заготовку тестов
`M1-08`». По `ADR-0004` каждый ключ должен быть под тестом, иначе его исчезновение никто не
заметит.

**«Каждый» проверяется механически, а не перечнем в голове.** Отдельный тест сверяет список
ограничений в живой базе (`pg_constraint`, partial unique index) со списком тех, на которые
ссылаются тесты. Новый `CHECK` без теста делает набор красным. Это и есть правило `ADR-0004`
про объекты без теста.

**Тесты кода сюда не входят.** Их не на чем запускать: агрегатов и сервисов ещё нет. Каждый
такой тест получает адрес там, где появится код (пункт 8).

### Вход из `M1-10` (2026-10-06): обвязка для тестов на живой базе уже есть

Пункт 11 `M1-10` требовал тест на настоящем PostgreSQL раньше, чем дошла очередь до этого
issue. Поэтому минимальная обвязка сделана там, и вопрос «как тест поднимает базу» здесь
стоит как **принять или переделать**, а не «придумать».

Что есть:

- `pnpm --filter server test:db`, конфиг `vitest.config.db.ts`, файлы `*.db-spec.ts`;
- `utils/tests/db/global-setup.ts`: на каждый прогон создаёт базу `test_<uuid>` рядом с
  dev-базой (по `POSTGRES_URL`, если не задан — из `../../.env`), мигрирует через
  `drizzle-orm/node-postgres/migrator`, в конце делает `DROP … WITH (FORCE)`. Чистая база —
  требование «На что смотрю на ревью»;
- `utils/tests/db/db.helpers.ts`: `withRollback` (тест в транзакции, в конце `ROLLBACK`) и
  `expectViolation` (SQLSTATE + имя ограничения через savepoint);
- `utils/tests/db/catalog.fixture.ts`: площадка → место → событие → оплаченный заказ;
- первый потребитель — `test/db/soft-delete.db-spec.ts`.

Что осталось решить здесь:

- **Нужен работающий compose-Postgres.** Testcontainers (M7) убрал бы эту зависимость.
- **CI нет вообще.** «Тест работает на чистой базе в CI» пока проверено только локально.
- **Тесты внутри одного файла идут последовательно, файлы — параллельно** в одной базе. С
  `ROLLBACK` это безопасно, пока тест не делает `COMMIT`. Тест гонки (две сессии) этого
  правила не выдержит, и ему понадобится своя схема очистки.

#### Пункт 2 — обвязка

Принята как есть: база `test_<uuid>` на каждый прогон, миграции из `./drizzle`, тест в
транзакции с `ROLLBACK`.

**Цена:**

- нужен запущенный compose-Postgres;
- тест, которому нужен `COMMIT` (гонка двух сессий), в эту схему не ложится и потребует
  своей уборки;
- все файлы делят одну базу. С `ROLLBACK` это безопасно.

`pnpm test` по-прежнему без Docker: `*.db-spec.ts` в его маску не попадает.

#### Пункт 3 — хелпер

`expectError(client, sql, { code, constraint | column | message })`. Под savepoint, поэтому
транзакция теста после ошибки жива. «Statement succeeded» — отдельная ошибка, а не зелёный
тест.

**Ловушка из плана подтвердилась.** У `22P02`, `22001` и `22007` нет ни `constraint`, ни
`column`, поэтому там сверяется текст сообщения. Это слабее имени, и названо в коде.

Хелпер поймал реальную ошибку ещё при написании: я ждал `22P02` для `'next friday'::
timestamptz`, а Postgres отдаёт `22007` (`invalid_datetime_format`).

**Правило «один нарушенный ключ на строку».** При удалении секции с местами срабатывают два
FK (тип и площадка), и какой ответит, зависит от порядка их создания. Такой тест проверял
бы порядок, а не ключ. Поэтому `RESTRICT` проверен на площадке и на месте, где ключ один.

`order_currency_fk` создаёт новый холд и заказ.

#### Пункт 9 — покрытие

`coverage.db-spec.ts` берёт из живой базы `CHECK`, FK, `UNIQUE` и unique-индексы без
constraint, исключая таблицы better-auth. Три проверки:

- у каждого объекта есть константа;
- у каждой константы есть объект в базе;
- на каждую константу ссылается какой-то `*.db-spec.ts`.

**Исключения поимённо — 11 ключей `(id, X)`.** Их дубль — это сначала дубль `*_pkey`, и
нарушить их самих нечем. Работа этих ключей проверена через FK, которые на них ссылаются.

**Цена.** «Ссылается» значит «имя встречается в тексте теста», а не «тест ждёт на нём
ошибку». Импорт константы без проверки засчитается.
