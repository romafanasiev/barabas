# M1-08 — Тест: невалидные данные напрямую в БД **падают** на constraint

Status: needs-triage

## Задача

Доказать тестом, что схема защищает себя без участия приложения. Тест ходит в базу **напрямую**,
мимо сервисов, DTO и валидации, и пытается записать каждое из невозможных состояний из `06`.
Каждая попытка обязана упасть.

Это первый тест проекта, который работает с настоящим PostgreSQL. Как он поднимается — решение
этого issue (оно же готовит почву для Testcontainers в M7).

## Definition of Done

- Есть тест на **каждый** пункт списка из `06`
- Тест проверяет не только факт падения, но и **какой именно** constraint сработал: иначе
  зелёный тест может означать опечатку в другом месте
- Тест не использует ни один сервис приложения — только соединение с базой
- Тест кусается: убрал constraint из миграции → тест красный

## На что смотрю на ревью

- Проверю мутацией: сниму один `CHECK` и жду красного. Не заметил — возврат
- `expect(...).rejects` без проверки кода ошибки — слабый тест: он зелёный и когда запрос упал
  по синтаксису
- Тест должен работать на чистой базе в CI, а не только на локальной с seed-данными

## Comments

### Вход из `M1-10` (2026-10-06): обвязка для тестов на живой базе уже есть

Пункт 11 `M1-10` требовал тест на настоящем PostgreSQL раньше, чем дошла очередь до этого
issue. Поэтому минимальная обвязка сделана там, и вопрос «как тест поднимает базу» здесь
стоит как **принять или переделать**, а не «придумать».

Что есть:

- `pnpm --filter server test:db`, конфиг `vitest.config.db.ts`, файлы `*.db-spec.ts`;
- `utils/tests/db/global-setup.ts`: на каждый прогон создаёт базу `test_<uuid>` рядом с
  dev-базой (по `POSTGRES_URL`, если не задан — из `../../.env`), мигрирует через
  `drizzle-orm/node-postgres/migrator`, в конце делает `DROP … WITH (FORCE)`. Чистая база —
  требование «На что смотрю на ревью»;
- `utils/tests/db/db.helpers.ts`: `withRollback` (тест в транзакции, в конце `ROLLBACK`) и
  `expectViolation` (SQLSTATE + имя ограничения через savepoint);
- `utils/tests/db/catalog.fixture.ts`: площадка → место → событие → оплаченный заказ;
- первый потребитель — `test/db/soft-delete.db-spec.ts`.

Что осталось решить здесь:

- **Нужен работающий compose-Postgres.** Testcontainers (M7) убрал бы эту зависимость.
- **CI нет вообще.** «Тест работает на чистой базе в CI» пока проверено только локально.
- **Тесты внутри одного файла идут последовательно, файлы — параллельно** в одной базе. С
  `ROLLBACK` это безопасно, пока тест не делает `COMMIT`. Тест гонки (две сессии) этого
  правила не выдержит, и ему понадобится своя схема очистки.
