# M1-07 — Seed-скрипт: площадка, концерт, 500 мест

Status: resolved

## Задача

Одна команда, после которой в базе есть площадка с секциями, 500 мест, концерт и категории
билетов. Воспроизводимо: два запуска на чистой базе дают одинаковые данные, а не два разных
набора со случайными id.

Этот скрипт дальше используется в демо, в нагрузочном тесте M4 и на защите.

## Definition of Done

- `pnpm <скрипт>` на чистой базе наполняет её за один запуск
- Данные детерминированы: id и коды предсказуемы, повторный прогон даёт то же самое
- Повторный запуск на непустой базе ведёт себя определённо (падает или идемпотентен) — выбрать
  и задокументировать
- Скрипт не обходит constraints и не пишет напрямую в системные таблицы

## На что смотрю на ревью

- Seed — не миграция и не живёт в папке миграций
- 500 мест вставляются не 500 отдельными запросами в цикле await
- Если используется faker — он засеян фиксированным seed, иначе «воспроизводимо» неправда

Issue отдан агенту целиком (2026-10-07, «делай сам, я ревьюю»). Развилки ответил Роман:
повторный запуск — **идемпотентно**; зал — **нумерованные секции + танцпол**.

- [x] **1. Где живёт и чем запускается.** Не в `drizzle/`, не в `src/` (в prod-сборку не
      попадает). Без новых зависимостей.
      *Готово, когда:* `pnpm --filter server db:seed` на чистой базе печатает `seeded …`.

- [x] **2. Данные.** Площадка; две нумерованные секции на 500 мест; танцпол; концерт;
      категория билетов на каждую секцию; `event_seat` на **каждое** место (решение 11);
      квота на танцпол. Все `CHECK` из `M1-06` соблюдены: цены и вместимости > 0, строки не
      пустые.
      *Готово, когда:* `venue/section/seat/event/ticket_type/event_seat/ticket_allocation` =
      `1/3/500/1/3/500/1`.

- [x] **3. Детерминизм.** id — константы, а не `defaultRandom()`; дата концерта —
      константа, а не `now()`. faker не нужен.
      *Готово, когда:* два прогона на чистой базе дают одинаковые строки без учёта
      `created_at`/`updated_at` (тест).

- [x] **4. Повторный запуск.** Идемпотентно, в одной транзакции.
      **Ловушка:** `ON CONFLICT DO NOTHING` без цели глотает **любой** конфликт уникальности,
      в том числе чужую строку с тем же естественным ключом. Seed тогда отчитается об
      успехе, а данные будут не его.
      *Готово, когда:* повторный прогон ничего не меняет (тест); чужая `Parter` в той же
      площадке роняет seed на `section_venue_id_label_live_idx` (тест).

- [x] **5. Не 500 запросов.** Одна вставка на таблицу.
      *Готово, когда:* в скрипте семь `INSERT` и ни одного `await` в цикле (линтер молчит).

- [x] **6. Устаревший seed.** `DO NOTHING` оставляет то, что лежит под теми же id. Если
      это уже не сходится с залом, seed обязан упасть, а не сказать `seeded`.
      *Готово, когда:* после снятия места seed падает с текстом про секцию (тест).

- [x] **7. Мутации.** Каждая правка скрипта ломает свой тест.
      *Готово, когда:* таблица в `## Comments`.

- [x] **8. Гейты.** `typecheck`, `lint`, `format:check`, `test`, `test:db`, `build`.

### 2026-10-07 — сделано агентом, ждёт ревью

**Файлы.** `apps/server/scripts/seed.ts` (данные, `seed(client)`, запуск при
`import.meta.main`), `apps/server/test/db/seed.db-spec.ts`, скрипт `db:seed` в
`package.json`, `scripts/**` в `tsconfig.json`.

**Что решал я, а не ты** — с этого списка начинай ревью:

1. **Запуск — `node scripts/seed.ts`, без `tsx`.** Node 26 сам стрипает типы. Цена:
   скрипт может импортировать только пакеты и встроенные модули. Импорт схемы через
   `.js`-путь в нативном Node не резолвится, поэтому seed пишет SQL через `pg`, а не через
   drizzle — в стиле фикстур `M1-08`. Если seed понадобится типизированный через схему,
   придётся заводить `tsx`.
2. **`ON CONFLICT (id) DO NOTHING`, а не `ON CONFLICT DO NOTHING`.** Глушится только
   повтор самого seed'а. Коллизия по естественному ключу (`venue_id, label`) падает с
   `23505`.
3. **Транзакцию держит вызывающий.** `seed(client)` не делает `BEGIN`/`COMMIT`: CLI
   оборачивает его сам, а тест вызывает внутри `withRollback`. Иначе `COMMIT` из seed'а
   закоммитил бы тестовую транзакцию.
4. **Пост-проверка `verify`.** В каждой нумерованной секции живых мест столько же, сколько
   `capacity`, и число `event_seat_live` события равно их сумме. Это проверка
   `Reconciliation` из решения 11, применённая к seed'у: она ловит «старый seed под теми
   же id».
5. **id вида `0000000K-5eed-4000-8000-NNNNNNNNNNNN`.** K — таблица (1 venue … 7 allocation,
   как в фикстурах), N — номер строки. Места нумеруются сквозь зал: `seat N` и
   `event_seat N` — одно и то же место. С id фикстур `M1-08` не пересекаются, и в логах
   seed-строку видно сразу.
6. **Данные.** «Sky Arena», Kyiv. Parter 15×20 по 1500 UAH, Balcony 10×20 по 900 UAH,
   Fan zone (standing, 1000) по 700 UAH с квотой на всю вместимость. Концерт «Northern
   Lights» 2027-06-19 19:00–22:00 +03. **Дата через ~8 месяцев станет прошедшей.** Если
   `M4` начнёт запрещать бронь на прошедший концерт, её придётся сдвинуть, и это осознанная
   цена детерминизма.
7. **Только каталог.** Пользователей, холдов и заказов нет. DoD их не просит, а нагрузочный
   тест `M4` создаёт их сам.
