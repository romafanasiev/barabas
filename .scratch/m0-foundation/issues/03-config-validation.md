# M0-03 — Конфигурация через env с валидацией на старте

Status: needs-triage

## Задача

Подключить `@nestjs/config` со схемой валидации. Приложение должно **падать на старте**,
если хоть одна обязательная переменная отсутствует или имеет неверный тип.

## Definition of Done

- Типизированный доступ к конфигу: `config.get('DATABASE_URL')` возвращает `string`, а не `any`
- Удалил переменную из `.env` → приложение не стартует и пишет в лог, какой именно не хватает
- Нигде в коде нет прямого `process.env.X` вне config-модуля
- Есть тест: невалидный конфиг → ошибка валидации

## На что смотрю на ревью

- Приложение не должно стартовать «наполовину» и падать позже при первом запросе.
  Fail fast — это и есть смысл задачи
- Значения по умолчанию для секретов недопустимы (`JWT_SECRET ?? 'secret'` — возврат)

### 2026-09-11 — заметка из ревью M0-02

`.env` читают два независимых потребителя: Compose (интерполяция `${...}` + `env_file`) и
Node-процесс (zod). «Нужна в `.env`» и «должна быть в схеме» — разные утверждения.

На момент M0-02 в схеме сидят три переменные, которых код не читает:
`POSTGRES_USER`, `POSTGRES_PASS` (нужны образу postgres, не приложению) и
`POSTGRES_DATABASE_URL` (потребитель появится только в M1).

Вопрос на ревью M0-03: что здесь конфигурация **приложения**, а что — **инфраструктуры**?
Схема должна описывать то, без чего процесс не может работать, иначе «падать на старте»
превращается в ложные срабатывания и привычку «допиши в `.env`, чтобы замолчало».

Отдельно: URL к базе не может иметь одного верного значения — изнутри контейнера это
`postgres:5432`, с хоста `localhost:5433`. Решить, приложение получает готовый URL
снаружи или собирает его из частей.
