# M0-04 — Структурированное логирование и correlation id

Status: resolved

## Задача

Подключить Pino. Каждый входящий запрос получает `x-request-id` (или генерирует свой), и
этот id попадает **во все** логи, порождённые этим запросом.

## Definition of Done

- Логи — валидный JSON в одну строку (в проде; в dev допустим pretty-print)
- В строке запроса есть `requestId` и `responseTimeMs` на верхнем уровне, а `method`,
  `url` и `statusCode` — внутри сериализованных `req`/`res` (см. решение от 2026-09-14)
- Клиент прислал `x-request-id` → он используется; не прислал → генерируется UUID
- `x-request-id` возвращается в ответе
- Пароли, токены и заголовок `authorization` **не** попадают в логи (redaction)
- `requestId` попадает в лог, написанный **из сервиса**, а не только в строку
  входа/выхода запроса. Проверяется тестом: один HTTP-запрос → минимум две записи
  (запрос и сервис) с **одинаковым** `requestId`
- Логгер Nest заменён (`app.useLogger(...)` или `bufferLogs`), чтобы стартовые строки
  самого фреймворка тоже были JSON. Два формата в одном потоке — это уже не структурированный
  лог, его не распарсит ни один коллектор
- Тест кусается: если убрать проброс id, тест на совпадение `requestId` краснеет

## Решено на триаже (2026-09-12)

**`x-request-id` не доверяем как есть.** Заголовок приходит снаружи, то есть это
пользовательский ввод: в лог поедет то, что прислал клиент. Принимаем только если значение
проходит проверку формата и длины, иначе генерируем свой. Иначе получаем log injection —
перевод строки в заголовке разрезает одну запись на две, и грепом по логам можно нарисовать
событие, которого не было.

**Генератор — `crypto.randomUUID()` из `node:crypto`.** Встроен в Node, не нужен пакет.

**Метадату биндим через child logger, а не таскаем аргументом.** `logger.child({ requestId })`
пинит пару к логгеру, и она печатается в каждой строке этого child. Как этот child доезжает
до сервиса на три вызова вглубь — см. открытый вопрос ниже.

## Открытый вопрос — решение твоё, зафиксируй в Comments до старта

`nestjs-pino` против ручной сборки на `pino` + `pino-http` + `AsyncLocalStorage`.

- **`nestjs-pino`** — быстрее: `LoggerModule.forRoot({ pinoHttp: {...} })`, `app.useLogger`,
  инжектишь `PinoLogger` — и `requestId` уже везде. Проброс внутри сделан на `AsyncLocalStorage`
  за тебя.
- **Руками** — дольше на пару часов, но ты один раз увидишь механизм: middleware кладёт child
  в `AsyncLocalStorage.run()`, провайдер достаёт его из `getStore()`. Это тот же механизм,
  на котором в M4 поедет транзакционный контекст (`ALS` с активным клиентом БД, чтобы
  репозитории попадали в одну транзакцию, не передавая её параметром).

**Рекомендация — руками**, ровно из-за второй строчки: `AsyncLocalStorage` тебе всё равно
понадобится в M4, и дешевле встретить его здесь, где цена ошибки — кривой лог, а не
разъехавшаяся транзакция. Если выберешь `nestjs-pino` — это нормальный выбор, но тогда
загляни в его исходник и найди там `AsyncLocalStorage` своими глазами.

**Проверить перед установкой:** `apps/server` — ESM (`"type": "module"`), Nest 12, Express 5.
`nestjs-pino` публикуется как CJS; если интероп заартачится, это не повод чинить его полдня —
это сигнал выбрать второй вариант.

## На что смотрю на ревью

## План работ

Отмечай пункты по ходу прямо здесь.

- [x] **1. Ветка.** `04-logging` от текущей.
      *Готово, когда:* `git status` чистый, ветка своя.

- [x] **2. `LOG_LEVEL` в схему env.** Новая переменная в zod-схеме из `M0-03`, с дефолтом
      (`info`), плюс в `.env` и `.env.example`. Уровень логов — конфигурация приложения,
      значит ему место именно в схеме.
      *Готово, когда:* поставил заведомо неверное значение → процесс падает на старте и
      называет переменную.

- [x] **3. Корневой логгер.** Один модуль, который создаёт `pino` и отдаёт его через DI-токен,
      как сделано с `ENV`. В dev — `pino-pretty`, в проде — голый JSON, ветка по `NODE_ENV`.
      *Готово, когда:* временный лог из `bootstrap` печатается JSON-строкой при
      `NODE_ENV=production` и человекочитаемо в dev.

- [x] **4. Заменить логгер Nest.** `NestFactory.create(AppModule, { bufferLogs: true })` и
      `app.useLogger(...)`. Без этого стартовые строки Nest остаются своим форматом, и в одном
      потоке едут два формата сразу — такой лог не распарсит ни один коллектор.
      *Готово, когда:* строки `Nest application successfully started` и `Mapped {/health}` —
      тоже JSON.

- [x] **5. Хранилище контекста.** Один экземпляр `AsyncLocalStorage` на процесс, в отдельном
      файле. Не внутри модуля с логгером — в `M4-05` в него поедет клиент БД, и он не должен
      зависеть от логирования.
      *Готово, когда:* есть unit-тест: два параллельных `run()` видят каждый своё значение.

- [x] **6. `pino-http` с `genReqId`.** Именно этот хук читает `x-request-id`, валидирует его и
      ставит заголовок в ответ — всё в одном месте, поэтому источник id получается один.
      Ставь `quietReqLogger: true`: тогда `req.log` — это child, к которому привязан **только**
      id, а не весь объект запроса. Иначе каждая строка из сервиса потащит за собой заголовки.
      *Готово, когда:* `curl -i` показывает `x-request-id` в ответе; присланный клиентом id
      возвращается тем же; мусорный — заменяется своим.

- [x] **7. Middleware, который открывает контекст.** Кладёт `req.log` в
      `storage.run(логгер, () => next())`.
      **Главная ловушка всей задачи:** `next()` вызывается **внутри** колбэка `run`. Вынесешь
      наружу — контекст закроется раньше, чем начнётся обработка, и `getStore()` вернёт
      `undefined` везде. Регистрируй его раньше остальных middleware.
      *Готово, когда:* временный лог из любого сервиса печатается с id, а сигнатура этого
      сервиса не изменилась.

- [x] **8. Провайдер логгера для слоёв.** Достаёт из `getStore()`, а если контекста нет —
      отдаёт корневой логгер. Фолбэк обязателен: вне запроса (bootstrap, shutdown, воркер)
      контекста не будет, и логгер не имеет права падать.
      *Готово, когда:* лог из `bootstrap` (вне запроса) пишется и не бросает.

- [x] **9. `redact`.** Минимальный набор для этой задачи: `authorization`, пароли, токены.
      Email и платёжные данные — в `M0-07`, сюда не тащим.
      *Готово, когда:* запрос с заголовком `Authorization: Bearer ...` → в логе `[Redacted]`.

- [x] **10. Имена полей — привести к DoD.** По умолчанию `pino-http` пишет `reqId` и
      `responseTime`, а DoD требует `requestId` и `responseTimeMs`. Плюс `method`, `url` и
      `statusCode` лежат **внутри** сериализованных `req` и `res`, а не на верхнем уровне.
      Решение твоё (`customAttributeKeys`, свои сериализаторы или правка DoD) — но расскажи
      на ревью, что выбрал и почему. Это не косметика: по этим именам через год будут
      строиться дашборды и алерты, и переименование в проде стоит дорого.
      *Готово, когда:* имена в реальном выводе совпадают с тем, что записано в DoD.

- [x] **11. Тесты.** Четыре:
      (а) один HTTP-запрос → две строки, из middleware и из сервиса, с **одинаковым** id;
      (б) присланный `x-request-id` используется и возвращается в ответе;
      (в) мусорный заголовок → сгенерирован свой;
      (г) `authorization` в лог не попал.
      Тест должен читать **сериализованную строку**: собирай приложение с логгером, пишущим
      в свой `Writable`, и разбирай собранные строки как JSON. Ассерт на аргументы вызова
      логгера ничего не доказывает — до сериализации `redact` ещё не отработал.
      *Готово, когда:* `pnpm test` зелёный.

- [x] **12. Мутация.** Замени в провайдере из шага 8 `getStore()` на корневой логгер и убедись,
      что тест (а) краснеет. Верни обратно, мутацию не коммить.
      *Готово, когда:* есть вывод обоих прогонов — до и после.

### 2026-09-14 — решение по шагу 10: имена полей

Роман решил сделать **половину пункта 10** и вторую половину сознательно пропустить.

**Сделано:** `customAttributeKeys: { reqId: 'requestId', responseTime: 'responseTimeMs' }`
в опциях `pino-http`. Проверено на живом запросе: оба имени на верхнем уровне и в строке
`request completed`, и в строке, написанной из сервиса через child-логгер.

**Пропущено:** подъём `method`, `url`, `statusCode` на верхний уровень записи. Для этого
нужны свои сериализаторы `req`/`res`, а вместе с ними — риск вынести в лог то, чего там
сейчас нет (тело запроса, полный набор заголовков), и тогда список `redact` из шага 9
остаётся единственной защитой. Цена пропуска низкая: данные из лога никуда не деваются,
они лежат вложенными в `req`/`res` и достаются запросом по вложенному пути.

Причина решения — слова Романа: информации хватает, чтобы понять, как строятся дашборды,
а делать их много он смысла не видит. Для учебной цели M0 этого достаточно.

DoD выше приведён в соответствие: требование «всё на верхнем уровне» заменено на то, что
фактически сделано. Если в M1 появится настоящий коллектор логов и запросы по `method`/
`statusCode` станут частыми, поднять их наверх — отдельная маленькая задача, но сделать её
тогда будет дороже: строки, записанные до переименования, по новому имени не найдутся.

**Отступления от плана, зафиксированы сознательно:**

- **Ветка** называется `04-pino`, а не `04-logging` (пункт 1). Косметика, менять не стали.
- **Генератор id** — `v4()` из пакета `uuid` вместо `crypto.randomUUID()` из `node:crypto`,
  как было решено на триаже. Пакет всё равно нужен ради `validate()` для проверки формата.
- **Пункт 10 сделан наполовину** — см. отдельную запись от 2026-09-14 выше. DoD приведён

  Заголовок с `\r\n` невозможно отправить — его отвергает сам HTTP-клиент, то есть до
  проверки в `genReqId` дело не доходит. Это второй эшелон защиты, и тестировать его
  штатным клиентом нечем.

**Незапланированная работа:** появились `AppController` и `AppService` — без настоящего
роута нельзя было проверить требование DoD «`requestId` в строке из сервиса». `AppService`
