# M0-06 — Graceful shutdown

Status: ready-for-human

## Задача

По `SIGTERM` приложение должно перестать принимать новые запросы, дождаться завершения
текущих и аккуратно закрыть пул соединений с PostgreSQL и клиент Redis.

## Definition of Done

- `app.enableShutdownHooks()` включён, реализован `OnApplicationShutdown` где нужно
- `docker compose stop api` завершает контейнер быстро и без `SIGKILL` по таймауту
- Запрос, выполнявшийся в момент сигнала, доходит до конца и получает ответ
- В логах видна последовательность: получен сигнал → закрываем → закрыто

## На что смотрю на ревью

- Почему это важно именно для нашего проекта: незакрытая транзакция при деплое = висящая
  блокировка = очередь покупателей. Спрошу, связал ли ты одно с другим
- Ловится ли `SIGTERM`, а не только `SIGINT` (Docker шлёт `SIGTERM`)

## Решено на триаже (2026-09-15)

Всё ниже я проверил на твоём коде и опытами, а не по памяти. Числа и цитаты — настоящие.

**Порядок хуков в Nest 12 — вот он, и он решает всю задачу.** Смотрел исходник
`@nestjs/core/nest-application-context.js`, метод `close()`:

```
prepareClose()  →  onModuleDestroy  →  beforeApplicationShutdown  →  dispose()  →  onApplicationShutdown
                                                                     ↑
                                                       вот здесь закрывается HTTP-сервер
```

Отсюда следует правило, которое и есть содержание issue: **зависимость закрывается только
в `onApplicationShutdown`.** Это единственный хук, который выполняется после того, как
HTTP-сервер закрыт и запросы в полёте дожили до ответа. Положишь `pool.end()` в
`onModuleDestroy` — отнимешь базу у запроса, который ещё пишет ответ.

**`beforeApplicationShutdown` — место для паузы на вывод из балансировки.** Он выполняется
до закрытия сервера, то есть трафик в этот момент ещё принимается. Ровно то, что нужно для
«лжи во спасение» из урока 0006: readiness уже отдаёт `503`, но инстанс ещё обслуживает то,
что балансировщик успел прислать.

**`app.enableShutdownHooks()` без аргументов подписывается на все 11 сигналов** из enum
`ShutdownSignal` — не только `SIGTERM` и `SIGINT`, но и `SIGILL`, `SIGSEGV`, `SIGUSR2`.
Список стоит сузить осознанно.

**После хуков Nest убивает процесс сам:** `process.kill(process.pid, signal)` со снятым
собственным обработчиком. Код выхода будет `143`, а не `0`. У метода есть опция
`enableShutdownHooks(signals, { useProcessExit: true })` — тогда будет `process.exit(0)`.
В исходнике рядом лежит комментарий, зачем она появилась: «required for async loggers
(like Pino with transports) to flush their buffers». У тебя в dev именно такой логгер —
`pino-pretty` через `transport`. Это точка решения, см. пункт 9 плана.

**`forceCloseConnections: true` брать нельзя** — хотя выглядит как готовый ответ. В
`ExpressAdapter.close()` он рвёт **все** отслеженные сокеты в первой же строке, до
`httpServer.close()`. Воспроизвёл на голом Node: запрос в полёте получает
`curl: (52) Empty reply from server`, а обработчик при этом досчитывает и пишет ответ
в уничтоженный сокет. Это прямое нарушение третьего пункта DoD.

**А вот `return503OnClosing: true` — кандидат, но с изъяном.** Он навешивает middleware,
который на время остановки отдаёт `503` и заголовок `Connection: close`. Изъян в том, что
он отвечает `503` на **все** роуты, включая liveness `/health`. Урок 0006 был ровно про
то, почему liveness и readiness — разные ручки. Решай сам и назови выбор на ревью.

**Что на Node 26 закрывается само, а что вешает процесс.** Проверил на голом HTTP-сервере,
`server.close()` без всего:

| что держит соединение | сколько жил процесс после SIGTERM |
| --- | --- |
| праздное keep-alive соединение | 0.13 s — не мешает вообще |
| запрос в полёте, 3 s работы | 3.83 s, клиент получил свои `200` |
| пришла половина заголовков запроса | **жив спустя 14 s**, спасает только SIGKILL |

Третья строка — это `headersTimeout`, у него умолчание 60 секунд. `closeIdleConnections()`
её не лечит: соединение, у которого начался разбор запроса, не считается праздным.
Вывод: **дедлайн обязателен**, и он часть смысла graceful shutdown, а не страховка.

**В контейнере у тебя три процесса, и сигнал не доходит до третьего.** `docker exec` в
живой `barabas-api-1`:

```
PID   PPID  COMMAND
    1     0 pnpm --filter server dev
   35     1 node .../@nestjs/cli/bin/nest.js start --watch
  202    35 node --enable-source-maps .../dist/main
```

`SIGTERM` от `docker compose stop` приходит в PID 1, то есть в `pnpm`. Проверил локально
на отдельном стенде: дочерний процесс с обработчиками на `SIGTERM`, `SIGINT` и `SIGHUP`
и логом на `exit` **не записал ни одной строки** — ни один обработчик не выполнился, процесс
умер жёстко. Значит, в dev-образе второй пункт DoD сейчас недостижим в принципе: сколько
graceful shutdown ни пиши, до `node` сигнал не дойдёт. Это точка решения, пункт 10.

**`stop_grace_period` в `docker-compose.yml` не задан** — значит, в силе умолчание Docker:
10 секунд, потом `SIGKILL`. Твой дедлайн из пункта 7 обязан быть заметно меньше этого
числа, иначе дедлайн никогда не сработает — контейнер убьют раньше.

**`pool.end()` ждёт возврата всех клиентов.** Запрос, взявший клиента через `pool.connect()`
и зависший, держит `end()` навсегда. Индикатор из `M0-05` как раз такой клиент и берёт.
Поэтому дедлайн стоит не только на дренаже, а на остановке целиком.

**Почему это вообще важно здесь, а не «в общем случае».** Незакрытая транзакция уходит
вместе с процессом, но не вместе с блокировкой: строки остаются захваченными, пока
PostgreSQL не заметит обрыв TCP, а с мёртвым сокетом он замечает не сразу. В M4 эти строки
будут местами в зале, и очередь покупателей встанет на деплое — при том, что «деплой прошёл
успешно». Это тот же `client.release(true)` из `M0-05`, только на уровне всего процесса.

## План работ

Отмечай пункты по ходу прямо здесь.

- [x] **1. Ветка.** `06-graceful-shutdown` от текущей.
      *Готово, когда:* `git status` чистый, ветка своя.

- [x] **2. Сигнал доходит и виден.** `app.enableShutdownHooks()` в `main.ts` плюс строка
      в лог о том, какой сигнал пришёл.
      **Ловушка:** вызов без аргументов подписывается на все 11 сигналов из `ShutdownSignal`,
      включая `SIGSEGV` и `SIGUSR2`. Сузь список до тех, которые действительно означают
      «пора остановиться», и будь готов объяснить выбор.
      *Готово, когда:* `kill -TERM <pid>` локально → в логе строка с именем сигнала,
      процесс завершается.

- [x] **3. Закрытие пула и Redis в `onApplicationShutdown`.** Порядок внутри хука: сначала
      Postgres, потом Redis, каждое закрытие — со своей строкой в логе.
      **Ловушка:** оба провайдера у тебя `useFactory`, возвращающий чужой объект — `Pool`
      и `Redis`. У этих объектов нет метода `onApplicationShutdown`, и Nest их не вызовет,
      сколько интерфейсов на них ни вешай. Хук обязан жить на **твоём** классе: либо на
      классе модуля, либо на отдельном провайдере, которому пул инжектится.
      *Готово, когда:* в логе последовательность «сигнал → сервер закрыт → пул закрыт →
      redis закрыт», и после этого процесс выходит сам, без `kill -9`.

- [x] **4. Readiness начинает отдавать `503` до закрытия.** Заведи состояние «останавливаюсь»
      и научи `/health/ready` его учитывать; `/health` при этом остаётся `200` — инстанс жив,
      он просто больше не берёт трафик.
      **Точка решения:** как именно readiness узнаёт о состоянии — отдельный индикатор
      в списке `health.check([...])`, guard на роуте или проверка в контроллере до вызова
      terminus. Выбери и скажи, почему; заодно реши, брать ли `return503OnClosing` из Nest
      вместо своего состояния — и что тогда будет с `/health`.
      *Готово, когда:* после `SIGTERM` и до фактической остановки `curl` показывает
      `/health` → `200`, `/health/ready` → `503`.

- [x] **5. Пауза на вывод из балансировки.** В `beforeApplicationShutdown` — задержка
      между «readiness сказал `503`» и «перестаём принимать соединения». Длительность —
      в env-схему, рядом с остальными настройками, с умолчанием и обоснованием.
      **Ловушка:** в тестах эта пауза умножится на число e2e-файлов, потому что `app.close()`
      идёт ровно тем же путём. Значение должно уметь становиться нулём.
      **Точка решения:** число. Свяжи его с `periodSeconds` пробы (то же рассуждение, что
      в `M0-05`, пункт 8) и с `stop_grace_period` из пункта 10 — оно обязано поместиться
      внутрь бюджета остановки вместе с дренажем.
      *Готово, когда:* в логе видно, что между строкой про `503` и строкой про закрытие
      сервера прошло заданное время, и оно совпадает с настройкой.

- [x] **6. Дедлайн на всю остановку.** Таймер, который при истечении пишет строку в лог
      и выходит с ненулевым кодом. Он не отменяет ничего из предыдущих пунктов — он
      страхует от того, чего они не покрывают.
      **Ловушка:** сам таймер не должен удерживать процесс, когда всё прошло штатно
      (`unref` или `clearTimeout`) — иначе быстрая остановка станет медленной ровно
      на длину дедлайна.
      **Почему он обязателен, а не «на всякий случай»:** соединение, приславшее половину
      заголовков, вешает закрытие на `headersTimeout` — это 60 секунд по умолчанию, я мерил.
      Плюс `pool.end()` не завершится, пока зависший запрос держит клиента.
      *Готово, когда:* есть вывод, где остановка упёрлась в дедлайн — процесс вышел сам
      с ненулевым кодом, а не был убит снаружи. Чтобы это воспроизвести, нужен клиент,
      который начал запрос и не дослал его (`printf 'GET /health HTTP/1.1\r\n'` в `nc`
      без завершающей пустой строки — этого достаточно).

- [x] **7. Запрос в полёте доживает — тест.** E2E: начать медленный запрос, во время него
      закрыть приложение, убедиться, что клиент получил полный ответ, а не обрыв.
      **Ловушка:** существующие e2e тоже пойдут новым путём — `app.close()` теперь дёргает
      хуки. Подменённые в `M0-05` `POSTGRES` и `REDIS` — это объекты с `connect` и `ping`,
      но без `end`/`quit`; первый же прогон это покажет.
      *Готово, когда:* `pnpm test:e2e` зелёный, и в нём есть тест, который краснеет от
      мутации из пункта 11.

- [x] **8. Код выхода и последние строки лога.** Проверь, что именно печатает процесс
      перед смертью: у тебя в dev pino пишет через `transport`, то есть в отдельном потоке.
      **Точка решения:** `enableShutdownHooks(signals, { useProcessExit: true })` даёт код
      `0` и даёт логгеру дописать буфер; без него Nest шлёт сигнал сам себе и код будет
      `143`. У обоих вариантов есть цена — выбери и обоснуй.
      *Готово, когда:* есть `echo $?` после остановки и последние три строки лога, которые
      действительно доехали до терминала.

- [x] **9. Docker: чтобы сигнал дошёл до `node`.** Сейчас PID 1 — это `pnpm`, а под ним
      ещё `nest` и только потом `node`; я проверил, что `pnpm` не доносит `SIGTERM` до
      своего ребёнка. Плюс задай `stop_grace_period` явно, а не полагайся на умолчание.
      **Точка решения:** как решать. Укоротить цепочку в dev-образе; или признать, что
      graceful shutdown проверяется на production-таргете, где `CMD` — это сразу
      `node dist/main.js`; или что-то третье. Назови выбор и его цену на ревью.
      *Готово, когда:* `time docker compose stop api` укладывается заметно быстрее
      `stop_grace_period`, а в логах контейнера перед остановкой видна вся
      последовательность из пункта 4. Десять секунд ровно — это не «успели», это `SIGKILL`.

- [x] **10. Мутация.** Перенеси закрытие пула из `onApplicationShutdown` в `onModuleDestroy`
      и убедись, что тест из пункта 8 краснеет. Верни обратно, мутацию не коммить.
      *Готово, когда:* есть вывод обоих прогонов — до и после.

- [x] **11. Гейты и ревью.** `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`,
      `pnpm test:e2e` — все зелёные, потом зови на ревью.

## Что спрошу на ревью словами

- Почему пул нельзя закрыть в `onModuleDestroy`. Ответ на один абзац, без кода.
- Что именно происходит с блокировками в PostgreSQL, если процесс умер с открытой
  транзакцией, и почему для зала на 2000 мест это хуже, чем для склада.
- Зачем нужна пауза в пункте 6, если сервер и так дожидается запросов в полёте.

### 2026-09-15 — триаж

Issue переведён в `ready-for-human`. Добавлены: проверенный порядок хуков Nest 12, замеры
по тому, что вешает `server.close()`, находка про цепочку `pnpm → nest → node` в контейнере,
разбор `forceCloseConnections` и `return503OnClosing`, план из 12 пунктов.

**Что появилось.** `core/lifecycle/`: `ShutdownState` (флаг «останавливаюсь») и
`ShutdownService`, который держит все три хука. `health/indicators/shutdown.health.ts` —
индикатор для readiness. Две переменные в схеме env: `SHUTDOWN_DRAIN_DELAY_MS` (5000) и
`SHUTDOWN_TIMEOUT_MS` (15000), с cross-field проверкой «дедлайн строго больше паузы».

**Точка решения, пункт 4 — как readiness узнаёт о состоянии.** Отдельный индикатор в
списке `health.check([...])`, а не guard и не проверка в контроллере: terminus продолжает
владеть кодом `503` и формой тела, и останавливающийся инстанс назван в `error.shutdown`
так же, как называется любая упавшая зависимость. `return503OnClosing` отвергнут — он
отвечает `503` на все роуты, включая liveness `/health`, то есть kubernetes перезапускал бы
контейнер, который просто останавливается (урок 0006).

**Находка, которой не было на триаже:** terminus умеет это сам. `HealthCheckExecutor`
регистрирует собственный `beforeApplicationShutdown`, поднимает `isShuttingDown` и отдаёт
`status: "shutting_down"` + `503` (`health-check-executor.service.js:93`,
`health-check.service.js:57`). То есть `503` мы получили бы и без своего индикатора. Свой
оставлен сознательно: он не зависит от того, в каком порядке Nest обойдёт модули в фазе
`beforeApplicationShutdown`, и называет причину явно. Там же лежит альтернатива паузе из
пункта 5 — опция `TerminusModule.forRoot({ gracefulShutdownTimeoutMs })`; не взята, чтобы
весь бюджет остановки задавался в одном месте, через env.

**Точка решения, пункт 8 — `useProcessExit: true`.** Цена: остановка по `SIGTERM` даёт код
`0`, а не `143`. Платим потому, что в dev pino пишет через `transport`, то есть отдельный
поток, и смерть от сигнала теряет как раз те строки, которые описывают остановку. Дедлайн
при этом выходит с `1`, так что «остановился плохо» по коду по-прежнему отличимо.

**Точка решения, пункт 9 — dev-таргет не чинится, проверка на production.** Замер: SIGTERM
до `node` в dev-образе **доходит** (вопреки предположению на триаже), но `pnpm` и `nest` не
ждут потомка и выходят сразу — контейнер останавливается за 3.0 с посреди дренажа с кодом
`137`, в логе только первая строка. На production-таргете PID 1 — сам `node dist/main.js`.
`stop_grace_period: 30s` задан явно, оговорка про dev записана комментарием в compose.

#### Вывод, на который это опирается

Штатная остановка, `node dist/main.js`, `SHUTDOWN_DRAIN_DELAY_MS=5000`:

```
=== до сигнала ===        /health = 200   /health/ready = 200
=== через 1 с после SIGTERM, идёт пауза на дренаж ===
                          /health = 200   /health/ready = 503
{"status":"shutting_down","info":{"postgres":{"status":"up"},"redis":{"status":"up"}},
 "error":{"shutdown":{"message":"shutting down","status":"down"}}}
=== exit code = 0, остановка заняла 5.0 c ===
```

Дедлайн, `SHUTDOWN_TIMEOUT_MS=4000`, клиент прислал половину заголовков и замолчал:

```
[15:58:46.521] INFO  shutdown signal received, readiness now reports 503  signal: SIGTERM delayMs: 1000
[15:58:47.528] INFO  drain delay elapsed, closing http server             signal: SIGTERM
[15:58:50.522] FATAL shutdown deadline exceeded, exiting the hard way     timeoutMs: 4000

... drain delay elapsed → http server closed → postgres closed → redis closed
```
