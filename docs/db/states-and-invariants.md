# Состояния и инварианты: Hold, HoldItem

Рабочий документ issue `M1-02`. Закрывает пункт 7 (предмет удержания и место, где живёт
уникальность) и пункт 10 (чем на диаграмме держится каждый инвариант). Читается вместе с
[er-model.md](./er-model.md).

Значения статусов отсюда попадают в миграцию `M1-05`, предикат частичного индекса — в `M1-10`.

## Принятые решения

| #   | Решение                                                                                                                                                                                                          | Статус  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| 1   | Инвариант «одно место — один активный Hold» держит **база**, а не дисциплина кода: partial unique index по `hold_item`. Поддержка в Drizzle подтверждена спайком в [ADR-0004](../adr/0004-data-layer-drizzle.md) | принято |
| 2   | `HoldItem` знает только «держит / не держит» (вариант A). Исход холда — истёк, отменён, подтверждён — живёт в `Hold.status`                                                                                      | принято |
| 3   | Источник правды — `Hold.status`; `HoldItem.status` — его материализация на уровне позиции. Синхронизируются одной транзакцией, схемой это не гарантируется                                                       | принято |
| 4   | Просроченные холды гасит **фоновый sweeper**. Ленивое истечение на конфликте — известное продолжение, когда окно начнёт мешать                                                                                   | принято |

## `hold_status` — состояния `Hold`

| Значение    | Что означает                                   | Кто ставит                                          |
| ----------- | ---------------------------------------------- | --------------------------------------------------- |
| `active`    | создан, `expires_at` в будущем, не подтверждён | создание холда                                      |
| `confirmed` | подтверждён, из него сделан `Order`            | подтверждение, в одной транзакции с созданием Order |
| `expired`   | `expires_at` прошёл, никто не подтвердил       | фоновый sweeper (решение 4)                         |
| `cancelled` | покупатель отказался сам, до истечения         | действие покупателя                                 |

`expired` и `cancelled` разделены намеренно: по одному булеву флагу «истёк сам» и «отменили
руками» неразличимы, а для разбора «почему место освободилось» разница нужна.

Разрешённые переходы:

```
active → confirmed     подтверждение до истечения
active → expired       время вышло
active → cancelled     отказ покупателя
```

Из `confirmed`, `expired`, `cancelled` переходов нет — это терминальные состояния.

## `hold_item_status` — состояния `HoldItem`

| Значение   | Что означает                                           |
| ---------- | ------------------------------------------------------ |
| `active`   | место занято этой позицией, строка **входит в индекс** |
| `released` | место отпущено, строка вне индекса                     |

Предикат частичного уникального индекса:

```sql
CREATE UNIQUE INDEX hold_item_one_active_per_event_seat
    ON hold_item (event_seat_id)
 WHERE status = 'active';
```

**Это и есть место, где физически невозможно продать одно место дважды.**

Две вещи, которые следуют из варианта A и которые легко забыть:

1. **`active` вечен для проданных мест.** После подтверждения холда и выпуска билета позиция
   остаётся `active` — иначе между подтверждением и появлением `Ticket` место на мгновение
   освободится, и его успеет забрать чужой холд. То есть `active` в этой колонке означает не
   «удержание живо», а «место занято этой строкой».
2. **Гашение просроченных обязано смотреть в `Hold`.** Отпускать можно только позиции, у
   которых холд одновременно `status = 'active'` и `expires_at < now()`. Если условие по
   `Hold.status` пропустить, запрос отпустит места **оплаченных** заказов. Тест на это —
   обязателен в `M1-08`.

## Иерархия источников правды

```
Hold.expires_at     ← истина (время)
      ↓ материализует; отстаёт не более чем на период sweeper'а
Hold.status         ← истина для позиций (решение 3)
      ↓ материализует; отстаёт на ту же транзакцию
HoldItem.status     ← то, что читает предикат индекса
```

Каждый уровень отстаёт от предыдущего. Отставание — **баг доступности, а не корректности**:
двойной продажи в окне отставания не случится (индекс стоит, место занято), свободное место
просто некоторое время выглядит занятым.

## Решение 4: просроченные холды гасит фоновый sweeper

В базе ничего не происходит само, когда `expires_at` проходит. Кто-то должен записать.

| Стратегия                              | Окно рассинхрона | Чем платим                                                                                                 |
| -------------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| Фоновый sweeper (cron / BullMQ)        | период запуска   | батчи, блокировка от параллельных инстансов, метрика «воркер умер»                                         |
| Ленивое истечение на конфликте `23505` | ноль             | retry-путь в коде, запись в чужой агрегат из запроса покупателя, риск дедлока (`M4-08`)                    |
| Фильтр по времени только в чтении      | ноль на чтении   | запись всё равно упрётся в индекс: страница покажет «свободно», покупка упадёт. Самостоятельно не работает |

**Выбран sweeper**, по трём причинам: он тестируется без конкурентности (а значит проверяется
уже в `M1-08`, задолго до `M4`); он даёт верхнюю границу рассинхрона, которую можно назвать
числом; он же даёт метрику для `Reconciliation` — если sweeper отстал,
`проданные + удержанные + свободные ≠ вместимость`.

Ленивое истечение — известное продолжение, а не запасной план: `ON CONFLICT (...) WHERE ...`
уже проверен спайком в ADR-0004, порядок захвата — тема `M4-08`.

Что придётся сделать вместе с ним (не в этом issue, но список нужен уже сейчас):

- гасить **одной транзакцией** `hold.status = 'expired'` и `hold_item.status = 'released'`;
- обязательное условие `hold.status = 'active' AND hold.expires_at < now()` — без первой
  половины запрос отпустит места оплаченных заказов;
- индекс на `hold (status, expires_at)`, иначе каждый тик — seq scan по всем холдам;
- батчи с `LIMIT`, иначе первый запуск после инцидента возьмёт блокировки на всю таблицу;
- защита от параллельных инстансов: `pg_try_advisory_lock` или repeatable job в BullMQ
  (Redis в стеке уже есть);
- метрика «холдов просрочено, но не погашено» — иначе умерший воркер тихо остановит продажи.

## Пункт 10: чем держится каждый инвариант

Таблица «Агрегаты и их инварианты» из [CONTEXT.md](../../CONTEXT.md), сверху вниз.

| Агрегат              | Инвариант                                           | Чем держится                                                                                         |
| -------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Seat**             | место удерживается не более чем одним активным Hold | partial unique index `hold_item (event_seat_id) WHERE status = 'active'`                             |
| **Seat**             | проданное место нельзя удержать заново              | та же строка остаётся `active` после подтверждения (вариант A)                                       |
| **TicketAllocation** | `held + sold <= capacity`                           | ❌ не разобрано — ненумерованная секция, пункт 6                                                     |
| **TicketAllocation** | `available` не отрицателен                          | ❌ не разобрано — пункт 6, `CHECK` на строке счётчика                                                |
| **Hold**             | Hold непустой                                       | ничем в схеме: «есть хотя бы одна дочерняя строка» без deferrable trigger не выразить — код агрегата |
| **Hold**             | `expiresAt > createdAt`                             | `CHECK` в пределах одной строки `hold`                                                               |
| **Hold**             | истёкший Hold нельзя подтвердить                    | ничем в схеме: сравнение с текущим временем немутабельно — код агрегата                              |
| **Hold**             | принадлежит ровно одному покупателю                 | `hold.user_id` FK NOT NULL                                                                           |
| **Order**            | `total = Σ(item.price × qty)`                       | ❌ дыра: `order_item` не ссылается на покупаемое, пункт 8                                            |
| **Order**            | переходы только по разрешённой схеме                | ❌ не разобрано, пункт 8                                                                             |
| **Order**            | оплаченный заказ нельзя оплатить второй раз         | ❌ дыра: у `payment` нет ключа идемпотентности, хотя словарь определяет Payment через неё            |
| **Ticket**           | гасится ровно один раз                              | ❌ дыра: `check_in.ticket_id` — FK без `UNIQUE`                                                      |

Строки с ❌ — задел для пунктов 6 и 8; без ответа их закрывать нельзя.

## Правило про колонки из будущих этапов

Колонка из будущего этапа попадает на M1-диаграмму, если она упомянута в `CONTEXT.md`
(решено 2026-09-16). Под правило подпадают `user.role` и `user.email_verified` — оба из `M3`,
оба следуют из статьи словаря про `User`. Всё, что словарём не названо, на диаграмме не
появляется: раздел «На что смотрю на ревью» в `M1-02` запрещает колонки на будущее.

## Решённые вопросы именования

- **Значения `hold_item_status` — `active` / `released`** (решено 2026-09-16). Рассматривалась
  пара `occupied` / `released`, которая точнее описывает смысл колонки: по варианту A позиция
  остаётся `active` и после продажи, то есть говорит «место занято», а не «удержание живо».
  Выбраны `active` / `released` — значение совпадает с предикатом индекса и с тем, как это
  состояние называют во всех текстах проекта. Цена — см. ловушку 1 в разделе про
  `hold_item_status`: читатель может решить, что просроченные холды не гасятся. Ловушка
  снимается комментарием к индексу в миграции `M1-05`.
- **Два enum-типа**, `hold_status` и `hold_item_status` (решено 2026-09-16). Наборы значений
  не пересекаются: общий тип не содержал бы `released` и делал бы `confirmed` / `expired` /
  `cancelled` представимыми для позиции, где они ничего не значат.
- **`Order.status`** изобретать не надо — значения заданы словарём: `pending → paid → fulfilled`,
  либо `cancelled` / `refunded`. Колонка называется `status` во всех таблицах (решено
  2026-09-16, `state` больше не используется).
