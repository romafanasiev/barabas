# Состояния и инварианты: Hold и его позиции

Рабочий документ issue `M1-02`. Закрывает пункт 6 (два механизма учёта), пункт 7 (предмет
удержания и место, где живёт уникальность) и пункт 10 (чем на диаграмме держится каждый
инвариант). Читается вместе с [er-model.md](./er-model.md).

Значения статусов отсюда попадают в миграцию `M1-05`, предикат частичного индекса — в `M1-10`.

## Принятые решения

| #   | Решение                                                                                                                                                                                                          | Статус  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| 1   | Инвариант «одно место — один активный Hold» держит **база**, а не дисциплина кода: partial unique index по `hold_seat_item`. Поддержка в Drizzle подтверждена спайком в [ADR-0004](../adr/0004-data-layer-drizzle.md) | принято |
| 2   | Позиция холда знает только «держит / не держит» — **узкий статус**. Исход холда: истёк, отменён, подтверждён — живёт в `Hold.status`                                                                            | принято |
| 3   | Источник правды — `Hold.status`; статус позиции — его материализация на уровне строки. Синхронизируются одной транзакцией, схемой это не гарантируется                                                          | принято |
| 4   | Просроченные холды гасит **фоновый sweeper**. Ленивое истечение на конфликте — известное продолжение, когда окно начнёт мешать                                                                                   | принято |
| 5   | Вместимость на продажу задаётся в `TicketAllocation.capacity`; `Section.capacity` — физический предел зала, и квота не может его превышать. Держит **схема**: копия `section_capacity` плюс составной FK с `ON UPDATE CASCADE` | принято |
| 6   | Развилка «место или квота» — **две независимые таблицы позиций** без общего супертипа: `hold_seat_item` и `hold_allocated_item`. Ниже `Hold` ветки сливаются: `Order`, `Ticket`, `CheckIn` — по одной таблице        | принято |
| 7   | Ненумерованная секция учитывается **материализованным счётчиком** `ticket_allocation` (`held`, `sold`, `capacity`), ключ `(event_id, section_id)`, тип билета — колонкой в той же строке                            | принято |
| 8   | Цена живёт в `ticket_type` вместе с типом: тип принадлежит событию (`UK (event_id, type)`), отдельной таблицы `ticket_price` нет. История цены держится копиями в `ticket.ticket_price` и `order_item.price`        | принято |
| 9   | Учёт секции двумя способами сразу запрещается **схемой**: дискриминатор `section_type` в дочерних таблицах плюс составной FK на `section (id, type)`. Триггер рассмотрен и отвергнут                                | принято |
| 10  | Границы агрегатов помечаются **комментарием у атрибута** (`"aggregate root: Hold"`, `"part of Hold"`), потому что только он попадает в рендер. Сущность без пометки живёт вне агрегатов                             | принято |
| 11  | Место, существующее в событии, **всегда продаётся**: `event_seat.ticket_type_id NOT NULL`. Снятия отдельного места с продажи в модели нет                                                                          | принято |
| 12  | `order_item` ссылается на покупаемое **парой nullable FK** (`event_seat_id`, `allocation_id`) с `CHECK` «ровно одна заполнена, и `quantity` согласован». Прямое следствие слияния веток ниже `Hold`                | принято |
| 13  | Один `Order` на один `Hold`: `order.hold_id` **`NOT NULL`** с `UNIQUE`. Заказа в обход удержания не существует. Покупатель берётся джойном через `hold.user_id`, своей колонки у заказа нет                         | принято |
| 14  | Успешный платёж **неизменяем**: возврат не переводит его в другой статус, а записывается отдельно. Значит `succeeded` — терминальное состояние строки `payment`                                                    | принято |
| 15  | `Ticket` ссылается на **платёж**, и только на успешный: `payment_id` плюс дискриминатор `payment_status` с `CHECK` и составным FK на `payment (id, status)`. «Билет не раньше оплаты» — гарантия схемы             | принято |
| 16  | Предмет билета — та же пара nullable FK, что у позиции заказа: `event_seat_id` / `allocation_id` с `CHECK` «ровно одна заполнена». Колонки `seat_id` и `event_id` из `ticket` уходят                                | принято |
| 17  | Второй рубеж против двойной продажи места: `UNIQUE INDEX ON ticket (event_seat_id) WHERE event_seat_id IS NOT NULL`. Квотных билетов не касается — там количество стережёт `sold`                                   | принято |
| 18  | Строка `payment` создаётся **до** обращения к провайдеру, в статусе `pending`. Статусы: `pending → succeeded \| failed`, оба исхода терминальны, повтор после неудачи — новая строка                                | принято |
| 19  | Ключ идемпотентности приходит от клиента и уникален **глобально**: `UNIQUE (idempotency_key)`                                                                                                                      | принято |
| 20  | «Оплаченный заказ нельзя оплатить второй раз» держит схема: `UNIQUE INDEX ON payment (order_id) WHERE status = 'succeeded'`                                                                                        | принято |
| 21  | Валюта — **справочная таблица** `currency`, на неё смотрят FK из `ticket_type`, `order`, `order_item`, `payment`, `ticket`. Совпадение валют между заказом и платежом этим **не** закрывается                      | принято |
| 22  | Валюта заказа едина для платежа и позиций: `UNIQUE (id, currency)` на `order`, составной FK `(order_id, currency)` из `payment` и из `order_item`. `ticket` остаётся вне правила                                    | принято |
| 23  | Состояния `fulfilled` в `order_status` нет: «билеты выпущены» видно по наличию строк `ticket`, отдельного флага для этого не заводим                                                                                | принято |
| 24  | `order.total_price` **не хранится**: сумма считается запросом по `order_item`. Инвариант `total = Σ(item.price × qty)` исчезает — расходиться нечему                                                                | принято |
| 25  | Оплаченный заказ отменить нельзя: `paid` терминален в `M1`. Отмена после оплаты — это возврат, и он появляется в `M3`                                                                                               | принято |

## `hold_status` — состояния `Hold`

| Значение    | Что означает                                   | Кто ставит                                          |
| ----------- | ---------------------------------------------- | --------------------------------------------------- |
| `active`    | создан, `expires_at` в будущем, не подтверждён | создание холда                                      |
| `confirmed` | подтверждён, из него сделан `Order`            | подтверждение, в одной транзакции с созданием Order |
| `expired`   | `expires_at` прошёл, никто не подтвердил       | фоновый sweeper (решение 4)                         |
| `cancelled` | покупатель отказался сам, до истечения         | действие покупателя                                 |

`expired` и `cancelled` разделены намеренно: по одному булеву флагу «истёк сам» и «отменили
руками» неразличимы, а для разбора «почему место освободилось» разница нужна.

Разрешённые переходы:

```
active → confirmed     подтверждение до истечения
active → expired       время вышло
active → cancelled     отказ покупателя
```

Из `confirmed`, `expired`, `cancelled` переходов нет — это терминальные состояния.

## `hold_item_status` — состояния позиции

Один enum на обе таблицы позиций: наборы значений совпадают, различается только предмет.

| Значение   | В `hold_seat_item`                                     | В `hold_allocated_item`                                  |
| ---------- | ------------------------------------------------------ | -------------------------------------------------------- |
| `active`   | место занято этой позицией, строка **входит в индекс** | `quantity` этой строки входит в `ticket_allocation.held`  |
| `released` | место отпущено, строка вне индекса                     | количество возвращено в `held`, строка его больше не даёт |

Два частичных уникальных индекса, по одному на ветку:

```sql
CREATE UNIQUE INDEX hold_seat_item_one_active_per_event_seat
    ON hold_seat_item (event_seat_id)
 WHERE status = 'active';

CREATE UNIQUE INDEX hold_allocated_item_one_active_per_allocation
    ON hold_allocated_item (hold_id, allocation_id)
 WHERE status = 'active';
```

**Первый и есть место, где физически невозможно продать одно место дважды.** Второй слабее по
смыслу: он запрещает две активные позиции на одну квоту внутри одного холда — то есть
схлопывает «взял два входа и ещё три» в одну строку, — но вместимость стережёт не он, а
`CHECK` на строке счётчика. Это разные по силе инструменты, и путать их нельзя.

Две вещи, которые следуют из узкого статуса и которые легко забыть:

1. **`active` вечен для проданных мест.** После подтверждения холда и выпуска билета позиция
   остаётся `active` — иначе между подтверждением и появлением `Ticket` место на мгновение
   освободится, и его успеет забрать чужой холд. То есть `active` в этой колонке означает не
   «удержание живо», а «место занято этой строкой».
2. **Гашение просроченных обязано смотреть в `Hold`.** Отпускать можно только позиции, у
   которых холд одновременно `status = 'active'` и `expires_at < now()`. Если условие по
   `Hold.status` пропустить, запрос отпустит места **оплаченных** заказов. Тест на это —
   обязателен в `M1-08`. Для квоты цена ошибки та же, но громче: вместе со статусом уедет
   `held`, и счётчик начнёт расходиться с реальностью — ровно то, что ловит `Reconciliation`.

## Иерархия источников правды

```
Hold.expires_at             ← истина (время)
      ↓ материализует; отстаёт не более чем на период sweeper'а
Hold.status                 ← истина для позиций (решение 3)
      ↓ материализует; отстаёт на ту же транзакцию
HoldSeatItem.status         ← то, что читает предикат индекса
HoldAllocatedItem.status    ← то же самое для квоты
      ↓ материализует; отстаёт на ту же транзакцию
TicketAllocation.held       ← сумма quantity активных позиций; то, что читает CHECK
```

Каждый уровень отстаёт от предыдущего. Отставание — **баг доступности, а не корректности**:
двойной продажи в окне отставания не случится (индекс стоит, место занято), свободное место
просто некоторое время выглядит занятым.

У ветки квоты последний уровень длиннее на шаг, и этот шаг — единственный, который база
проверяет: `CHECK` читает `held`, а не сумму по позициям. Значит расхождение между `held` и
строками `hold_allocated_item` не будет замечено ничем, кроме `Reconciliation`. Отсюда
правило: обе записи всегда в одной транзакции, без исключений.

## Решение 4: просроченные холды гасит фоновый sweeper

В базе ничего не происходит само, когда `expires_at` проходит. Кто-то должен записать.

| Стратегия                              | Окно рассинхрона | Чем платим                                                                                                 |
| -------------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| Фоновый sweeper (cron / BullMQ)        | период запуска   | батчи, блокировка от параллельных инстансов, метрика «воркер умер»                                         |
| Ленивое истечение на конфликте `23505` | ноль             | retry-путь в коде, запись в чужой агрегат из запроса покупателя, риск дедлока (`M4-08`)                    |
| Фильтр по времени только в чтении      | ноль на чтении   | запись всё равно упрётся в индекс: страница покажет «свободно», покупка упадёт. Самостоятельно не работает |

**Выбран sweeper**, по трём причинам: он тестируется без конкурентности (а значит проверяется
уже в `M1-08`, задолго до `M4`); он даёт верхнюю границу рассинхрона, которую можно назвать
числом; он же даёт метрику для `Reconciliation` — если sweeper отстал,
`проданные + удержанные + свободные ≠ вместимость`.

Ленивое истечение — известное продолжение, а не запасной план: `ON CONFLICT (...) WHERE ...`
уже проверен спайком в ADR-0004, порядок захвата — тема `M4-08`.

Что придётся сделать вместе с ним (не в этом issue, но список нужен уже сейчас):

- гасить **одной транзакцией** `hold.status = 'expired'`, статус позиций в обеих таблицах и
  возврат `ticket_allocation.held` на сумму погашенных `quantity`;
- обязательное условие `hold.status = 'active' AND hold.expires_at < now()` — без первой
  половины запрос отпустит места оплаченных заказов;
- индекс на `hold (status, expires_at)`, иначе каждый тик — seq scan по всем холдам;
- батчи с `LIMIT`, иначе первый запуск после инцидента возьмёт блокировки на всю таблицу;
- защита от параллельных инстансов: `pg_try_advisory_lock` или repeatable job в BullMQ
  (Redis в стеке уже есть);
- метрика «холдов просрочено, но не погашено» — иначе умерший воркер тихо остановит продажи.

## Пункт 10: чем держится каждый инвариант

Таблица «Агрегаты и их инварианты» из [CONTEXT.md](../../CONTEXT.md), сверху вниз.

| Агрегат              | Инвариант                                           | Чем держится                                                                                         |
| -------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **EventSeat**        | место удерживается не более чем одним активным Hold | partial unique index `hold_seat_item (event_seat_id) WHERE status = 'active'`                        |
| **EventSeat**        | на место выпущен не более чем один билет            | partial unique index `ticket (event_seat_id) WHERE event_seat_id IS NOT NULL` (решение 17)           |
| **EventSeat**        | проданное место нельзя удержать заново              | та же строка остаётся `active` после подтверждения (узкий статус)                                     |
| **TicketAllocation** | `held + sold <= capacity`                           | `CHECK (held + sold <= capacity)` на строке счётчика: все три величины лежат в одной строке          |
| **TicketAllocation** | `available` не отрицателен                          | тем же `CHECK` плюс `CHECK (held >= 0 AND sold >= 0)`; `available` — не колонка, а `capacity - held - sold` |
| **TicketAllocation** | `capacity <= section.capacity`                      | `CHECK (capacity <= section_capacity)` плюс составной FK с `ON UPDATE CASCADE` (решение 5)           |
| **Hold**             | Hold непустой                                       | ничем в схеме, и по решению 6 считается по **двум** таблицам сразу — код агрегата                    |
| **Hold**             | `expiresAt > createdAt`                             | `CHECK` в пределах одной строки `hold`                                                               |
| **Hold**             | истёкший Hold нельзя подтвердить                    | ничем в схеме: сравнение с текущим временем немутабельно — код агрегата                              |
| **Hold**             | принадлежит ровно одному покупателю                 | `hold.user_id` FK NOT NULL                                                                           |
| **Order**            | `total = Σ(item.price × qty)`                       | инвариант снят: `total` не хранится, сумма производная (решение 24)                                  |
| **Order**            | валюта заказа, позиций и платежа совпадает          | `UNIQUE (id, currency)` на `order` + составной FK из `payment` и `order_item` (решение 22)           |
| **Ticket**           | валюта билета совпадает с валютой платежа           | ❌ сознательно не держится схемой — решение 22, ловится тестом                                       |
| **Order**            | переходы только по разрешённой схеме                | ничем в схеме: enum задаёт значения, но не стрелки — код агрегата, тест в `M1-08` (решения 23, 25)   |
| **Order**            | оплаченный заказ нельзя оплатить второй раз         | `UNIQUE INDEX payment (order_id) WHERE status = 'succeeded'` (решение 20); повтор запроса ловит `UNIQUE (idempotency_key)` (решение 19) |
| **Order**            | нельзя вернуть неоплаченный                         | возврата в `M1` не существует — правило переезжает в `M3` вместе с механикой (решение 14)            |
| **Ticket**           | гасится ровно один раз                              | `UNIQUE (ticket_id)` на `check_in` (поставлено 2026-09-17)                                            |

Осталась одна строка с ❌, и она такая **сознательно**: валюта билета против валюты платежа
(решение 22) — цена второго составного ключа на ту же таблицу сочтена несоразмерной, правило
ловится тестом. Это не дыра, а названная граница; произнести её на ревью нужно, закрывать —
нет.

Четыре инварианта держатся не схемой, а кодом агрегата, и это тоже осознанно: «Hold непустой»,
«истёкший Hold нельзя подтвердить», переходы `Order.status` и отсутствие возврата в `M1`.
Первые два невыразимы в принципе — «хотя бы одна дочерняя строка» требует deferrable trigger,
а сравнение с текущим временем немутабельно.

## Решение 6: две ветки позиций и место, где они сливаются

Принято 2026-09-17. Рассматривались четыре формы (разбор —
[урок 0007](../../lessons/0007-hold-that-does-not-know-what-it-holds.html)): одна таблица с
двумя nullable FK, супертип с двумя дочерними, две независимые таблицы, отказ от развилки
через строки `EventSeat` для ненумерованной секции.

**Выбраны две независимые таблицы.** Что из этого следует прямо в схеме:

- ни одной колонки, которая для половины строк ничего не значит: `quantity` есть только в
  `hold_allocated_item`, `event_seat_id` — только в `hold_seat_item`;
- ни одного развилочного `CHECK` вида «ровно одно из двух заполнено»;
- обе ссылки `NOT NULL`, то есть позиция, которая не держит ничего, непредставима;
- `status` лежит в той же таблице, что и ссылка, — оба частичных индекса строятся без оговорок.

Чем платим:

- у позиции холда **нет общего id**: сослаться на «позицию» одним внешним ключом снизу нельзя.
  Пока ниже `Hold` ссылок на позиции нет, цена нулевая; она появится в тот день, когда
  понадобится трассировка «из какой позиции вырос этот билет»;
- «Hold непустой» проверяется по двум таблицам;
- подтверждение и гашение трогают обе таблицы, а значит в `M4-08` детерминированный порядок
  захвата задаётся ещё и **между таблицами**, а не только между строками;
- enum `hold_item_status` общий на две таблицы: менять набор значений придётся помня про обе.

**Ниже `Hold` ветки сливаются.** `Order`, `Ticket` и `CheckIn` — по одной таблице. Основание:
единица в обеих ветках становится одинаковой — один проход, одна строка, один код; три входа
в фан-зону — это три `Ticket`, ровно как три места в партере. Инвариант «место продано один
раз» остаётся выше, в `hold_seat_item` (решение 2), и слияние его не задевает. Побочная
выгода: `CheckIn` сохраняет один FK на одну таблицу.

Цена слияния, которую надо помнить в `M1-06`: у `order_item` единица покупки разная — строка
для места и `quantity` для квоты, — значит эта таблица получает ту самую форму с двумя
nullable FK и `CHECK` вида «ровно одно из двух заполнено, и `quantity` согласован с тем, что
заполнено». Форма выбрана сознательно и ровно на одном звене.

## Решение 7: счётчик вместо строк

Принято 2026-09-17. Ненумерованная секция не имеет `Seat`, и учёт ведётся строкой
`ticket_allocation` с колонками `held`, `sold`, `capacity`.

Причина не в экономии строк, а в выразимости. Инвариант `held + sold <= capacity` — правило
над множеством: пока «сколько удержано» существует только как сумма по позициям, база его не
видит, потому что `CHECK` читает одну строку и не принимает подзапросы. Как только все три
величины оказались в одной строке, правило стало `CHECK`'ом и перестало зависеть от
дисциплины кода:

```sql
CHECK (held + sold <= capacity)
CHECK (held >= 0 AND sold >= 0)
```

`available` колонкой не является: это `capacity - held - sold`, и второй `CHECK` делает его
неотрицательность следствием, а не отдельным правилом.

Кто и когда меняет числа:

| Событие                  | Что происходит со счётчиком          | В одной транзакции с                            |
| ------------------------ | ------------------------------------ | ----------------------------------------------- |
| создание позиции холда   | `held = held + quantity`             | `INSERT` в `hold_allocated_item`                |
| подтверждение холда      | `held = held - quantity`, `sold = sold + quantity` | переводом `hold.status` в `confirmed` |
| истечение или отмена     | `held = held - quantity`             | переводом статуса позиции в `released`          |

Атомарность здесь — не про изоляцию, а про форму запроса: `SET held = held + :n` считает
внутри базы и сериализуется на блокировке строки, тогда как «прочитать, сложить в приложении,
записать» — классический lost update, от которого `CHECK` не спасает: он проверит то число,
которое ему привезли. Это же означает, что вся ненумерованная секция — одна строка, то есть
одна очередь на блокировку; цена названа здесь и вернётся в `M4`.

Денормализация оплачивается отдельно: `held` обязан совпадать с суммой `quantity` активных
позиций, и никакой constraint этого не проверяет. Сверка — это и есть `Reconciliation` из
словаря; обоснование самой денормализации — задача `M1-12`.

## Решение 9: одна секция — один способ учёта

Принято 2026-09-17. `section.type` задаёт вид секции, но сам по себе ничего не запрещает:
до этого решения ничто не мешало одной секции иметь и строки `seat` → `event_seat`, и строку
`ticket_allocation`. Место, посчитанное дважды, даёт расхождение `Reconciliation`, которое
потом невозможно объяснить.

Запрет ставится тем же приёмом «дискриминатор плюс составной FK», что рассматривался для
формы B в решении 6:

```sql
section           (id PK, type section_type NOT NULL, UNIQUE (id, type))

seat              (..., section_id, section_type section_type NOT NULL
                        CHECK (section_type = 'numbered'),
                   FOREIGN KEY (section_id, section_type)
                       REFERENCES section (id, type))

ticket_allocation (..., section_id, section_type section_type NOT NULL
                        CHECK (section_type = 'standing'),
                   FOREIGN KEY (section_id, section_type)
                       REFERENCES section (id, type))
```

Строка `ticket_allocation` требует, чтобы в `section` существовала пара `(id, 'standing')`.
У нумерованной секции там лежит `(id, 'numbered')` — пары нет, вставка падает. Симметрично
`seat` не встанет в стоячую секцию. Учёт двумя способами сразу становится непредставимым,
без единого триггера.

**`section_type` в дочерних таблицах — не обычная денормализация.** Копию стережёт тот же
внешний ключ, поэтому разъехаться с оригиналом она не может в принципе; в «иерархию
источников правды» эта колонка не попадает. Платим другим: **сменить тип секции нельзя, пока
в ней есть хоть одна строка** — `UPDATE section SET type = ...` упрётся в FK. Для продаж это
скорее правильное поведение, чем ограничение, но обнаружить его в `M1-08` как непонятную
ошибку было бы неприятно, поэтому оно записано здесь.

Триггер `BEFORE INSERT` на обеих таблицах даёт ту же гарантию и отвергнут: логика уезжает в
базу мимо TS-схемы Drizzle, не видна в типах и тестируется отдельно.

## Решение 10: как на диаграмме видно границы агрегатов

Принято 2026-09-17. Пометка ставится комментарием у атрибута:

```
Hold          { uuid id PK "aggregate root: Hold" }
HoldSeatItem  { uuid id PK "part of Hold" }
```

Причина выбора — рендер. `%%`-комментарий в исходнике Mermaid в SVG не попадает, а DoD
пункта 9 сформулирован через картинку: агрегат должен находиться за пять секунд, и должно
быть видно, какие сущности внутри, а какие — ссылки по id снаружи. Легенда рядом с блоком
```` ```mermaid ```` остаётся как оглавление, но не заменяет пометку.

Два следствия, о которые легко споткнуться:

1. **Комментарий у атрибута один.** Там, где он уже занят ключами (`hold_seat_item.id` несёт
   описание частичного индекса), пометку агрегата придётся либо дописать в ту же строку через
   разделитель, либо повесить на другую колонку. Разнобой здесь хуже, чем лишний символ:
   выбери один способ и держись его по всей диаграмме.
2. **Отсутствие пометки — тоже утверждение.** `Venue`, `Section`, `Seat`, `TicketType`, `User`
   остаются без комментария, потому что инвариантов не защищают и живут вне агрегатов —
   это прямо следует из раздела «Где DDD не применяется» в `CONTEXT.md`. На ревью пустая
   пометка читается как «забыл», поэтому одна строка про это нужна в легенде.

Состав каждого агрегата — пункт 9, обоснование границ — `M1-13`. Здесь зафиксирована только
нотация.

## Решение 11: место в событии всегда продаётся

Принято 2026-09-17. `event_seat.ticket_type_id` обязателен, связь `TicketType ||--o{ EventSeat`
имеет минимум «один». Места, которое существует в событии, но не продаётся — служебного,
выкупленного организатором, сломанного, — в модели нет.

Упрощение сознательное, но у него два следствия за пределами этого issue.

**Подготовка события обязана создать строку на каждое место.** Раз место без `event_seat` в
событии не существует, то концерт, для которого строки не сгенерированы, выглядит ровно как
распроданный — с той разницей, что об этом никто не узнает. Схема этого не ловит, значит:

- `M1-07` (seed) создаёт `event_seat` для всех мест всех нумерованных секций площадки и
  назначает каждому `ticket_type_id`;
- `Reconciliation` получает ещё одну проверку: число `event_seat` события сходится с суммой
  `capacity` нумерованных секций его площадки.

**Снятие места с продажи придёт в `M1-10`.** Когда появится soft delete с `deleted_at`,
придётся решить, что означает удалённое место и обязан ли предикат частичного уникального
индекса (`WHERE status = 'active'`) дополниться условием по нему. Здесь этот вопрос только
назван; решается он там.

## Решение 12: форма развилки в `order_item`

Принято 2026-09-17. Решение 6 слило ветки ниже `Hold`, и на позиции заказа это стоит ровно
того, что было названо заранее: единица покупки разная — строка для места и `quantity` для
квоты, — поэтому таблица получает две nullable FK и `CHECK`, который делает «ни одной» и
«обе сразу» непредставимыми:

```sql
order_item (
  ...,
  event_seat_id  uuid NULL REFERENCES event_seat (id),
  allocation_id  uuid NULL REFERENCES ticket_allocation (id),
  quantity       int  NOT NULL,
  CHECK (num_nonnulls(event_seat_id, allocation_id) = 1),
  CHECK ((event_seat_id IS NOT NULL AND quantity = 1) OR
         (allocation_id  IS NOT NULL AND quantity >= 1))
)
```

Это та самая форма, которую урок 0007 называет ловушкой, — и здесь она выбрана сознательно,
на **одном** звене цепочки и с известной ценой: `CHECK` придётся дописывать всякий раз, когда
у одной из веток появится собственный атрибут. Выше по цепочке, в `Hold`, развилка по-прежнему
выражена двумя таблицами (решение 6); ниже, в `Ticket`, единица одинаковая и развилки нет.

## Решение 13: один заказ на один холд

Принято 2026-09-17. `order.hold_id` с `UNIQUE`: из одного холда рождается не более одного
заказа. Подтверждение холда и создание заказа лежат в одной транзакции (см. `hold_status`),
поэтому второй заказ по тому же холду — это уже не бизнес-сценарий, а баг, и ловит его ключ,
а не проверка в сервисе.

**`hold_id` обязателен** (решено 2026-09-17). Причина не в удобстве: инвариант «место продано
один раз» держится partial unique index'ом на `hold_seat_item`, то есть на ветке холда. Заказ,
созданный в обход холда, шёл бы мимо единственного места, где стоит эта уникальность, — и
продажа одного места дважды снова стала бы возможной. `NOT NULL` закрывает путь целиком.

Цена: административная выдача билета — комп, приглашение, замена испорченного — обязана
создавать холд, пусть служебный и живущий секунду. Отдельного пути «выписать билет напрямую»
в модели нет.

Связь для диаграммы отсюда следует однозначно: `Hold ||--o| Order` — у холда ноль или один
заказ (истёкший холд заказа не имеет), у заказа ровно один холд.

**Покупатель берётся джойном** (решено 2026-09-17): `order.user_id` не существует, владелец
заказа — это `hold.user_id`. Одна истина, разъезжаться нечему, и в таблице инвариантов не
появляется ещё одной строки «держится кодом».

Цена: чтение «мои заказы» всегда идёт через `hold`. Заметить это придётся не сейчас, а в
`M8`, когда список заказов покупателя попадёт под замеры; денормализация остаётся известным
продолжением, а не запасным планом — колонку добавить дешевле, чем убрать.

## Решение 14: успешный платёж не мутирует

Принято 2026-09-17. Возврат не меняет статус исходной строки `payment` — она остаётся
`succeeded` навсегда.

**Сам возврат в `M1` не моделируется** — переезжает в `M3` (решено 2026-09-17). Значение
`refunded` в `order_status` при этом остаётся: оно названо словарём, а по правилу про колонки
из будущих этапов названное словарём на диаграмму попадает. Чем записывается операция
возврата — строкой в `payment` со знаком, отдельной таблицей `refund` или только статусом
заказа — решается там же, в `M3`. В `M1` из этого следует одно: сумма возврата нигде не
хранится, поэтому сверка с выпиской провайдера на этом этапе невозможна.

Зачем это зафиксировано раньше, чем выбрана ссылка билета: неизменяемость успеха делает
**бесплатным** составной FK «билет ссылается только на успешный платёж». Если бы статус
мутировал — при возврате или chargeback'е, — такой ключ держал бы переход до тех пор, пока
существуют билеты, и их пришлось бы аннулировать первыми. При терминальном `succeeded`
держать нечего.

Что из этого следует за пределами M1:

- chargeback и ошибочный `succeeded` (двойной webhook, подделанное уведомление) тоже не
  правят строку, а порождают новую запись — иначе решение перестаёт действовать;
- у `Ticket` нет статуса, поэтому после возврата билет неоткуда признать недействительным:
  гашение есть (`check_in`), аннулирования нет. В `M1` это осознанная дыра, упрётся она в
  `M3` на сканере.

## Решение 15: билет ссылается только на успешный платёж

Принято 2026-09-17. Рассматривались три ссылки — на `order`, на `order_item`, на `payment`.
Выбран `payment`, потому что только он позволяет сделать проверку «билет не раньше оплаты»
свойством схемы, а не дисциплиной кода:

```sql
payment (id PK, status payment_status NOT NULL, ..., UNIQUE (id, status))

ticket  (...,
         payment_id     uuid NOT NULL,
         payment_status payment_status NOT NULL CHECK (payment_status = 'succeeded'),
         FOREIGN KEY (payment_id, payment_status) REFERENCES payment (id, status))
```

**Почему обычного FK недостаточно** (вопрос возникает первым и заслуживает ответа наизусть).
`ticket.payment_id → payment.id` проверяет только существование строки; статус этой строки
внешнему ключу невидим, условий вида «и чтобы там было `succeeded`» в SQL нет. А строки
не-succeeded в таблице точно есть — это прямое следствие решения 18: строка создаётся в
`pending` до обращения к провайдеру, чтобы занять ключ идемпотентности, и остаётся в `failed`
при отказе. Значит простой FK пропустил бы билет, привязанный к отклонённому платежу.

Колонка `ticket.payment_status` связывает два условия в одно проверяемое: `CHECK` требует,
чтобы билет утверждал `succeeded`, а составной FK — чтобы такая пара действительно нашлась в
`payment`. Порознь ни одно из них гарантии не даёт.

Это не обычная денормализация: копия не может разойтись, её стережёт тот же ключ, а по
решению 14 `succeeded` терминален — переписать статус под выпущенными билетами нельзя. Тот же
дискриминатор, что `section_type` в решении 9.

Работает это в паре с решением 14: `succeeded` терминален, поэтому платёж не может стать
неуспешным после того, как билеты выпущены. Без неизменяемости успеха ключ пришлось бы
дополнять правилами отката.

**Что гарантирует схема:** билета, ссылающегося на неуспешный или ещё не прошедший платёж, не
существует. Это прямой ответ на вопрос плана «что мешает перепрыгнуть через звено» для
последнего шага цепочки.

**Чего не гарантирует** — произносить вслух вместе с гарантией, иначе она выглядит шире, чем
есть:

- что платёж относится к тому же заказу, из которого взяты место или квота: билет знает
  платёж и предмет, но связь между ними схемой не замкнута;
- что сумма платежа покрывает выпущенные билеты — правило над множеством строк, как и
  `total = Σ(item × qty)`;
- что на одно место не выпущено два билета — для этого нужна отдельная уникальность по
  предмету билета.

**Цена.** Третье применение приёма «дискриминатор плюс составной FK» (первые два — в решении
9, у `seat` и у `ticket_allocation`) и денормализованная колонка `ticket.payment_status`,
которая существует только ради ключа. Плюс работа, которой раньше не было: у `payment` появляется `payment_status` — свой
enum, свой набор значений и свои разрешённые переходы, — а также `UNIQUE (id, status)`.

## Решение 16: чем билет ссылается на предмет

Принято 2026-09-17. Та же форма, что в решении 12, и по той же причине: ниже `Hold` ветки
слиты, поэтому развилка выражается парой nullable FK, а не двумя таблицами билетов.

```sql
ticket (...,
        event_seat_id uuid NULL REFERENCES event_seat (id),
        allocation_id uuid NULL REFERENCES ticket_allocation (id),
        CHECK (num_nonnulls(event_seat_id, allocation_id) = 1))
```

`quantity` здесь, в отличие от `order_item`, не нужен: билет — это один проход, три входа в
фан-зону дают три строки.

**Что уходит из `ticket`:** `seat_id` и `event_id`. Пара дублировала строку `event_seat`,
которая существует ровно для этого; событие для квотного билета выводится через
`ticket_allocation.event_id`. Это тот же выбор, что в решении 13, — джойн вместо копии;
денормализация остаётся известным продолжением, если чтение «билеты на событие» попадёт под
замеры в `M8`.

Составной `UK (payment_id, seat_id, event_id, code)`, который стоял у `ticket` на диаграмме,
теряет смысл вместе с этими колонками: уникален сам `code`, и этого достаточно.

**Решение 17: второй рубеж против двойной продажи.** Решение 15 честно перечисляло, чего
схема не гарантирует, и первым пунктом там стояло «на одно место не выпущено два билета».
С появлением `event_seat_id` дыра закрывается одной строкой:

```sql
CREATE UNIQUE INDEX ticket_one_per_event_seat
    ON ticket (event_seat_id)
 WHERE event_seat_id IS NOT NULL;
```

NULL-ы в уникальный индекс не конфликтуют, поэтому квотных билетов он не касается — там
количество стережёт `sold` в счётчике, а не уникальность. Это **вторая** линия обороны:
первая — partial unique index на `hold_seat_item`, который не пускает два активных удержания
на место. Вторая ловит случай, до которого первая не дотягивается: баг в коде выпуска,
ручной `INSERT`, повторное проведение платежа.

## `payment_status` — состояния платежа

Решения 18–20, приняты 2026-09-17.

| Значение    | Что означает                                          | Кто ставит                                  |
| ----------- | ----------------------------------------------------- | ------------------------------------------- |
| `pending`   | ключ занят, строка создана, к провайдеру ещё не ходили | создание платежа, до внешнего вызова        |
| `succeeded` | провайдер подтвердил списание                          | обработка ответа или webhook                |
| `failed`    | провайдер отказал                                      | обработка ответа или webhook                |

```
pending → succeeded    терминальное (решение 14)
pending → failed       терминальное
```

Из `succeeded` и `failed` переходов нет. Повтор после неудачи — **новая строка с новым
ключом**, а не возврат в `pending`: так сохраняется история попыток, и сверка с выпиской
провайдера остаётся возможной.

**Почему строка создаётся до обращения к провайдеру.** Идемпотентность работает только так.
Ключ занимается вставкой, и два параллельных запроса с одним ключом сталкиваются на уникальном
индексе: второй получает `23505`, читает результат первого и возвращает его же. Если писать
строку после ответа, оба запроса успеют уйти наружу и деньги спишутся дважды — ровно то, от
чего словарь и защищает, определяя Payment через идемпотентность.

Два уникальных ключа, каждый со своей работой:

```sql
CREATE UNIQUE INDEX payment_idempotency_key       ON payment (idempotency_key);
CREATE UNIQUE INDEX payment_one_succeeded_per_order
    ON payment (order_id) WHERE status = 'succeeded';
```

Первый не пускает второй запрос с тем же ключом — это защита от повторной отправки одного и
того же намерения. Второй не пускает вторую успешную оплату одного заказа — это инвариант
`Order` из `CONTEXT.md`, ставший гарантией схемы. Ключ выбран **глобально уникальным**, а не
в пределах заказа: так подстановка чужого ключа ловится тоже.

## Решение 21: валюта — справочник, а не строка в пяти таблицах

Принято 2026-09-17. Код валюты перестаёт быть свободным `varchar(3)` и становится ссылкой на
справочник `currency`; FK стоят в `ticket_type`, `order`, `order_item`, `payment`, `ticket`.

Что это закрывает: **несуществующий код**. `usd` вместо `USD`, опечатка в сиде, пустая строка —
всё это перестаёт попадать в базу, и проверка не зависит от того, прошла ли запись через
приложение.

Чего это **не** закрывает: справочник не мешает заказу и платежу ссылаться на **разные**
существующие валюты. Это добирается решением 22.

**Решение 22: валюта платежа равна валюте заказа.** `UNIQUE (id, currency)` на `order` и
составной FK `(order_id, currency)` из `payment` — четвёртое применение приёма
«дискриминатор плюс составной ключ» в этой схеме. Оплатить рублями заказ, выставленный в
евро, становится непредставимо.

Тот же ключ стоит и у `order_item` (решено 2026-09-17): пара `(order_id, currency)` нужна там
даже сильнее, потому что `total = Σ(item.price × qty)` складывает суммы позиций и молча
предполагает одну валюту. Теперь это предположение держит схема.

**`ticket` оставлен вне правила** (решено 2026-09-17). Прямой ссылки на заказ у него нет — он
смотрит на платёж, — поэтому валюту пришлось бы цеплять вторым составным ключом к
`payment (id, currency)`, при том что один составной FK на ту же таблицу у билета уже есть,
на `(id, status)`. Цена сочтена несоразмерной: `ticket.currency` — копия цены на момент
покупки, и её расхождение с платежом ловится тестом, а не ключом. Строка в таблице
инвариантов ниже отражает это честно.

Практическая деталь для `M1-05`: если ключом справочника сделать сам код ISO 4217 (`char(3)`),
FK читается без единого джойна — колонка `currency` в дочерних таблицах остаётся человеческим
кодом, а не суррогатным id. Суррогатный ключ здесь добавит джойн в каждый запрос, где нужна
валюта, и не даст ничего взамен.

Справочник — это ещё одна сущность на диаграмме; по решению от 2026-09-17 отдельной статьи в
словаре ей не нужно, достаточно упоминания в описании value object `Money`.

## `order_status` — состояния заказа

Решения 23–24, приняты 2026-09-17.

| Значение    | Что означает                                  | Кто ставит                                   |
| ----------- | --------------------------------------------- | -------------------------------------------- |
| `pending`   | заказ создан из подтверждённого холда         | подтверждение холда, та же транзакция        |
| `paid`      | по заказу есть успешный платёж                | обработка успешного `payment`                |
| `cancelled` | покупатель отказался до оплаты                | действие покупателя                          |
| `refunded`  | деньги возвращены                             | `M3`, вместе с механикой возврата            |

```
pending → paid         успешный платёж
pending → cancelled    отказ до оплаты
```

**`fulfilled` не заводим** (решение 23). Состояние «билеты выпущены» выводится из наличия
строк `ticket` — ровно как «билет погашен» выводится из наличия строки `check_in`. Один и тот
же приём: факт живёт в одном месте, отдельного флага, который может разойтись с фактом, нет.
Это правка словаря: статья `Order` в `CONTEXT.md` перечисляла `fulfilled`, теперь не
перечисляет.

**Оплаченный заказ отменить нельзя** (решение 25). `paid` терминален: отмена после оплаты —
это по смыслу возврат денег, а возврат переехал в `M3` вместе с решением 14. Значит в `M1`
терминальных состояний два, `paid` и `cancelled`, и из них переходов нет.

Следствие, которое стоит помнить при тестах `M1-08`: попытка отменить оплаченный заказ должна
отбиваться доменом, а не молча ничего не делать. Схемой переход не запрещён — `order_status`
это enum, а не машина состояний; правило живёт в агрегате `Order`, и в таблице инвариантов оно
так и записано.

## Решение 24: `total` не хранится

Принято 2026-09-17. Колонки `order.total_price` нет; сумма заказа считается запросом по
`order_item`.

Это тот редкий случай, когда инвариант закрывается **удалением** данных, а не добавлением
проверки. `total = Σ(item.price × qty)` — правило над множеством строк, `CHECK` его не
выразил бы (см. [урок 0007](../../lessons/0007-hold-that-does-not-know-what-it-holds.html)), и
пришлось бы выбирать между пересчётом в коде, триггером и «ловим тестом». Нет колонки — нет
расхождения: сумма перестаёт быть фактом, который надо синхронизировать, и становится
производной.

Цена: агрегат при каждом чтении заказа, и `GROUP BY` вместо колонки в списке «мои заказы».
Историчность при этом не страдает — цена позиции зафиксирована в `order_item.price` на момент
покупки, поэтому пересчёт всегда даёт ту же сумму, что и в день продажи.

`order.currency` остаётся: он нужен составному FK из решения 22 и отвечает на вопрос «в какой
валюте выставлен заказ» без чтения позиций.

## Два `capacity`: физический предел и то, что выставлено на продажу

Решение 5, принято 2026-09-17.

| Колонка                     | От чего зависит                                     | Когда меняется                       |
| --------------------------- | --------------------------------------------------- | ------------------------------------ |
| `section.capacity`          | от площадки: сколько человек физически помещается   | при перестройке зала, вне продаж     |
| `ticket_allocation.capacity`| от пары «событие + секция»: сколько открыли к продаже | при подготовке конкретного концерта |

Числа законно различаются: половину фан-зоны можно не открывать, оставить под гостей или под
вторую волну продаж. Незаконно обратное — открыть к продаже больше, чем влезает в зал. Это и
есть инвариант: `ticket_allocation.capacity <= section.capacity`.

**`CHECK` его не выразит.** Правило связывает две строки в двух таблицах, а выражение
`CHECK` видит только колонки текущей строки и не принимает подзапросы (проверено в
[уроке 0007](../../lessons/0007-hold-that-does-not-know-what-it-holds.html): `ERROR: cannot
use subquery in check constraint`). Значит механизм выбирается из трёх, и выбор пока не
сделан:

| Механизм                                                             | Что даёт                                                                 | Чем платим                                                                                                        |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Копия числа плюс составной FK** ← выбрано                          | полная гарантия схемы, и копия не может разъехаться: её ведёт тот же ключ | колонка `section_capacity`, `UNIQUE (id, capacity)` на секции, блокировки на квотах при изменении вместимости зала |
| Триггер `BEFORE INSERT OR UPDATE` на `ticket_allocation`              | гарантия без копии числа, читает `section` напрямую                      | логика в базе мимо Drizzle: не видна в TS-схеме, тестируется отдельно, при конкуренции нужна блокировка `section`  |
| Код агрегата плюс тест в `M1-08`                                      | ничего не усложняет в схеме, правило живёт там же, где остальные проверки | `INSERT` мимо приложения правило не заметит — а миграции и сиды ходят именно так                                   |

**Выбран первый** (2026-09-17). Ключевое отличие от обычной денормализации — `ON UPDATE
CASCADE`: копия не «обязана меняться вместе с оригиналом», она меняется сама.

```sql
section           (id PK, capacity int NOT NULL, UNIQUE (id, capacity))

ticket_allocation (...,
                   section_id       int NOT NULL,
                   section_capacity int NOT NULL,
                   capacity         int NOT NULL,
                   CHECK (capacity <= section_capacity),
                   FOREIGN KEY (section_id, section_capacity)
                       REFERENCES section (id, capacity) ON UPDATE CASCADE)
```

Проверено на живой базе, четыре свойства сразу:

| Сценарий                                        | Что делает база                                                     |
| ----------------------------------------------- | --------------------------------------------------------------------- |
| квота 150 при вместимости 100                   | `violates check constraint` — вставки нет                             |
| подделать копию (`section_capacity = 999`)      | `violates foreign key constraint` — такой пары в `section` нет        |
| расширили зал до 120                            | копии в квотах уехали сами, каскадом                                  |
| сжали зал до 50 при уже открытой квоте 80       | каскадный `UPDATE` падает на `CHECK`, и **вся** операция откатывается |

Последняя строка — самая ценная: уменьшить вместимость секции, под которую уже открыты
квоты, нельзя целиком, а не «частично применится». Для справочных данных, которые меняются
вне продаж, цена в блокировках нулевая.

**Оговорка на будущее.** Выбранный механизм работает, пока ключ квоты — пара
`(event_id, section_id)`, то есть на секцию события приходится одна квота. Если он станет
тройкой с `ticket_type_id` — в одной секции появятся Standard и Early Bird одновременно, —
правило превратится в «**сумма** `capacity` всех квот секции не больше вместимости», то есть
снова в правило над множеством строк, и этот механизм перестанет быть достаточным:
понадобится ещё один материализованный счётчик, теперь на уровне секции.

## Открытые вопросы

Не решены на 2026-09-17, перечислены здесь, чтобы не потеряться между issue.

- **Чем механически держится `capacity <= section.capacity`** — три варианта с ценой в
  разделе «Два `capacity`».
- **Один тип билета на ненумерованную секцию.** Ключ `(event_id, section_id)` допускает ровно
  одну квоту на секцию события, то есть один `TicketType`, тогда как в нумерованной секции их
  сколько угодно (`event_seat.ticket_type_id` у каждого места свой). Early Bird в фан-зоне
  сейчас невыразим. Если ключ станет тройкой — появится правило «сумма `capacity` квот секции
  не больше вместимости секции», снова над множеством строк.
- **Остаётся ли `HoldAllocatedItem` активной после подтверждения.** Для мест ответ есть
  (ловушка 1: остаётся, иначе место на мгновение освободится). Для квоты перенос
  `held → sold` атомарен внутри одной строки, поэтому позицию, возможно, можно закрывать
  сразу — но это решение, а не очевидность.
- **Составной FK `(event_id, ticket_type_id)` на `ticket_type`.** После решения 8 и
  `event_seat`, и `ticket_allocation` несут эту пару, а тип билета знает своё событие сам —
  значит месту можно назначить тип **с чужого концерта**, и схема этого не заметит. Лечится
  `UNIQUE (id, event_id)` на `ticket_type` и внешним ключом по паре из обеих таблиц. Приём
  доступен, решение не принято.

## Решённые вопросы именования

- **Имена таблиц позиций — `hold_seat_item` и `hold_allocated_item`** (решено 2026-09-17,
  решение 6). Сущности на диаграмме — `HoldSeatItem` и `HoldAllocatedItem`; таблицы
  `hold_item` больше нет.
- **«Вариант A» переименован в «узкий статус»** (2026-09-17). Старое имя появилось до урока
  0007, где буквами A–D названы формы развилки «место или квота». Два разных смысла у одной
  буквы в одном документе — готовая путаница на ревью.
- **Значения `hold_item_status` — `active` / `released`** (решено 2026-09-16). Рассматривалась
  пара `occupied` / `released`, которая точнее описывает смысл колонки: при узком статусе
  позиция остаётся `active` и после продажи, то есть говорит «место занято», а не «удержание
  живо».
  Выбраны `active` / `released` — значение совпадает с предикатом индекса и с тем, как это
  состояние называют во всех текстах проекта. Цена — см. ловушку 1 в разделе про
  `hold_item_status`: читатель может решить, что просроченные холды не гасятся. Ловушка
  снимается комментарием к индексу в миграции `M1-05`.
- **Два enum-типа**, `hold_status` и `hold_item_status` (решено 2026-09-16). Наборы значений
  не пересекаются: общий тип не содержал бы `released` и делал бы `confirmed` / `expired` /
  `cancelled` представимыми для позиции, где они ничего не значат. `hold_item_status` при этом
  один на обе таблицы позиций — значения у них совпадают.
- **`Order.status`** изобретать не надо — значения заданы словарём: `pending → paid → fulfilled`,
  либо `cancelled` / `refunded`. Колонка называется `status` во всех таблицах (решено
  2026-09-16, `state` больше не используется).
