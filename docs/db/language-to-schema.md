# Единый язык против схемы: карта понятий

Артефакт пункта 2 issue `M1-02`. У каждого понятия из `Ubiquitous language` в
[CONTEXT.md](../../CONTEXT.md) стоит пометка, **как именно** оно учтено в
[er-model.md](./er-model.md): таблица, поле, результат запроса или часть агрегата, у которой
своей таблицы нет. По этому списку проверяется DoD: «каждая сущность на диаграмме обязана
быть в словаре, каждое понятие словаря — найтись на диаграмме или получить объяснение».

Сверка идёт в обе стороны, поэтому в конце два раздела: понятия без места в схеме и
сущности без статьи в словаре.

## Value objects

Ни один не является таблицей: это набор колонок, который валидирует себя в конструкторе на
стороне домена. На диаграмме их видно только как группы полей.

| Value object     | Как учтён                       | Где именно                                                                              |
| ---------------- | ------------------------------- | ----------------------------------------------------------------------------------------- |
| **Money**        | пара колонок, повторяется       | `ticket_type (price, currency)`, `order (total_price, currency)`, `order_item (price, currency)`, `payment (price, currency)`, `ticket (ticket_price, currency)` |
| **SeatLocation** | три колонки в двух таблицах     | `seat (section_id, row_no, seat_number)`                                                  |
| **Quantity**     | колонка                         | `hold_allocated_item.quantity`, `order_item.quantity`                                     |
| **TimeWindow**   | пара колонок                    | `event (starts_at, ends_at)`; у `hold` роль второй границы играет `expires_at` против `created_at` |
| **TicketCode**   | колонка                         | `ticket.code`, `UNIQUE`                                                                   |
| **Email**        | колонка                         | `user.email`, `UNIQUE`                                                                    |

## Доменные события

`SeatHeld`, `HoldExpired`, `HoldConfirmed`, `OrderPaid`, `OrderCancelled`, `TicketIssued`,
`TicketCheckedIn` — **не таблицы M1**. Они уезжают в outbox в `M5-05` и на диаграмме этого
этапа появиться не должны: правило про колонки из будущих этапов разрешает только то, что
названо словарём как свойство существующей сущности.

## Сущности на диаграмме, у которых нет отдельной статьи

Решено 2026-09-17: **отдельные статьи им не нужны, достаточно упоминания** внутри статьи
родительского понятия и в таблице агрегатов. Имена при этом остаются каноническими — они
взяты из единого языка, а не придуманы в схеме.

| Сущность                                | Где упомянута                                                        |
| --------------------------------------- | ---------------------------------------------------------------------- |
| **HoldSeatItem**, **HoldAllocatedItem**  | таблица агрегатов, строка `Hold`                                      |
| **OrderItem**                            | таблица агрегатов, строка `Order`                                     |
| **TicketAllocation**                     | таблица агрегатов + статья `Inventory` как один из двух механизмов     |
| значения `section_type`                  | статья `Section`: `numbered` против `standing`                        |

`EventSeat` из этого списка выведен — у него своя статья (2026-09-17), потому что это
самостоятельное понятие, за которое идёт гонка, а не деталь чужого агрегата.

## Расхождения, найденные при сверке

0. ~~**Агрегат `Seat` против таблицы `seat`.**~~ Закрыто 2026-09-17: агрегат переименован в
   `EventSeat`, статья добавлена в словарь, статья `Seat` уточнена как справочные данные.
1. ~~**`Inventory` — статья есть, таблицы нет.**~~ Закрыто 2026-09-17: статья переписана как
   зонтичное понятие с явной оговоркой «таблицы с таким именем нет» и отсылкой к обоим
   механизмам.
2. ~~**`Hold` описан через `HoldItem`.**~~ Закрыто 2026-09-17: в таблице агрегатов записаны
   позиции двух видов, `HoldSeatItem` и `HoldAllocatedItem`.
3. **`Ticket` дублирует `EventSeat`.** На диаграмме у билета `seat_id` и `event_id` по
   отдельности, хотя строка с этой парой уже существует и называется `event_seat`. Плюс
   `payment_id` вместо `order_id`: билет привязан к оплате, а словарь определяет его как
   «результат оплаченного `Order`». Это территория пункта 8, здесь только зафиксировано.
4. **Статус гашения.** Словарь говорит, что агрегат `Ticket` содержит «код и статус
   гашения», а в схеме статуса нет — гашение выражено наличием строки `check_in`. Решение
   разумное (одна истина вместо двух), но словарь его не отражает.

## Что этот список закрывает

Пункт 2 плана `M1-02`: у каждого понятия из `CONTEXT.md` стоит пометка, включая
`Reconciliation` (запрос) и `CheckIn` (таблица). Он же даёт вход для пункта 10: колонка «где
именно» — это то место, на которое ссылается ответ «чем держится инвариант».
