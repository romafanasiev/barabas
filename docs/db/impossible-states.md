# Невозможные состояния: что запрещено и чем

Артефакт issue `M1-06`. Список состояний, которые **не должны существовать физически**, по
всей схеме — таблица за таблицей, колонка за колонкой. У каждой строки — механизм защиты и
место в миграции; строки, оставленные коду, названы с причиной.

Список — вход в `M1-08`: каждая строка разделов 1 и 2 — будущий тест, который пытается
записать запрещённое и ждёт ошибку с этим именем ограничения.

Граница с `M1-05` (критерий из `M1-13`): здесь — правила о **допустимом значении одной
колонки**. Правило, которое теряет смысл без второй колонки, второй строки или второй
таблицы, — это связь, и его механизм описан в [aggregate-map.md](./aggregate-map.md).
Исключение одно: `I-36` (`ends_at > starts_at`) связывает две колонки, но переехало сюда
решением в `M1-04`, чтобы все проверки диапазонов лежали в одной миграции.

Ссылки на миграции — `apps/server/drizzle/<файл>:<строка>`.

## 1. Уже закрыто до `M1-06`

## 2. Добавлено в `M1-06`

Все девятнадцать — в `apps/server/drizzle/0005_check_constraints.sql`, по одной строке на
ограничение. Имена — по конвенции `<таблица>_<колонки>_ck`, константы — в
`<таблица>.constraints.ts` рядом со схемой.

| --- | --- | --- | --- |

### Решения, принятые в этом issue

**Деньги — `> 0`, не `>= 0`.** Бесплатных билетов в `M1` нет: приглашение и комп — не
продажа, и в модели продажи им места нет. Цена правила названа сразу: административная
выдача из [решения 13](./states-and-invariants.md#решение-13-один-заказ-на-один-холд)
(служебный холд, живущий секунду) с нулевой ценой сейчас **невозможна**. Когда она
понадобится, это будет отдельное решение — ослабить четыре `CHECK` до `>= 0` или завести
для выдачи свой путь, — а не молчаливая дыра, которую кто-то однажды использует. Замена
испорченного билета не страдает: она выписывается по исходной цене.

**Пустые строки — `length(btrim(x)) > 0`, не `x <> ''`.** Второй вариант дешевле на одну
функцию, но пропускает `'   '`, а это тот же «безымянный» объект, только незаметный в
логах. Стоимость `btrim` на вставке справочной строки несущественна: ни одна из этих
таблиц не пишется в горячем пути продажи, кроме `ticket.code` и `payment.idempotency_key`,
и там это одна строка на транзакцию.

**`currency.code` держит база, а не дисциплина seed'а.** Справочник наполняется миграцией,
но проверка стоит одну строку, а ошибка в коде валюты разъезжается по всем денежным
таблицам через FK — исправлять её пришлось бы каскадом.

**Имя `ticket_allocation_capacity_positive_ck` — отступление от конвенции.** Имя
`ticket_allocation_capacity_ck` занято правилом `capacity <= section_capacity` из `M1-04`;
по конвенции ему полагалось бы `ticket_allocation_capacity_section_capacity_ck`.
Переименование — это правка закрытого issue и контракта ошибок `M2`, поэтому оно не
сделано здесь; если его делать, то до `M2`.

### Чего здесь сознательно нет — это была бы церемония

- **`CHECK (quantity > 0)` на `order_item`** — уже закрыто `order_item_quantity_ck`.
- **`CHECK (capacity < 0)` на `ticket_allocation`** — отрицательную вместимость уже отбивает
  `held_sold_capacity_ck`: при `held >= 0` и `sold >= 0` из `held + sold <= capacity` следует
  `capacity >= 0`. Замер: `capacity = -5` без нового ограничения падает на
  `ticket_allocation_held_sold_capacity_ck`. Новое правило закрывает ровно одну дыру — ноль.
- **`CHECK (section_capacity > 0)` на `ticket_allocation`** — колонка — копия
  `section.capacity`, закреплённая FK; `section_capacity_ck` держит её транзитивно.
- **Проверки валюты в дочерних таблицах** — FK на справочник, а справочник держит
  `currency_code_ck`.
- **Любые `IS NOT NULL` в `CHECK`** — это работа `NOT NULL`, и он её уже делает.

### Ловушка `NULL`

`CHECK` отбивает только `false`, а сравнение с `NULL` даёт `NULL`: `CHECK (price > 0)`
пропустит строку с `price IS NULL`. Все девятнадцать новых правил стоят на `NOT NULL`-колонках,
поэтому ловушка здесь не срабатывает. Nullable в домене только `event_seat_id` /
`allocation_id` в `order_item` и `ticket`, и правила о них (`num_nonnulls(...) = 1`,
`order_item_quantity_ck`) написаны так, что `NULL` учитывается явно. Если какая-то из
колонок раздела 2 когда-нибудь станет nullable, её правило придётся перечитать.

## 3. Оставлено коду

Каждое правило здесь — не «так проще», а одно из трёх: связывает строки (или таблицы),
сравнивает с текущим временем, или описывает переход, а не значение.

| Правило | Почему не схемой | Где держится |
| --- | --- | --- |
| `I-15` Hold непустой | «хотя бы одна дочерняя строка» по двум таблицам — deferrable trigger; решение 6 его отвергло | агрегат `Hold` |
| `I-18` истёкший холд нельзя подтвердить | сравнение с `now()` немутабельно, `CHECK` его не примет | агрегат `Hold` |
| Событие начинается в будущем | то же: `now()` | сервис создания события (`M2`) |
| `I-19` статус холда против статусов позиций | связывает строки двух таблиц | агрегат `Hold` |
| `I-20`, `I-27` переходы статусов | enum задаёт значения, а не стрелки | агрегаты `Hold`, `Order` |
| `I-26` успешный платёж неизменяем | правило о **переходе** | агрегат `Payment` |
| Оплаченный заказ без успешного платежа | связывает две таблицы; статус заказа и платёж пишутся в одной транзакции | application service оплаты |
| `I-31` валюта билета = валюта платежа | сознательная граница (решение 22) | тест выпуска билета, `M5-07` (перенесено из `M1-08`: кода выпуска в `M1` нет) |
| `I-32` нельзя оплатить отменённый заказ | `Payment` не видит статуса заказа, `Order` не участвует в записи | application service оплаты, тест `M5-04` (перенесено из `M1-08`) |
| Цена позиции = цена типа билета в момент подтверждения | связывает две таблицы; копия нарочно не обновляется (решение 8) | агрегат `Order` |
| Сумма платежа = сумма позиций заказа | связывает строки двух таблиц | application service оплаты |
| `quantity` позиции холда не больше остатка квоты | связывает строки; держит счётчик `held` и `held_sold_capacity_ck` | `UPDATE ticket_allocation` в той же транзакции |
| `updated_at >= created_at` | `updated_at` ставит drizzle (`$onUpdate`), а не база; правило о двух колонках, нарушить его может только ручной `UPDATE` | ORM |

### Вне списка

Таблицы better-auth (`user`, `session`, `account`, `verification`) генерируются командой
`auth:schema` и перезаписываются целиком — ограничения, добавленные туда руками, исчезнут
при следующей генерации. Их правила — забота библиотеки.

## Что будет с этим issue в `M7`

Сегодня `ALTER TABLE ... ADD CONSTRAINT ... CHECK` бесплатен, потому что все таблицы пусты.
На живой таблице тот же оператор берёт `ACCESS EXCLUSIVE` — блокирует и запись, и чтение —
и держит её, пока читает таблицу целиком, чтобы проверить каждую строку; на десяти
миллионах билетов это остановка продаж. В `M7` он превращается в два шага:
`ADD CONSTRAINT ... NOT VALID` (блокировка на миг, проверяются только новые строки) и
отдельный `VALIDATE CONSTRAINT`, который берёт `SHARE UPDATE EXCLUSIVE` и не мешает ни
чтению, ни записи — приём из [урока 0008](../../lessons/0008-hall-that-shrank-under-the-sold.html).
И до `VALIDATE` нужен ещё один шаг, которого сегодня нет вовсе: найти и починить старые
строки, которые правило нарушают, — иначе `VALIDATE` упадёт.
