# Логи: уровни и гигиена

Правило для `apps/server`. Конфигурация живёт в
`src/core/telemetry/logger/` — `logger.redaction.ts` (что вырезается) и
`logger.serializers.ts` (что вообще попадает в строку запроса). Почему выбраны именно эти
механизмы — в [ADR-0003](./adr/0003-log-redaction-allowlist.md).

## Уровни

Ось одна: **кто должен отреагировать и когда**. Не «насколько тревожно» — это вкус, о нём
спорят. «Нужен ли человек и через сколько» — проверяемо третьим лицом.

| Уровень | Кто реагирует | Признак |
|---|---|---|
| `debug` | никто | Нужно только тому, кто прямо сейчас чинит этот участок кода. В проде выключен — гарантируется схемой env, не дисциплиной |
| `info` | никто | Реагировать не надо, но строка обязана остаться в истории запроса: по ней потом восстанавливают, что произошло |
| `warn` | дежурный утром | Система справилась сама — retry, fallback, деградация, — но повторяемость означает поломку |
| `error` | дежурный сейчас | Работа, которую кто-то ждал, не сделана, и автоматика её не доделает |
| `fatal` | дежурный сейчас | Процесс не может продолжать работу и выходит |

Два вопроса решают выбор:

1. **Справилась ли система сама?** Нет → `error`. Да → дальше.
2. **Нужна ли эта строка, чтобы восстановить историю запроса?** Да → `info`. Нет → `debug`.
   Если справилась, но повторение означает поломку → `warn`.

### Три вызова из этого кода, прогнанные через правило

**`greeting requested`** (`app.service.ts`) → **`info`**. Система справилась. Строка нужна в
истории запроса: это единственное доказательство, что слой сервиса отработал внутри этого
`requestId` — строка `request completed` говорит только про HTTP. Один вопрос → один уровень,
спорить не о чем.

**`postgres connection error`** (`postgres.module.ts`) → **`warn`**, и это защищается. Это
обработчик `pool.on('error')`: он срабатывает на **простаивающий** client, которого закрыла
другая сторона. Пул выбрасывает его и выдаёт следующему запросу новый — система справилась
сама, ждущего нет. Реагировать надо не на строку, а на **частоту**: алерт вешается на rate,
а не на факт. Запрос, который действительно упал из-за базы, даст свой `error` там, где
делался query, — и вот он уже про «работа не сделана».

**`dependency failed to close`** (`shutdown.service.ts`) → было `error`, стало **`warn`**.
Процесс всё равно выходит: повторить некому, ждущих нет, сокеты закроет ОС. Реагировать
сейчас не на что. Но недоступный при закрытии postgres — повод посмотреть утром, потому что
следующий под поднимется в ту же сеть. Строку рядом — `shutdown deadline exceeded` — правило
оставляет `fatal`: процесс уходит через `exit(1)`.

### Обязательное содержимое строки

- **`error` и `fatal`** — всегда с `err` (pino разворачивает его в `message` + `stack`) и с
  `requestId`. `requestId` приезжает сам, если писать через `ContextLogger`: он берёт
  request-scoped логгер из ALS. Писать через корневой `LOGGER` внутри запроса — потерять связь.
- **Вне запроса** (старт, shutdown, фоновые задачи) `requestId` не существует. Его место
  занимает признак операции: `signal`, `dependency`, имя джобы.

## Что не попадает в лог никогда

Два разных механизма, и путать их не надо:

- **Строка запроса** (`req`, `res`) — собирается allowlist-сериализаторами. Заголовок или
  значение query-параметра, которого нет в списке разрешённых, в лог не попадает вообще.
- **Объекты, которые код логирует сам** (`logger.info({ user })`) — чистятся `redact` по
  именам полей: пароли, токены, ключи, платёжные данные вырезаются в `[Redacted]`, email
  маскируется до `v***@example.com`.

### Чего этот конфиг не умеет — и что с этим делать руками

**`redact` не читает текст.** Он ходит по путям в объекте. Всё это проезжает насквозь:

```ts
logger.info(`password=${password}`);        // секрет в msg
throw new Error(`bad token ${token}`);      // секрет в err.message и в err.stack
```

Отсюда дисциплина, которую конфигом не заменить:

1. **Секрет — всегда поле, никогда не часть сообщения.** `msg` — константа, переменное
   уходит в объект. Заодно по такому `msg` можно грепать и агрегировать.
2. **Текст ошибки не склеивать из данных.** Идентификатор — в поле (`{ orderId }`), не в
   строке исключения.
3. **Не логировать сырые объекты, пришедшие снаружи.** `logger.info({ body })` — это ставка
   на то, что список `redact` длиннее, чем фантазия клиента. Логировать перечисленные поля.

**Список `redact` конечен по глубине.** `*.password` закрывает ровно один уровень, `**` не
работает и об этом не сообщает. Сгенерировано четыре уровня — этого хватает на реальные DTO,
но пятый уровень утечёт молча. Единственная защита, не зависящая от длины списка, — правило 3
выше.

**Список устаревает.** Через полгода в коде появится `cardholderToken` или `x-internal-key`,
и в список их никто не добавит — про них просто забудут. Поэтому allowlist стоит там, где
данные приходят снаружи (заголовки, query): забытый пункт там даёт потерянное отладочное
поле, а не утёкший секрет. `redact` остаётся вторым рубежом для того, что пишет наш
собственный код, где имена полей мы контролируем.
