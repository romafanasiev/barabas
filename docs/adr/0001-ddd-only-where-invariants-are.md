# ADR-0001 — DDD применяется только там, где есть инварианты

Status: accepted
Date: 2026-09-10

## Контекст

Проект — система продажи билетов на концерты. Часть предметной области содержит жёсткие
правила, нарушение которых делает данные бессмысленными: место не может быть продано дважды,
заказ не может быть оплачен дважды, билет гасится один раз. Другая часть — обычные справочные
данные: площадки, секции, профили пользователей.

Тактический DDD (агрегаты, value objects, репозитории на агрегат, доменные события) даёт
защиту инвариантов ценой заметного объёма кода: отдельный доменный слой, мэпперы между
доменной моделью и моделью хранения, запрет на обращение к ORM из домена.

Применять его ко всему проекту — значит писать три слоя ради CRUD над таблицей `venues`.
Не применять нигде — значит размазать правило «не продавать место дважды» по сервисам и
контроллерам, где оно рано или поздно будет нарушено.

## Решение

**DDD применяется точечно — там, где есть инвариант, который нужно защитить при записи.**

Агрегаты: `Seat`, `TicketAllocation`, `Hold`, `Order`, `Ticket`. Их инварианты перечислены
в [CONTEXT.md](../../CONTEXT.md).

Обычный CRUD без доменного слоя: каталог площадок и секций, профили пользователей,
административные справочники.

Чтение (списки концертов, страница доступности, отчёты) идёт **мимо доменной модели** —
прямыми запросами в read-модель. Агрегат загружается только тогда, когда что-то меняется.

Структура кода:

```
src/modules/
  ticketing/            ← DDD
    domain/             ← агрегаты, value objects, доменные события, порты (интерфейсы)
    application/        ← use cases, оркестрация транзакций
    infrastructure/     ← репозитории, ORM-сущности, мэпперы
    api/                ← контроллеры, DTO
  catalogue/            ← обычный CRUD, доменного слоя нет
  identity/             ← обычный CRUD
```

Жёсткое правило: **`domain/` не импортирует ничего из NestJS, TypeORM и любой инфраструктуры.**
Проверяется линтером, а не договорённостью (issue `M1-15`).

## Последствия

**Хорошее**

- Инвариант живёт в одном месте и не может быть обойдён мимо агрегата.
- Доменный слой тестируется без базы и без Docker — быстрые unit-тесты (`M7-01`).
- Граница агрегата явно показывает границу транзакции и границу блокировки — прямая связь
  с этапом M4.

**Плохое, принимаем сознательно**

- Мэпперы между доменной моделью и таблицами — это код, который надо писать и поддерживать.
- Два разных стиля в одном проекте (DDD и CRUD). Нужна дисциплина, чтобы граница не поплыла.
- Подтверждение Hold захватывает несколько агрегатов `Seat` в одной транзакции, что нарушает
  правило «одна транзакция — один агрегат». Обоснование и цена — в `M1-14`.

**Признаки, что решение оказалось неверным** (пересматриваем ADR)

- В `catalogue/` появились правила сложнее «поле обязательно» → пора и туда завести домен.
- В `ticketing/domain/` появились классы без поведения, одни геттеры и сеттеры → это anemic
  domain model, DDD выродился в лишние файлы.

## Альтернативы

- **DDD везде.** Отклонено: цена не оправдана для справочников.
- **Никакого DDD, транзакционные скрипты в сервисах.** Отклонено: правило про овербукинг
  расползётся по коду, и M4 негде будет закрепить.
- **Event sourcing.** Отклонено: см. «Out of scope» в [MISSION.md](../../MISSION.md). Outbox
  берём, event sourcing — нет.
