# ADR-0003 — Данные запроса в логах: allowlist в сериализаторе, redact — вторым рубежом

Status: accepted
Date: 2026-09-15

## Контекст

После `M0-04` логи структурированные и с `requestId`, но текут. Замер на живом коде,
`GET /?token=SECRET_IN_QUERY&email=victim@example.com` с заголовками `authorization`,
`cookie`, `x-api-key`:

```json
"req": {
  "url": "/?token=SECRET_IN_QUERY&email=victim@example.com",
  "query": { "token": "SECRET_IN_QUERY", "email": "victim@example.com" },
  "headers": { "authorization": "[Redacted]", "cookie": "[Redacted]", "x-api-key": "SECRET_CUSTOM_HEADER" }
}
```

Вырезано только то, что было перечислено поимённо. Дефолтный сериализатор `pino-http` кладёт
в строку **все** заголовки, полный `url` и разобранный `query`, то есть любой секрет, который
клиент решил прислать, оказывается в логе по умолчанию.

Замеры на pino 10, определившие решения:

- `*.password` закрывает ровно один уровень. `{ user: { profile: { password } } }` — утечка.
- `**.password` не работает и **не сообщает об ошибке**: выглядит как рекурсивный вариант,
  ведёт себя как отсутствие правила.
- Индекс массива — обычный сегмент пути: `*.*.password` закрывает и `users[0].password`.
- `censor` получает путь, ведущие сегменты которого — символы, если сработал wildcard.
  Последний сегмент — всегда имя поля, которое совпало.

## Решение

**1. Заголовки — allowlist, а не denylist.** Сериализатор `req` оставляет только
перечисленные заголовки (`host`, `user-agent`, `content-type`, `x-request-id`,
`x-forwarded-for`, …), остальные не попадают в строку. То же для `res`.

*Цена:* новый полезный заголовок не появится в логах, пока его не добавят в список; отладка
на секунду упирается в «а где оно?». Denylist был бы дешевле и тёк бы на каждом новом
заголовке — сегодня это `x-api-key`, завтра `x-internal-token`. Мы выбрали ошибку в сторону
потерянного отладочного поля вместо ошибки в сторону утёкшего секрета.

**2. `url` режется до pathname, значения query не логируются — только имена ключей.**
Строка получает `path: "/orders"` и `queryKeys: ["token", "email"]`.

*Цена:* по логу не видно, с какими параметрами звали ручку — видно только, какие параметры
были. Альтернатива «вырезать `req.url` целиком» отнимает самое полезное поле строки: пропадает
роут. Альтернатива «перечислить `req.query.*` по именам» — это denylist из решения 1, с той же
протечкой. Имена ключей не секретны и отвечают на «каким фильтром пользовались»; значение,
которое действительно нужно в логе, хендлер логирует сам и поимённо.

**3. `redact` — по конечному списку имён, сгенерированному на четыре уровня вложенности.**
Списки имён (`password`, `token`, `apiKey`, `card`, `cvv`, `iban`, …) разворачиваются в пути
`key`, `*.key`, `*.*.key`, `*.*.*.key`. Массивы закрываются тем же самым, индекс — сегмент пути.

*Цена:* пятый уровень вложенности утечёт, и молча. Держать глубину бесконечной нельзя —
`**` в pino не работает. Поэтому `redact` объявлен **вторым рубежом**, а не защитой: первый
рубеж — правило «не логировать сырые объекты, пришедшие снаружи» (docs/logging.md). Ставить
защиту на список, который зависит от фантазии клиента, нельзя; на список, который зависит от
имён полей в нашем коде, — можно.

**4. Email маскируется до `v***@example.com`, а не вырезается целиком.** Через `censor`,
который различает email по последнему сегменту пути.

*Цена:* маска не уникальна — `v***@example.com` это и `victim@`, и `vasya@`, так что запрос
«найди все логи этого клиента» по ней не решается. Он и не должен: для этого есть `userId`,
который не является персональными данными и логируется как есть. Маска отвечает на другой,
частый при разборе инцидента вопрос — «в этих двух строках один и тот же человек или разные».
Вырезанный целиком email не отвечает и на него.

## Следствия

- Тело запроса `pino-http` не логирует вообще и логировать не начнём: ловушка с глубиной
  срабатывает именно на собственных вызовах `logger.info({ body })`.
- `redact` не смотрит в текст: секрет в `msg` или в `err.message` проходит насквозь. Это
  закрывается дисциплиной, а не конфигом, — см. docs/logging.md.
- Заголовки защищены сериализатором, а не `redact`; пути вида `req.headers.authorization`
  в списке избыточны и не держат ничего. Имя `authorization` в списке `redact` осталось —
  оно работает на поле `authorization` в произвольном объекте, а не на заголовке.
- `LOG_LEVEL=debug` при `NODE_ENV=production` роняет старт (`env.schema.ts`): цена debug-логов
  в проде — это и деньги, и внутренности запросов, переживающие ротацию.
