# ADR-0004 — Слой данных: drizzle-orm поверх существующего пула `pg`, схема в TypeScript как источник правды

Status: accepted
Date: 2026-09-15

## Контекст

До этого решения проект ходит в PostgreSQL напрямую: `core/infrastructure/postgres/postgres.module.ts`
держит пул `pg@8`, его читает health-индикатор (`M0-05`) и закрывает graceful shutdown (`M0-06`).
Работает, но у результата запроса нет типов, мэппинг руками, миграций нет вообще.

Выбор слоя данных здесь — не вопрос синтаксиса. Цель проекта — писать блокировки руками,
читать `EXPLAIN ANALYZE` собственного SQL и понимать, какая транзакция где стоит. Слой,
который это прячет, отнимает смысл `M4` и `M8`.

### Требования и откуда они взялись

| Требование | Источник | Зачем |
| --- | --- | --- |
| `SELECT … FOR UPDATE`, `SKIP LOCKED` | `M4-01`, `M4-07` | пессимистичная блокировка места |
| Уровень изоляции на конкретную транзакцию | `M4-07` | Read Committed по умолчанию не спасает |
| `lock_timeout` / `NOWAIT` на отдельном запросе | `M4-07` | перестать ждать осознанно |
| Код ошибки PostgreSQL доступен коду | `M4-08` | без `40001` / `40P01` ретрай не написать |
| `INSERT … ON CONFLICT` по partial unique | `M1-10`, `M4-07` | «одно место — один активный Hold» |
| Сырой SQL с предсказуемым результатом | `M8-02`, `M8-03` | `EXPLAIN ANALYZE` читается по своему SQL |
| Программный запуск миграций | `M7-02` | Testcontainers поднимает схему из кода теста |
| `CHECK` и partial unique index в миграции | `M1-06`, `M1-10` | constraints — последняя линия обороны |
| Доступ к пулу и его настройкам | `M8-06` | размер пула объясняется цифрами |
| Отсутствие в `domain/` | `M1-15` | чистая доменная модель |

Два ограничения репозитория, отсекающие часть кандидатов: `apps/server` — ESM
(`"type": "module"`, `module: nodenext`, импорты с суффиксом `.js`), и в нём включён
`emitDecoratorMetadata` ради DI NestJS, из-за чего там уже нельзя включить
`consistent-type-imports` ([ADR-0002](./0002-oxlint-and-import-boundary.md)).

### Замеры

Спайк прогнан на `postgres:18` из `docker-compose.yml`, `drizzle-orm@0.45.2`,
`drizzle-kit@0.31.10`, драйвер — `node-postgres` поверх того же `Pool`. Логировался
текст SQL, который слой реально отправил в базу.

**1. Что генерируется из TS-схемы.** Таблица с двумя `check()` и `uniqueIndex().where()`
превращается ровно в то, что нужно `M1-06` и `M1-10`:

```sql
CREATE TABLE "spike_holds" (
	"id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
	"price_amount" numeric(12, 2) NOT NULL,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL,
	"expires_at" timestamp with time zone NOT NULL,
	CONSTRAINT "spike_holds_price_positive" CHECK ("spike_holds"."price_amount" > 0),
	CONSTRAINT "spike_holds_ttl_forward" CHECK ("spike_holds"."expires_at" > "spike_holds"."created_at")
);
CREATE UNIQUE INDEX "spike_holds_one_active_per_seat" ON "spike_holds" USING btree ("seat_id") WHERE "spike_holds"."status" = 'active';
```

`timestamp with time zone` и `numeric(12,2)` — без специальных усилий; `numeric` приходит
обратно **строкой** (`"100.00"`), что совпадает с требованием `M1-16` к `Money`.

**2. Блокировки.** `.for('update')`, `.for('update', { skipLocked: true })`,
`.for('update', { noWait: true })` дают дословно `… for update`, `… for update skip locked`,
`… for update nowait`. Проверено на двух соединениях: при удержанной строке `SKIP LOCKED`
вернул 0 строк, `NOWAIT` упал с `55P03`, `set local lock_timeout = '150ms'` внутри
транзакции — тоже `55P03`.

**3. Изоляция.** `db.transaction(cb, { isolationLevel: 'serializable', accessMode: 'read write' })`
отправляет `begin isolation level serializable read write`; `show transaction_isolation`
внутри подтверждает `serializable`.

**4. Ошибки.** Нарушение `CHECK` прилетает как `DrizzleQueryError`, и **`error.code` у него
`undefined`** — код PostgreSQL лежит на уровень глубже:

```
поймано: DrizzleQueryError
e.code       = undefined
e.cause.code = 23514 | constraint = spike_holds_price_positive
```

**5. `ON CONFLICT` по partial unique — асимметрия API.** Предикат индекса задаётся ключом
`where` в `onConflictDoNothing` и ключом `targetWhere` в `onConflictDoUpdate`. Перепутанный
ключ роняет предикат из SQL и даёт ошибку планировщика:

```
doNothing + where        → on conflict ("seat_id") where "status" = 'active' do nothing   ✅
doNothing + targetWhere  → on conflict ("seat_id") do nothing                             ❌ 42P10
doUpdate  + targetWhere  → on conflict ("seat_id") where "status" = 'active' do update …  ✅
```

`tsc` эту ошибку ловит (`TS2353: 'targetWhere' does not exist in type …`), а прогон через
vitest — нет: esbuild снимает типы, не проверяя их. То есть от неё защищает `pnpm typecheck`
в гейтах, а не тест.

**6. Программные миграции.** `migrate(db, { migrationsFolder })` накатывает в одной
транзакции (`begin` → DDL → `insert … __drizzle_migrations` → `commit`), журнал —
таблица `drizzle.__drizzle_migrations` в отдельной схеме. Это и есть вызов для `M7-02`.

**7. Потолок.** У `drizzle-kit` нет команды отката: `generate`, `migrate`, `introspect`,
`push`, `up`, `check`, `drop`, `export` — и `drop` удаляет файл миграции из журнала, а не
откатывает её в базе. В `pg-core` нет конструктора `EXCLUDE`-constraint (`exclude` в
экспортах отсутствует; `excluded` — это псевдотаблица для upsert). Escape hatch —
`db.execute<T>(sql\`…\`)`, где `T` — **утверждение разработчика**, а не вывод: `select count(*)`
вернул `{"n":"1"}`, и никто бы не заметил, объяви я `n: number`.

## Решение

**1. Слой запросов — `drizzle-orm` поверх уже существующего `Pool`.** Модуль
`PostgresModule` остаётся владельцем пула (`M8-06`, shutdown из `M0-06`), drizzle получает
этот же пул, а не заводит свой.

*Цена:* на один слой абстракции больше между кодом и `pg`. Каждая ошибка драйвера теперь
приезжает завёрнутой (см. решение 4).

**2. Миграции — `drizzle-kit generate` из TS-схемы, накат — программный `migrate()`.**
Команда генерирует SQL-файл, файл коммитится и ревьюится как код; тесты `M7` накатывают
схему вызовом `migrate()`, а не командой в терминале.

*Цена:* отката нет. Down-миграцию, когда она понадобится, пишем руками SQL-файлом и
запускаем сами — инструмент в этом не помогает.

**3. Источник правды — TS-схема; то, что DSL не выражает, дописывается SQL-ом в
сгенерированную миграцию.** `CHECK` и partial unique index выражаются схемой (замер 1) и
остаются в источнике правды. `EXCLUDE` (если он понадобится в `M1-06`) схемой не
выражается — он идёт руками в файл миграции.

*Цена:* про такой руками дописанный объект `drizzle-kit` не знает — он диффит снапшот схемы,
а не живую базу. Источник правды перестаёт быть единственным ровно на этих объектах, и
удержать их в голове — задача ревью, а не инструмента. Поэтому правило: **каждый объект,
дописанный руками, сопровождается тестом из `M1-08`**, иначе его исчезновение никто не заметит.

**4. Ошибки PostgreSQL распаковываются из `cause`.** Кодом ошибки считается
`error.cause.code`, а не `error.code`. Один хелпер на весь проект, к `M4-08` он же станет
местом, где живёт список ретраибельных кодов (`40001`, `40P01`).

*Цена:* зависимость от внутренней формы ошибки drizzle. Тест, который проверяет, что по
нарушенному constraint мы получаем `23514`, обязателен — иначе смена версии сломает ретраи молча.

**5. Границу `M1-15` drizzle не пересекает.** Таблицы drizzle — обычные объекты, а не
декорированные классы, поэтому доменная сущность ими не является и быть не может:
`schema.ts` живёт в `infrastructure/`, `domain/` про drizzle не знает, преобразование —
мэппер из `M1-18`. Правило линтера из `M1-15` запрещает импорт `drizzle-orm` внутрь
`domain/` наравне с NestJS.

*Цена:* две модели и мэппер между ними — руками, на каждый агрегат.

## Отвергнутые альтернативы

**Raw `pg` (baseline, уже в репозитории).** Стоимость внедрения нулевая, потолка нет, весь
SQL свой. Отвергнут не за это, а за отсутствие типов у `rows` и за то, что мигратор всё
равно пришлось бы выбирать отдельно: девять требований из таблицы он закрывает, десятое
(«типы таблиц») — не закрывает ничем, кроме дисциплины. Замеры 2, 3 и 6 показывают, что
drizzle отдаёт тот же SQL, ничего не пряча, — то есть за типы не платим ни одной из тех
возможностей, ради которых baseline выбирали бы.

**Kysely.** По требованиям почти неотличим от выбранного: тот же уровень (query builder, не
ORM), та же прозрачность SQL, `kysely-ctl` для миграций и кодогенерации типов из базы.
Отвергнут по одному различию: у Kysely источник правды — база, типы вытягиваются из неё
командой, то есть нужен шаг в процессе, который кто-то обязан не забыть; у drizzle схема в
TS порождает и SQL, и типы из одного файла. Спайком Kysely не проверялся — решение принято
по этому критерию, и если он окажется неверным, пересматривать надо именно его.

**TypeORM.** Доменная сущность — декорированный класс, то есть либо он же становится
доменной моделью (и `M1-15` нечем закрыть), либо всё равно нужны две модели и мэппер — но
тогда весь вес ORM оплачен ни за что. Плюс глобы для поиска сущностей и миграций — самое
частое место поломки в ESM, а `emitDecoratorMetadata` уже стоил проекту одного отключённого
правила линтера.

**Prisma.** Прячет ровно то, что этот проект должен выучить: блокировки и почти весь
интересный SQL уходят в `$queryRaw`, где типизация — то же самое утверждение разработчика,
что и в замере 7, только теперь так выглядит основная работа `M4`, а не крайний случай.
Рекомендация из `NOTES.md` — не Prisma на первом проекте — принята.

## Следствия

- **Отката миграций нет.** На `M1-03`…`M1-05` это незаметно (база пересоздаётся), на первом
  же изменении схемы на живых данных — заметно. Решение о down-миграциях откладывается до
  `M7`, и это осознанный долг, а не недосмотр.
- **`pnpm typecheck` становится гейтом целостности, а не удобства.** Замер 5 — пример
  ошибки, которую тест пропускает, а компилятор ловит. Убрать typecheck из гейтов теперь
  значит потерять единственную защиту от таких ошибок.
- **Типы сырого SQL держатся на честном слове.** Каждый `db.execute<T>` — место, где типы и
  реальность могут разойтись молча. Дисциплина: `numeric` и `count(*)` — это `string`.
- **Версия drizzle становится частью контракта с базой.** Форма ошибки (`cause.code`) и
  асимметрия `where`/`targetWhere` — детали реализации, а не документированный API. Обновление
  минорной версии — повод прогнать тесты `M1-08`, а не формальность.
- **Чем выбор хуже отвергнутого `pg`:** появилась зависимость, чьё поведение надо знать
  дополнительно к поведению PostgreSQL — ошибку теперь нужно распаковывать, а предикат
  `ON CONFLICT` можно потерять из-за ключа в объекте. На чистом `pg` обе эти ошибки
  невозможны, потому что SQL пишется целиком руками.
