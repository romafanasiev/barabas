Урок 0006 · этап M0 · эксплуатация

Проверка, которая не отвечает

Health check выглядит как задача на полчаса: два роута, два SELECT 1, готово. Сегодня ты сломаешь её тремя способами в терминале и увидишь, что настоящая работа в M0-05 — не в проверках, а в таймауте, который умеет отменять, и в одном вопросе, который решает, какая проверка в какой эндпоинт попадает.

≈ 30 минут Только Node и curl, без Docker и без базы Ведёт к M0-05, M0-06, M8-09

Сначала вспомни

Без подглядывания в прошлые уроки.

Recall · 1 из 2

Зачем контекстному логгеру фолбэк на корневой, если getStore() пуст?

Контекст живёт только внутри run(). Всё, что начинается не с HTTP-запроса — bootstrap, cron, обработчик сигнала, — выполняется без store, и getStore() там честно вернёт undefined. Сегодняшний health check — как раз такой код: первые строки он пишет до того, как придёт хоть один запрос.

Recall · 2 из 2

По какому признаку видно, что строку таблицы пора разбивать на несколько?

Повтор значения — следствие, а не причина: он возникает именно потому, что факт «существует площадка» приклеен к факту «состоялась продажа». Разное время рождения и смерти — вот признак, который работает без формул. Сегодня ты применишь ровно тот же приём к эндпоинтам: разные последствия — разные эндпоинты.

Задача на один абзац

M0-05 просит два роута. GET /health — liveness, процесс жив. GET /health/ready — readiness, могу обслуживать трафик, и для этого хожу в PostgreSQL и Redis. Разница выглядит как разница в глубине проверки: один поверхностный, другой основательный. Это неверное понимание, и оно стоит дороже всего, что ты сегодня напишешь.

Начнём с конца — с того, что случается, когда зависимость умирает невежливо. Не «соединение разорвано», а «сервер принял соединение и замолчал»: так выглядит перегруженный Postgres, так выглядит виртуалка, у которой отобрали CPU, так выглядит сетевой сплит. Соединение живое, ответа нет.

Опыт 1: зависимость, которая молчит

Создай папку вне репозитория и положи туда два файла. Никаких зависимостей, только Node.

blackhole.mjs — «зависимость», которая принимает соединения и не отвечает

import net from 'node:net';

let open = 0;

net
  .createServer((socket) => {
    open += 1;
    console.log(`принял соединение, отвечать не буду. Открыто: ${open}`);
    socket.resume();                 // см. сноску ниже — без этого опыт 3 не сработает
    socket.on('error', () => {});
    socket.on('close', () => {
      open -= 1;
      console.log(`соединение закрыто. Открыто: ${open}`);
    });
  })
  .listen(7777, () => console.log('blackhole слушает 7777'));
Что делает socket.resume()

Сокет без подписки на data находится в paused-режиме: входящие байты лежат в буфере непрочитанными, и закрытие с той стороны такой сокет замечает не сразу. Нам это помешало бы в третьем опыте — счётчик не уменьшался бы, хотя соединение уже разорвано. resume() заставляет поток читать и выбрасывать данные, и события приходят вовремя. Заодно пустой обработчик error: закрытие через destroy() прилетает сюда как ECONNRESET, а необработанное событие error на сокете роняет процесс.

app.mjs — приложение с двумя эндпоинтами

import http from 'node:http';
import net from 'node:net';

// наивная проверка: подключиться и дождаться ответа
function ping() {
  return new Promise((resolve, reject) => {
    const socket = net.connect(7777, '127.0.0.1', () => socket.write('PING\r\n'));
    socket.once('data', () => {
      socket.end();
      resolve('pong');
    });
    socket.once('error', reject);
  });
}

const json = (res, code, body) => {
  res.writeHead(code, { 'content-type': 'application/json' });
  res.end(JSON.stringify(body));
};

http
  .createServer(async (req, res) => {
    if (req.url === '/health') {
      return json(res, 200, { status: 'ok' });
    }
    if (req.url === '/health/ready') {
      try {
        await ping();
        return json(res, 200, { status: 'ok', dep: 'up' });
      } catch (err) {
        return json(res, 503, { status: 'error', dep: 'down', reason: err.message });
      }
    }
    json(res, 404, { status: 'not found' });
  })
  .listen(3000, () => console.log('app слушает 3000'));

А в первом терминале — одна строка: принял соединение, отвечать не буду. Открыто: 1. И она там осталась: curl сдался, а соединение живо.

Смотри внимательно

Твой эндпоинт не ответил «плохо». Он не ответил. Решение, сколько ждать, принял curl — своей опцией -m 5, про которую ты ничего не знаешь. Убери её, и он будет ждать столько, сколько разрешит операционная система: минуты.

В проде вместо curl — проба оркестратора, и у неё свои умолчания. В Kubernetes у пробы есть timeoutSeconds (по умолчанию 1), periodSeconds (10) и failureThreshold (3). То есть под уедет из балансировки примерно через тридцать секунд после смерти зависимости — и ровно столько же времени на него будет литься трафик. Твоя проверка, которая «честно проверяет», в этой картине не участвует: она не успела ничего сказать ни разу.

И обрати внимание на вторую половину: за эти тридцать секунд проба сходила три раза, и три соединения к мёртвой зависимости остались открытыми внутри твоего процесса. Это уже не про честность ответа, это про утечку.

Проверка · 1 из 3

Что главного не так с проверкой, у которой нет таймаута?

Проверка без таймаута не отдаёт ни 200, ни 503 — она не отдаёт ничего, и весь смысл эндпоинта теряется: «не ответил за N секунд» — это ответ клиента самому себе, а не твоя диагностика. Удержание соединения — тоже правда, но это следствие, и с ним мы разберёмся в следующем опыте.

Опыт 2: таймаут, который перестаёт ждать, но ничего не отменяет

Очевидное лекарство — Promise.race. Добавь в app.mjs и замени вызов ping() на raceTimeout(ping(), 300):

const timeout = (ms) =>
  new Promise((_, reject) => setTimeout(() => reject(new Error(`timeout ${ms}ms`)), ms));

const raceTimeout = (promise, ms) => Promise.race([promise, timeout(ms)]);

Перезапусти app.mjs и запусти опрос — как это делал бы оркестратор, только чаще, чтобы не ждать:

$ while true; do curl -s -o /dev/null -w "%{http_code} " localhost:3000/health/ready; sleep 0.5; done
503 503 503 503 503 503 503 503 503 503 503 503

Выглядит как победа: быстрый честный отказ, код правильный, тело с причиной. Теперь посмотри в терминал с blackhole.mjs.

принял соединение, отвечать не буду. Открыто: 2
принял соединение, отвечать не буду. Открыто: 3
...
принял соединение, отвечать не буду. Открыто: 24
Вот оно

Ни одной строки соединение закрыто. Эндпоинт отвечает за 300 мс, а счётчик растёт линейно и не падает никогда. Promise.race вернул управление — и только. Проигравший промис не отменён, сокет открыт, ping() всё ещё ждёт своё data.

Промис в JavaScript — это не задача, которую можно остановить. Это уведомление о результате. Promise.race выбирает, какое уведомление ты слушаешь, и не имеет ни малейшего доступа к работе, которая за ним стоит. Всё, что ты сделал, — перестал ждать. Работа продолжается.

Посчитай цену на живом примере. Проба ходит раз в 10 секунд, зависимость лежит 30 минут — это 180 повисших соединений и 180 неотпущенных сокетов в процессе, который снаружи выглядит абсолютно здоровым: он же отвечает. С настоящим драйвером всё жёстче: у pg.Pool по умолчанию max: 10, и десятая повисшая проверка заберёт последнее соединение из пула. Дальше твой health check не пустит в базу боевые запросы — те самые, ради которых приложение существует. Проверка начнёт ронять приложение.

Проверка · 2 из 3

Почему Promise.race с таймером не решает задачу таймаута?

Незакрытый таймер — реальная мелкая проблема (лечится clearTimeout), но она не про ресурс зависимости. Промис — уведомление о результате, а не ручка управления работой: отказавшись слушать, ты ничего не остановил. Отменять умеет только тот, кто владеет ресурсом, — сокет, драйвер или сервер.

Опыт 3: таймаут, который отменяет

Разница в одной строке — socket.destroy(). Замени ping() целиком:

function ping(ms) {
  return new Promise((resolve, reject) => {
    const socket = net.connect(7777, '127.0.0.1', () => socket.write('PING\r\n'));

    const timer = setTimeout(() => {
      socket.destroy();                       // вот это и есть отмена
      reject(new Error(`timeout ${ms}ms`));
    }, ms);

    socket.once('data', () => {
      clearTimeout(timer);
      socket.end();
      resolve('pong');
    });
    socket.once('error', (err) => {
      clearTimeout(timer);
      reject(err);
    });
  });
}

Перезапусти, включи тот же опрос и смотри в терминал blackhole.mjs:

принял соединение, отвечать не буду. Открыто: 1
соединение закрыто. Открыто: 0
принял соединение, отвечать не буду. Открыто: 1
соединение закрыто. Открыто: 0
Вот ради чего всё

Снаружи ничего не изменилось: те же 503, те же 300 мс. Изменилось то, чего не видно из ответа, — процесс перестал накапливать последствия собственных проверок. Именно поэтому в плане M0-05 пункт 8 сформулирован как отдельная работа, а не как «оберни в Promise.race».

Два сорта таймаута — и что из этого писать в драйвере

Обобщи то, что ты увидел. Таймаут бывает двух сортов, и они не взаимозаменяемы:

  • Перестать ждать. Ты возвращаешь ответ по таймеру. Работа продолжается у того, кто её делает.
  • Прекратить работу. Ресурс освобождается: сокет уничтожен, statement прерван, соединение выкинуто из пула.

Самое неприятное открытие ждёт тебя в документации драйверов: настройка с честным словом timeout в названии сплошь и рядом относится к первому сорту. Вот что на самом деле делают те настройки, которые тебе понадобятся в M0-05 (проверено по исходникам, а не по названиям):

НастройкаГде живётЧто происходит по истечении
connectionTimeoutMillis (pg) клиент сокет уничтожается, вызов падает с Connection terminated due to connection timeout
query_timeout (pg) клиент ошибка Query read timeout. Отмена на сервер не отправляется — запрос там продолжает выполняться
statement_timeout (pg → PostgreSQL) сервер PostgreSQL сам прерывает statement и возвращает ошибку
commandTimeout (ioredis) клиент таймер на каждую команду, по нему команда отбивается ошибкой
enableOfflineQueue: false (ioredis) клиент команда без живого соединения падает сразу: Stream isn't writeable…, а не ждёт реконнекта
Умолчания, которые стоит знать наизусть

В pg по умолчанию выключено всё: statement_timeout: false, query_timeout: false, connect_timeout: 0. То есть «из коробки» драйвер ждёт вечно на всех трёх уровнях. В ioredis maxRetriesPerRequest равен 20 — висящая команда отобьётся сама после двадцати неудачных реконнектов, а если поставить null, будет ждать вечно.

Для readiness из этого следует конкретный набор. SELECT 1 не бывает долгим — значит главный враг не «тяжёлый запрос», а мёртвый сокет и занятый пул. Поэтому connectionTimeoutMillis здесь важнее, чем statement_timeout, а query_timeout в одиночку недостаточен: он вернёт тебе ответ и оставит запрос жить на сервере. И держи в голове ещё одно: pool.query() ждёт свободного соединения молча — если все десять заняты повисшими проверками, твой таймаут внутри индикатора даже не начнёт тикать.

Вопрос, который решает, что куда класть

Теперь вторая половина урока — та, ради которой эндпоинтов два, а не один. Разница между liveness и readiness не в глубине проверки. Она в том, что сделает оркестратор с твоим ответом.

  • Liveness провалился → kubelet убивает контейнер и запускает заново.
  • Readiness провалился → под убирают из endpoints сервиса. Процесс живёт, трафик не идёт.

Представь десять подов и Postgres, который моргнул на сорок секунд. Если /health ходит в базу, происходит вот что: три подряд неудачные пробы по 10 секунд — и kubelet убивает все десять контейнеров почти одновременно. Они стартуют, разом открывают пулы (десять подов × max: 10 — это сто соединений в первую секунду, при max_connections по умолчанию тоже сто), база, которая только-только встала, получает шторм и снова не отвечает. Пробы снова красные, снова рестарт, CrashLoopBackOff. Перезапуск не чинил проблему ни разу — он её усиливал.

И отдельно обидное: вместе с процессом ты каждый раз выбрасываешь всё, что могло бы объяснить причину, — прогретые кеши, незавершённые запросы и те самые логи с requestId, за которые ты воевал в уроке 0004.

Главное

Liveness отвечает ровно на один вопрос: поможет ли здесь перезапуск? Если ответ «нет» — проверке не место в liveness, какой бы важной она ни была. Внешняя зависимость перезапуском не чинится никогда. Это и есть критерий — не «лёгкая проверка против тяжёлой».

У readiness обратное свойство, и оно ценное: отказ обратим сам собой. База вернулась — проба позеленела, под вернулся в балансировку, вмешательства не потребовалось. Поэтому «проверять зависимости» — это про readiness по определению, а не по традиции.

Третий вид проб, startupProbe, существует ровно по этой же логике: он прикрывает медленный старт, чтобы liveness не убил процесс раньше, чем тот успел подняться. Тебе он в M0-05 не нужен, но знать про него стоит — на собеседовании спрашивают именно тройку.

Проверка · 3 из 3

Почему проверку соединения с базой нельзя класть в liveness?

Дублирование само по себе безвредно — вредно последствие. Ответ liveness — это не отчёт о здоровье, это запрос на перезапуск контейнера. Отвечая 503 из-за чужой базы, ты просишь оркестратор сделать то, что не помогает и усиливает отказ: перезапустить сразу все инстансы, которые упрутся в ту же базу.

Зачем это на самом деле — мост в M0-06

Ты сейчас выучил не «как приделать два роута». Ты выучил, что readiness — это ручка управления трафиком, а не отчёт. Как только это в голове, следующий issue становится очевидным.

M0-06 — graceful shutdown. Процесс получил SIGTERM. Наивный порядок: закрыть сервер, закрыть пул, выйти. И он порождает 502 у покупателя, потому что балансировщик узнаёт об уходе пода не мгновенно — он узнаёт от readiness, с задержкой в целый период опроса. Правильный порядок начинается не с закрытия, а с лжи во спасение: readiness начинает отдавать 503, ты ждёшь один-два периода опроса, трафик перестаёт приходить — и только теперь закрываешь пул и сервер.

Поэтому health check делается раньше graceful shutdown, а не наоборот: без ручки readiness останавливать приложение аккуратно просто нечем. А ещё дальше, в M8, результат пробы станет метрикой — и вопрос «сколько минут за неделю инстанс был not ready» окажется одним из немногих, на которые бизнес реагирует сразу.

Первоисточники

  • Читать в первую очередь: Kubernetes — Configure Liveness, Readiness and Startup Probes. Нужны разделы про три вида проб и таблица параметров: periodSeconds, timeoutSeconds, failureThreshold. Оттуда же — умолчания, которые я приводил в уроке.
  • Kubernetes — Pod Lifecycle, Container probes: одно предложение про то, что делает kubelet при провале каждой из проб. Это весь сегодняшний раздел про каскад, в двух абзацах первоисточника.
  • node-postgres — Pool и Client: connectionTimeoutMillis, idleTimeoutMillis, max, query_timeout, statement_timeout. Заодно открой packages/pg/lib/client.js в репозитории и найди строку Query read timeout — там видно своими глазами, что отмена на сервер не уходит.
  • PostgreSQL — Client Connection Defaults, параметр statement_timeout. Это второй сорт таймаута в чистом виде.
  • ioredis — Auto-reconnect и опции commandTimeout, enableOfflineQueue, maxRetriesPerRequest. Ключевое предложение про null: «let commands wait forever until the connection is alive again».
  • NestJS — Healthchecks (Terminus), раздел Custom health indicator: HealthIndicatorService, up() / down(). Готового индикатора для сырого pg там нет — не ищи, это проверено.
