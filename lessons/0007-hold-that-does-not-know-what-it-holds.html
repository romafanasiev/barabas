Урок 0007 · этап M1 · моделирование

Бронь, которая не знает, что держит

В нумерованной секции покупатель держит место. В фан-зоне — две штуки из пятисот. Одна и та же кнопка «забронировать», две разные вещи в базе. Сегодня ты сломаешь в терминале самый экономный способ это записать и получишь критерий, по которому выбирается форма развилки — не «сколько таблиц красивее», а «какое правило после выбора ещё можно запретить схемой».

Сначала вспомни

Без подглядывания в прошлые уроки.

Recall · 1 из 2

Чем материализованный счётчик отличается от блокировки общей строки как средство от write skew?

Первые два способа защищают ровно тот код, который их применил: забыл взять lock в одном эндпоинте — дыра вернулась. Счётчик превращает правило в CHECK, то есть в свойство схемы: его нельзя обойти запросом, написанным через год человеком, который про правило не слышал. Сегодня ты увидишь, что это ещё и решение о форме схемы, а не только средство от гонки.

Recall · 2 из 2

По какому признаку видно, что колонка стоит не в своей таблице?

Присяга Кента: каждый неключевой атрибут зависит от ключа, от всего ключа и ни от чего, кроме ключа. Повтор значения — следствие, а не признак. Сегодня тот же вопрос задаётся связи, а не колонке: от чего зависит эта ссылка — и одна ли она по смыслу?

Задача на один абзац

У тебя на диаграмме HoldItem ссылается на EventSeat — строку «место на этом концерте». Для партера это точно: держать можно ряд 4 место 12, и M1-10 запретит держать его дважды partial unique index'ом. Теперь покупатель открывает фан-зону и берёт два входа. Строки EventSeat там нет — в ненумерованной секции мест нет вообще, есть вместимость и число занятых. Чем заполнить event_seat_id?

Это и есть развилка, которую M1-02 называет главным вопросом issue. У неё ровно четыре честные формы, и у каждой своя цена. Сегодня мы не выбираем — сегодня мы смотрим, что база умеет запретить в каждой.

Полигон

Схема на выброс, в отдельном schema, чтобы не мешать будущим миграциям. Типы здесь int, а не uuid — это полигон, а не твоя схема.

поднять базу и зайти в psql

$ docker compose exec postgres psql -U postgres -d barabas

INSERT INTO allocation VALUES (1, 2);

Опыт 1: самый экономный способ — одна таблица на обе ветки

Та самая форма, которую триаж M1-02 называет ловушкой: две nullable FK, заполнена всегда одна.

CREATE TABLE hold_item (
  id            serial PRIMARY KEY,
  hold_id       int  NOT NULL,
  event_seat_id int  REFERENCES event_seat(id),
  allocation_id int  REFERENCES allocation(id),
  quantity      int,
  status        text NOT NULL
);

CREATE UNIQUE INDEX ON hold_item (event_seat_id) WHERE status = 'active';

Сначала хорошая новость. Ветка «место» защищена ровно так, как ты решил в пункте 7:

INSERT INTO hold_item (hold_id, event_seat_id, quantity, status)
VALUES (1, 1, 1, 'active');
-- INSERT 0 1

INSERT INTO hold_item (hold_id, event_seat_id, quantity, status)
VALUES (2, 1, 1, 'active');
-- ERROR:  duplicate key value violates unique constraint "hold_item_event_seat_id_idx"
-- DETAIL:  Key (event_seat_id)=(1) already exists.
Работает

Обрати внимание, почему работает: «одно место — один активный Hold» — это правило про одну строку против одной строки. Уникальность — ровно такой инструмент. Ничего считать не надо, достаточно сравнить значения.

Теперь фан-зона. Вместимость — два. Два покупателя берут по два входа.

INSERT INTO hold_item (hold_id, allocation_id, quantity, status)
VALUES (3, 1, 2, 'active');
-- INSERT 0 1

INSERT INTO hold_item (hold_id, allocation_id, quantity, status)
VALUES (4, 1, 2, 'active');
-- INSERT 0 1

SELECT sum(quantity) AS held, (SELECT capacity FROM allocation WHERE id = 1) AS capacity
FROM hold_item WHERE allocation_id = 1 AND status = 'active';
--  held | capacity
-- ------+----------
--     4 |        2
Вот оно

Четыре удержанных при вместимости два, две команды подряд, ни одной ошибки, и даже без всякой конкуренции — это не race condition, это просто отсутствующее правило. Овербукинг в один поток.

Инстинктивное лекарство — дописать CHECK. Попробуй:

ALTER TABLE hold_item ADD CONSTRAINT within_capacity CHECK (
  (SELECT sum(quantity) FROM hold_item hi WHERE hi.allocation_id = hold_item.allocation_id) <= 2
);
-- ERROR:  cannot use subquery in check constraint

Почему база отказалась

Документация PostgreSQL формулирует это в одном предложении: выражение CHECK не может содержать подзапросы и ссылаться на что-либо, кроме колонок текущей строки. Причина не в лени разработчиков. Constraint проверяется при записи строки; чтобы он был честным, его истинность обязана зависеть только от того, что в этой записи есть. Правило «сумма по группе строк не больше числа» зависит от строк, которых команда не трогала, — проверить его один раз при вставке недостаточно, его пришлось бы перепроверять при каждом изменении любой соседней строки, включая те, что делают параллельные транзакции.

Ты это уже видел в уроке 0003 с другой стороны: правило шириной больше одной строки база не видит. Тогда речь шла про конкуренцию. Сегодня оказалось, что оно не видно даже без конкуренции — и это уже не про изоляцию, а про форму схемы.

Проверка · 1 из 3

Почему база пропустила четыре удержания при вместимости два?

Ни отдельная строка, ни отдельная команда правило не нарушают: «держу два при вместимости два» законно для каждой из них. Нарушает их сумма — факт, которого нет ни в одной строке таблицы. Пока факт не записан, запрещать нечего.

Опыт 2: сделать факт строкой

Если инвариант — про сумму, запиши сумму. Тогда правило перестаёт быть правилом над множеством и становится правилом внутри строки, а это база умеет.

CREATE TABLE ticket_allocation (
  id       int PRIMARY KEY,
  capacity int NOT NULL,
  held     int NOT NULL DEFAULT 0,
  sold     int NOT NULL DEFAULT 0,
  CONSTRAINT within_capacity CHECK (held + sold <= capacity),
  CONSTRAINT non_negative    CHECK (held >= 0 AND sold >= 0)
);

INSERT INTO ticket_allocation (id, capacity) VALUES (1, 2);

UPDATE ticket_allocation SET held = held + 2 WHERE id = 1;
-- UPDATE 1

UPDATE ticket_allocation SET held = held + 1 WHERE id = 1;
-- ERROR:  new row for relation "ticket_allocation" violates check constraint "within_capacity"
-- DETAIL:  Failing row contains (1, 2, 3, 0).

Та же проверка, которая минуту назад была невыразима, теперь стоит в схеме и стоит ноль строк кода. Второй CHECK закрывает available >= 0 — второй инвариант TicketAllocation из таблицы агрегатов.

Главное

Инвариант выразим ровно тогда, когда все его участники помещаются в одну строку. Вопрос «какую форму дать развилке» — это на самом деле вопрос «где записан факт, который я хочу запретить нарушать». Не «сколько таблиц», не «красиво ли выглядит».

И сразу цена, потому что бесплатно не бывает:

  • Счётчик — денормализация. held обязан меняться в той же транзакции, что и hold_item, иначе строки и число разъедутся, а Reconciliation из словаря — это ровно тот запрос, который такое расхождение ловит. Осознать эту цену и записать её — отдельный issue, M1-12.
  • В строке больше не видно, кто держит. ticket_allocation знает «занято три», но не знает, чьи это три. Знание живёт в hold_item.quantity, то есть проверка «отпустил ровно столько, сколько держал» — уже не constraint, а код агрегата.
  • Конкуренция никуда не делась, она переехала. UPDATE ... SET held = held + 1 атомарен и сериализуется на блокировке строки. А вот SELECT held → посчитать в приложении → UPDATE ... SET held = 3 — это классический lost update из урока 0001, и CHECK от него не спасёт: он проверит то число, которое ты сам привёз. Constraint защищает от неверного значения, а не от неверного способа его посчитать.
  • Вся фан-зона — одна строка. Значит все покупатели этой зоны выстраиваются в очередь на одну блокировку. Это цена, которую ты назовёшь вслух в M4, и она же — аргумент, который иногда перевешивает всё остальное.
Проверка · 2 из 3

Что именно изменилось, когда счётчик стал колонкой?

Считать заранее — это про скорость чтения, приятный побочный эффект. Смысл в другом: held, sold и capacity оказались в одной строке, а значит выражение над ними — законный CHECK. Изоляция при этом остаётся вопросом: constraint проверяет значение, а не то, как ты его получил.

Четыре формы развилки и их цена

Теперь то, ради чего урок. Ты знаешь, что каждая ветка умеет защищать поодиночке. Осталось решить, как они лежат вместе.

ФормаЧто держит базаЧем платишь
A. Одна таблица, две nullable FK Обе FK честные — NULL внешний ключ не проверяется, и это не дыра, а правило SQL. Partial unique по месту работает. «Ровно одно из двух» выражается CHECK (num_nonnulls(event_seat_id, allocation_id) = 1) CHECK растёт с каждым атрибутом ветки: quantity для места всегда 1, для квоты — любое, и это уже вторая половина выражения. Каждый запрос обязан помнить про NULL. Строка не отвечает на вопрос «что ты такое», пока не посмотришь на две колонки сразу
B. Супертип hold_item + две дочерние таблицы У каждой ветки свой FK без NULL и свои constraint, ни одного «иногда пусто». Общий hold_id и статус лежат в одном месте База не умеет потребовать «у каждой строки супертипа ровно одна дочерняя»: ни одной, или сразу две — законно. Join на каждое чтение. Это классический class-table inheritance со всеми его известными неудобствами
C. Две независимые таблицы, общего супертипа нет Каждая ветка — чистая схема: никаких NULL, никаких развилочных CHECK, свой partial unique там, где он нужен Инвариант «Hold непустой» теперь считается по двум таблицам сразу. Два репозитория, два пути в коде, две миграции. В M4-08 детерминированный порядок захвата придётся задавать ещё и между таблицами, а не только между строками
D. Развилки нет: ненумерованная секция тоже получает строки EventSeat Одна ветка на всё. Вместимость = число строк, «продано дважды» ловится тем же самым индексом, инвариант held + sold <= capacity исчезает как отдельное правило — его больше нечем нарушить Строки на каждое место фан-зоны, умноженные на каждый концерт. Ряд и номер становятся синтетическими — то есть у сущности появляются поля, которые ничего не значат для половины данных. «Сколько свободно» превращается в COUNT(*) на горячем пути, и денормализованный счётчик из M1-12 становится не выбором, а необходимостью
Критерий

Форма выбирается не по числу таблиц и не по красоте диаграммы. Задай каждому варианту два вопроса: какие инварианты после него остаются выразимыми в схеме — и какие переезжают в код, где их защищает дисциплина, а не база. Второй список не обязан быть пустым. Он обязан быть названным.

Заметь: вариант A — тот, который issue называет ловушкой, — вовсе не запрещён. Его цена известна и измерима, и есть системы, где она приемлема. Возвращают на доработку не за выбор A, а за выбор A молча, когда цена не названа и обнаруживается в M1-06, где CHECK внезапно оказывается на пять строк длиннее, чем ожидалось.

Как это выглядит на диаграмме — и почему это пункт 5, а не косметика

Развилка проступает в cardinality раньше, чем в DDL. В варианте A связь HoldItem → EventSeat читается как «ноль или один»:

EventSeat |o--o{ HoldItem : "held by"

Со стороны EventSeat стоит |o — ноль или один. То есть ты диаграммой заявляешь: у HoldItem может не быть места. Это выглядит безобидно, а означает ровно то, что ты видел в опыте 1: строку, которая не держит ничего, база примет с радостью, если не дописать CHECK. В варианте C та же связь становится || — ровно один, — и запрещать нечего, потому что непредставимо.

Отсюда правило для пункта 5: каждый |o и каждый o{ — это вопрос «а что, если ноль», на который должен быть ответ. Либо «так и задумано, вот constraint, который стережёт границу», либо это случайная дыра, которую ты сам на себя нарисовал. Сплошная и пунктирная линии (-- против ..) в пункте 9 отвечают на другой вопрос — может ли дочерняя строка пережить родителя, — и именно поэтому их ответы обязаны совпасть с границами агрегатов.

Проверка · 3 из 3

Что |o со стороны родителя означает на языке constraint'ов?

Минимум на конце связи — это про NOT NULL на колонке ссылки, и больше ни про что. «У родителя может не быть детей» — это другой конец линии. Отложенная проверка — это DEFERRABLE, свойство самого constraint, которое на диаграмме не рисуется вообще.

Что этот выбор потянет за собой

  • M1-04 — миграции. Форма решает, сколько таблиц ты создашь и какие колонки будут NOT NULL.
  • M1-06 — check constraints. В варианте A часть из них будет про развилку, в C — ни одного такого.
  • M1-10 — partial unique index. Уникальность «одно место — один активный Hold» переживает все четыре формы, но в A индекс строится по nullable-колонке, и стоит один раз проговорить, что NULL'ы в уникальный индекс не конфликтуют между собой.
  • M1-12 — ADR про денормализованный available. В варианте D этот ADR становится обязательным, в A и C — остаётся выбором.
  • M1-13 — границы агрегатов. TicketAllocation назван агрегатом в CONTEXT.md: значит Hold ссылается на него по id, а не втягивает внутрь себя. Форма развилки обязана этому не противоречить.
  • M4-08 — порядок захвата блокировок. Одна таблица или две — это разный алгоритм сортировки при захвате.

И отдельно — то, чего сейчас нет вообще. На твоей диаграмме от Inventory до концерта нет пути: Inventory знает TicketType, а TicketType не знает ни Event, ни Section. Любая форма из четырёх требует ответа на вопрос «квота чего»: квота типа билета на концерте, квота секции на концерте, или и то и другое. Это первая из трёх развилок триажа, и без неё вторая не решается.

Первоисточники

  • Читать в первую очередь: PostgreSQL — Constraints. Нужны разделы Check Constraints (там дословно про запрет подзапросов и про то, что видно только текущую строку) и Foreign Keys. Заодно посмотри Exclusion Constraints — инструмент, который умеет то, что UNIQUE не умеет, и однажды тебе понадобится.
  • PostgreSQL — Partial Indexes. Раздел 11.8.1 — ровно твой случай с WHERE status = 'active', и там же объяснение, почему частичный индекс дешевле полного.
  • PostgreSQL — Comparison Functions and Operators, функции num_nonnulls и num_nulls. Короткий способ записать «ровно одно из двух» без лестницы из AND и OR.
  • Bill Karwin, SQL Antipatterns, глава Polymorphic Associations. Это твоя развилка, разобранная целиком: почему одна колонка на две сущности ломает FK и какие три выхода из этого есть. Варианты B и C в уроке — оттуда.
  • Martin Fowler — Class Table Inheritance и рядом Single Table Inheritance. Те же A и B, но с точки зрения мэппинга объектов, а не схемы. Полезно прочитать оба взгляда до решения.
  • Mermaid — Entity Relationship Diagrams, таблица cardinality и разница -- / ... Пригодится в пунктах 5 и 9.
