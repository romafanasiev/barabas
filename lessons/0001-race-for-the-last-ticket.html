Поднимаем полигон

Настоящий PostgreSQL на пять минут, на порту 5433, чтобы ничего не задеть:

docker run --rm -d --name tix-lab \
  -e POSTGRES_PASSWORD=lab -p 5433:5432 postgres:18

Создаём остаток ровно в один билет:

docker exec -i tix-lab psql -U postgres <<'SQL'
CREATE TABLE inventory (
  ticket_type_id int PRIMARY KEY,
  available      int NOT NULL

INSERT INTO inventory VALUES (1, 1);
SQL

Теперь открой два терминала. В каждом:

docker exec -it tix-lab psql -U postgres

Это два одновременных запроса к твоему API. Терминал A — Аня, терминал B — Борис. Оба хотят последний билет.

Что только что произошло

Остаток честно равен нулю. Ошибок не было. Транзакции не откатились. И два человека едут на концерт с билетами на одно кресло. Ты не увидишь этого ни в логах, ни в мониторинге — узнаешь на входе, от охраны.

Это классическая аномалия, у неё есть имя: lost update. Обновление Ани потерялось — Борис затёр его, приняв решение по устаревшему прочтению.

Почему база это допустила

По умолчанию PostgreSQL работает на уровне изоляции Read Committed. Он даёт ровно одну гарантию: ты никогда не увидишь незакоммиченные чужие данные. Он не обещает, что данные не изменятся между твоим SELECT и твоим UPDATE.¹

А между ними — пропасть. Вот она:

МоментЧто происходит
t₀A читает available = 1
t₁B читает available = 1 — и он прав, ещё никто ничего не изменил
t₂A принимает решение в приложении, на основе данных из t₀
t₃B принимает решение в приложении, на основе данных из t₁
t₄Оба пишут. Оба «правы». Билетов продано два.

Ключевая мысль, которую стоит унести из этого урока целиком:

Решение, принятое в коде приложения по прочитанным данным, действительно ровно до момента, пока эти данные не защищены блокировкой или constraint. Секунду спустя оно уже ничего не значит.
Проверь себя

Почему BEGIN вокруг обоих запросов не спас от овербукинга?

Транзакция гарантирует «всё или ничего» для твоих изменений. Она ничего не говорит о том, что параллельная транзакция не прочитает и не изменит ту же строку. Обычный SELECT в Read Committed не берёт никакой блокировки — строка остаётся свободной для всех.

Починка №1: заблокировать строку при чтении

Скажем базе, что мы читаем с намерением изменить. Тогда вторая транзакция будет вынуждена подождать.²

Верни остаток в единицу и повтори тот же танец, добавив три слова:

UPDATE inventory SET available = 1 WHERE ticket_type_id = 1;

Терминал A · Аня

-- шаг 1
BEGIN;
SELECT available
  FROM inventory
 WHERE ticket_type_id = 1
   FOR UPDATE;      -- ← блокировка
-- available = 1



-- шаг 3
UPDATE inventory
   SET available = 0
 WHERE ticket_type_id = 1;
COMMIT;

Терминал B · Борис




-- шаг 2
BEGIN;
SELECT available
  FROM inventory
 WHERE ticket_type_id = 1
   FOR UPDATE;
-- ⏳ ВИСИТ. Ждёт commit от A.

-- шаг 4 (после commit A)
-- available = 0
-- "мест нет" → 409
ROLLBACK;
Вот он, момент

Терминал B завис на шаге 2. Это не баг — это ровно та секунда, которую база выкупила у гонки. Когда A закоммитил, B перечитал строку и увидел честный ноль. Один билет — один покупатель.

Цена у этого есть, и её надо знать заранее: пока A держит блокировку, все остальные стоят в очереди. Держать транзакцию открытой во время похода в платёжный шлюз — способ уронить прод. В M4 мы разберём это подробно.

Починка №2: та, которой ты доверяешь по-настоящему

Блокировку можно забыть поставить. В новом эндпоинте, в скрипте миграции, в чужом pull request. Поэтому последний рубеж ставится не в коде, а в схеме:

ALTER TABLE inventory
  ADD CONSTRAINT available_non_negative CHECK (available >= 0);

И тогда само списание становится одним атомарным выражением — без чтения, без решения в приложении, без окна для гонки:

UPDATE inventory
   SET available = available - 1
 WHERE ticket_type_id = 1
   AND available > 0;
-- UPDATE 1  → продано
-- UPDATE 0  → мест нет, отдаём 409

Здесь чтение и запись — одна операция, и база сама держит блокировку на время выполнения UPDATE. А CHECK стоит за ними и ловит любой будущий код, который попытается уйти в минус. Даже если этот код напишешь не ты.

Проверь себя

Зачем нужен CHECK (available >= 0), если UPDATE уже проверяет available > 0?

Constraint — единственная гарантия, которая не зависит от дисциплины разработчика. Условие в WHERE живёт в одном запросе; CHECK живёт в схеме и действует на все запросы, включая те, что напишут через полгода. Правило: инварианты предметной области выражай в схеме, а не только в сервисе.
