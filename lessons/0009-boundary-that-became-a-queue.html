Урок 0009 · этап M1 · тактический DDD

Граница, которая стала очередью

Агрегат Event со всеми местами внутри выглядит на диаграмме честнее всех: одно событие, одни правила, один корень. Сегодня ты увидишь в терминале, во что он превращается на второй одновременной покупке — и что покупатели разных кресел стоят в одной очереди, хотя не конкурируют ни за что. Потом сузишь границу до кресла и посмотришь, как из-под неё выпадает инвариант. Между этими двумя ошибками и лежит ответ, который ты запишешь в M1-13.

Сначала вспомни

Без подглядывания в прошлые уроки.

Recall · 1 из 2

Два запроса одновременно прочитали «свободных мест хватает» и оба записали бронь. Что именно не сработало?

Это write skew из урока 0003. База защищает то, что видит как конфликт: две записи в одну строку или два одинаковых значения в одном уникальном ключе. Прочитали одно, записали другое — конфликта для неё нет. Лечится не уровнем изоляции, а тем, во что ты превратил правило: строку, которую обе транзакции обязаны тронуть, или ключ, который обе обязаны занять.

Recall · 2 из 2

Что делает копию чужой колонки в своей таблице законной?

Из урока 0008: копия плюс опора плюс каскад. Сегодня то же самое слово «механизм» появится в другом месте — у инварианта. Спрашивать будем не «где записано правило», а «кто его исполняет в момент коммита».

Задача на один абзац

Про агрегат обычно рассказывают как про способ организовать код: корень, внутренности, доступ только через корень. Это правда, но из неё не следует, где провести границу — а именно это ты решаешь в M1-13, и решение уходит прямо в схему M1-05.

Полезнее определение через момент времени: агрегат — это множество данных, которые обязаны быть согласованы в момент коммита. Из него сразу следует цена, потому что согласованность в момент коммита в базе достигается ровно одним способом — все участники внутри одной транзакции. А одна транзакция — это одна пачка блокировок. Отсюда правило, которое связывает весь ROADMAP:

Одной строкой

Граница агрегата — это граница транзакции, а граница транзакции — это граница блокировки. Нарисуешь агрегат крупно сейчас — получишь очередь из покупателей в M4.

Сегодня ты потрогаешь обе стенки: сначала границу, проведённую слишком широко (очередь там, где конкуренции нет), потом слишком узко (инвариант, у которого не оказалось владельца). Обе ошибки в терминале выглядят по-разному, и обе выглядят одинаково безобидно на диаграмме.

Полигон

Схема на выброс, в отдельном schema. Три вкладки: A и B — два покупателя, C — наблюдатель, который смотрит на базу снаружи.

в каждой из трёх вкладок

$ docker compose exec postgres psql -U postgres -d barabas

один раз, в любой

CREATE SCHEMA lesson9;
SET search_path = lesson9;

CREATE TABLE event (
  id      int PRIMARY KEY,
  version int NOT NULL DEFAULT 0
);

CREATE TABLE event_seat (
  id       int  PRIMARY KEY,
  event_id int  NOT NULL REFERENCES event(id),
  label    text NOT NULL
);

CREATE TABLE hold_seat_item (
  id            int  GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  hold_id       int  NOT NULL,
  event_seat_id int  NOT NULL REFERENCES event_seat(id),
  active        bool NOT NULL DEFAULT true
);

INSERT INTO event (id) VALUES (1);
INSERT INTO event_seat VALUES (1, 1, 'A1'), (2, 1, 'A2');

Колонка version — не украшение: это самый распространённый способ защитить широкий агрегат. Корень несёт версию, репозиторий читает агрегат, при записи сверяет версию и увеличивает её. Дальше она нам понадобится как повод потрогать строку события.

Не забудь SET search_path = lesson9; в каждой вкладке отдельно — это настройка сессии, а не базы.

Опыт 1: агрегат размером с событие

Рисуем границу так, как её рисует инстинкт: корень — Event, внутри — все его места, все брони на эти места. Доступ только через корень, значит любая покупка начинается с захвата строки события. Аня берёт кресло A1, Борис — A2. Это разные кресла: конкуренции между ними нет никакой.

Терминал A · Аня, кресло A1

BEGIN;

SELECT id FROM event
  WHERE id = 1 FOR UPDATE;
--  id
-- ----
--   1

INSERT INTO hold_seat_item
  (hold_id, event_seat_id)
  VALUES (100, 1);
-- INSERT 0 1

Терминал B · Борис, кресло A2

BEGIN;

SELECT id FROM event
  WHERE id = 1 FOR UPDATE;
-- (курсор не возвращается)

Борис висит. Он не трогал ни кресло A1, ни бронь Ани — он попросил ту же строку события, потому что так велит граница агрегата. Посмотри на это снаружи, из третьей вкладки:

Терминал C · наблюдатель

SELECT pid, state, wait_event_type, wait_event, left(query, 52) AS query
FROM pg_stat_activity
WHERE datname = 'barabas' AND state <> 'idle' AND pid <> pg_backend_pid();

--  pid |        state        | wait_event_type |  wait_event   |                query
-- -----+---------------------+-----------------+---------------+---------------------------------
--  861 | idle in transaction | Client          | ClientRead    | INSERT INTO hold_seat_item (hold
--  862 | active              | Lock            | transactionid | SELECT id FROM event WHERE id = 1

Вот она, цена границы, и она измерима: wait_event_type = Lock, wait_event = transactionid. Борис ждёт не строку и не индекс — он ждёт завершения транзакции Ани. Сколько она продлится, зависит от Ани: сходит ли её код в платёжный шлюз, отправит ли письмо, подумает ли покупатель над схемой зала.

Закоммить Аню (COMMIT; в терминале A) — Борис тут же получит свою строку и поедет дальше. Ничего не сломалось. Сломалась только пропускная способность: в зале 500 мест, а продаётся он по одному месту за раз. На старте продаж это ровно та очередь, ради которой пишут «сайт лёг».

Проверь себя

Почему эта очередь называется фиктивной, хотя база вела себя совершенно правильно?

Аня писала в hold_seat_item строку про кресло A1, Борис — про A2. Пересечения нет. Общей у них была ровно одна строка — event, и попала она в транзакцию не потому, что данные этого требуют, а потому, что так проведена граница агрегата. Фиктивная конкуренция — это конкуренция, созданная моделью, а не задачей.

Признак слишком широкой границы

Внутри агрегата есть коллекция, которая растёт с бизнесом: места события, заказы покупателя, брони концерта. Такой агрегат нельзя ни загрузить целиком, ни заблокировать, не остановив то, ради чего он существует. Ровно этот признак стоит первым в разделе «На что смотрю на ревью» твоего M1-13.

Опыт 2: агрегат размером со строку

Инстинкт после опыта 1 — резать. Пусть агрегат будет самым маленьким из возможных: одна позиция холда, одна строка. Ни коллекций, ни корня над ними, никто никого не ждёт.

подготовка, в любой вкладке

TRUNCATE hold_seat_item;

Инвариант, который мы при этом обязаны сохранить, звучит так: одно место удерживается не более чем одним активным Hold. Проверять его каждый будет сам — как проверяет обычный сервис: сначала посмотрел, потом записал.

Терминал A · Аня, кресло A1

BEGIN;

SELECT count(*) FROM hold_seat_item
  WHERE event_seat_id = 1 AND active;
--  count
-- -------
--      0

INSERT INTO hold_seat_item
  (hold_id, event_seat_id)
  VALUES (100, 1);
COMMIT;

Терминал B · Борис, кресло A1

BEGIN;

SELECT count(*) FROM hold_seat_item
  WHERE event_seat_id = 1 AND active;
--  count
-- -------
--      0

INSERT INTO hold_seat_item
  (hold_id, event_seat_id)
  VALUES (200, 1);
COMMIT;

Обе команды прошли, обе транзакции закоммитились, база не сказала ни слова:

SELECT hold_id, event_seat_id, active FROM hold_seat_item ORDER BY hold_id;
--  hold_id | event_seat_id | active
-- ---------+---------------+--------
--      100 |             1 | t
--      200 |             1 | t

Два человека держат одно кресло. Никакой гонки в коде нет — обе проверки честно вернули ноль, потому что на момент проверки соседняя строка ещё не существовала. Это урок 0003 в чистом виде, но смотреть на него сегодня надо под другим углом.

Спроси не «почему база пропустила», а «кто должен был не пропустить». Инвариант говорит про множество строк одного кресла. Агрегат размером в одну строку про это множество ничего не знает: он видит только себя. Правило оказалось ничьим — и именно это, а не write skew, здесь диагноз. Write skew — симптом.

Опыт 3: граница на месте

Правильная граница — та, внутри которой инвариант выразим, и ни одной строкой шире. Правило «одно кресло — один активный Hold» говорит про кресло, значит владелец — кресло, а не событие и не отдельная позиция. В базе это тот самый механизм, который ты выбрал в M1-02 решением 1:

TRUNCATE hold_seat_item;

CREATE UNIQUE INDEX hold_seat_item_active_uq
  ON hold_seat_item (event_seat_id) WHERE active;

Теперь повтори опыт 2 без предварительного SELECT — сразу INSERT, оба на кресло A1. Аня первая, Борис через секунду.

Терминал A · Аня, кресло A1

BEGIN;
INSERT INTO hold_seat_item
  (hold_id, event_seat_id)
  VALUES (100, 1);
-- INSERT 0 1

-- держим транзакцию открытой
COMMIT;

Терминал B · Борис, кресло A1

BEGIN;
INSERT INTO hold_seat_item
  (hold_id, event_seat_id)
  VALUES (200, 1);
-- (курсор не возвращается)

-- после COMMIT у Ани:
-- ERROR:  duplicate key value violates
--   unique constraint "hold_seat_item_active_uq"
-- DETAIL:  Key (event_seat_id)=(1) already exists.

Обрати внимание на две фазы, они обе важны и обе видны в терминале C. Пока Аня не закоммитила, Борис ждёт с тем же wait_event = transactionid, что в опыте 1: база не может решить его судьбу, пока не знает исхода Аниной транзакции. Как только Аня коммитит — Борис мгновенно получает 23505. Если бы Аня сделала ROLLBACK, Борис поехал бы дальше с успешной вставкой.

А теперь главное — то, ради чего этот опыт стоит между двумя другими. Повтори его на разных креслах: Аня на A1, Борис на A2.

Терминал C · обе транзакции открыты, кресла разные

SELECT pid, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE datname = 'barabas' AND state <> 'idle' AND pid <> pg_backend_pid();

--  pid  |        state        | wait_event_type | wait_event
-- ------+---------------------+-----------------+------------
--   995 | idle in transaction | Client          | ClientRead
--   996 | idle in transaction | Client          | ClientRead

Ни одного Lock. Обе вставки прошли, никто никого не ждал. Сравни с опытом 1 построчно: там Lock / transactionid на тех же самых двух креслах — и разница между двумя выводами pg_stat_activity есть вся разница между двумя границами. Правильная граница создаёт очередь ровно там, где есть настоящий конфликт, и нигде больше.

Мера, которую можно предъявить на ревью

«Агрегат маленький» — это не про красоту диаграммы, и доказывается это не словами. Доказательство — две транзакции, которые по бизнесу не конфликтуют, и пустая колонка wait_event_type у обеих. Это же и есть заготовка race-теста из M4.

Опыт 4: очередь, которая честная

Из опыта 3 легко вынести неверный вывод — «блокировка это плохо». Нет: плохо, когда ждут те, кто не конкурирует. Вторая половина учёта в твоём домене устроена так, что конкуренция настоящая, и очередь там неизбежна.

CREATE TABLE ticket_allocation (
  id       int PRIMARY KEY,
  capacity int NOT NULL,
  held     int NOT NULL DEFAULT 0,
  sold     int NOT NULL DEFAULT 0,
  CONSTRAINT ta_held_sold_ck CHECK (held + sold <= capacity)
);

INSERT INTO ticket_allocation VALUES (1, 1, 0, 0);   -- последнее место в фан-зоне

Терминал A · Аня

BEGIN;
UPDATE ticket_allocation
  SET held = held + 1 WHERE id = 1;
-- UPDATE 1

COMMIT;

Терминал B · Борис

BEGIN;
UPDATE ticket_allocation
  SET held = held + 1 WHERE id = 1;
-- (ждёт; после COMMIT у Ани:)
-- ERROR:  new row for relation "ticket_allocation"
--   violates check constraint "ta_held_sold_ck"
-- DETAIL:  Failing row contains (1, 1, 2, 0).

Здесь Борис ждёт по делу: они с Аней претендуют на одно и то же последнее место, и порядок между ними обязан быть установлен. После коммита Ани база перечитывает строку заново и применяет held = held + 1 к свежему значению — поэтому CHECK и ловит переполнение. Это не то же самое, что опыт 2: там каждая транзакция несла свой заранее посчитанный результат, здесь обе выражены как приращение, и второе считается уже после первого.

Гранулярность очереди равна гранулярности границы. Агрегат TicketAllocation — это одна строка на пару «событие + секция», значит конкуренция замыкается внутри секции: партер не мешает балкону. Был бы агрегат «событие целиком» — мешал бы, и это в точности опыт 1.

Три вопроса к границе

Эти вопросы и есть инструмент, которым закрываются пункты M1-13. Задавать их надо к каждому инварианту по очереди, а не к сущностям.

ВопросЧто он ловитОтвет, который не принимается
Что обязано быть истинно в момент коммита? Всё названное обязано попасть в одну транзакцию, остальное — снаружи и по id «Данные должны быть консистентны» — это не правило, это пожелание
Сколько строк блокирует одна операция? Фиктивную конкуренцию: покупатели, которые ждут друг друга без причины «Это быстро» — измеряется через pg_stat_activity, а не оценивается
Что станет ничьим, если сузить? Инвариант без владельца: правило есть в голове, механизма нет ни у кого «Проверим в сервисе» — сервисов два, и они не видят друг друга

Первый вопрос разворачивается в схему, второй — в цену, третий — в возврат на доработку, если пропустить. В M1-13 они стоят пунктами 2, 4 и 3 соответственно.

Что этот урок не решает за тебя

Самый спорный вопрос твоей карты агрегатов сегодня намеренно оставлен открытым, и вот он целиком. Инвариант «одно место — один активный Hold» в CONTEXT.md приписан агрегату EventSeat. Но защищает его, как ты только что видел, уникальный индекс по hold_seat_item — таблице, которая по решению 6 из M1-02 лежит внутри Hold. В момент коммита строка event_seat не участвует вообще: её никто не читает и не блокирует.

Отсюда две возможные позиции, и обе защитимы:

  • Владелец — EventSeat. Правило про кресло, кресло и есть владелец, а hold_seat_item — лишь способ хранения его состояния. Тогда придётся объяснить, почему агрегат защищает инвариант, не участвуя в транзакции.
  • Владелец — Hold. В коммите участвуют строки холда и его позиций, они и составляют границу, а EventSeat снаружи и по id. Тогда придётся объяснить, что защищает кресло от двух разных холдов — ведь каждый из них валиден сам по себе.

Подсказка ровно одна: правильный ответ — тот, из которого следует схема M1-05, которую ты сможешь показать. Второй вариант ведёт к «инвариант держит индекс, а агрегат его только формулирует» — и это законный ответ, если он записан, а не подразумевается.

Чем платишь

У маленьких агрегатов есть цена, и на ревью я спрошу, знаешь ли ты её.

  • Согласованность между агрегатами перестаёт быть мгновенной. Между ними — ссылки по id и eventual consistency: сначала записали один, потом, отдельной транзакцией или событием, второй. Между этими моментами система в состоянии, которого нет ни в одной схеме на бумаге.
  • Иногда это неприемлемо — и тогда правило нарушают осознанно. Подтверждение холда на три места трогает три агрегата EventSeat в одной транзакции, потому что «продали дважды на секунду» бизнес не принимает. Цена нарушения — конкуренция за блокировки и риск дедлока: две транзакции, взявшие места в разном порядке, встают друг против друга. Лечится детерминированным порядком захвата (M4-08), а обосновывается в M1-14.
  • Чтение через агрегаты становится вредным. Страница «какие места свободны» не должна грузить ни один агрегат: она читает мимо доменной модели, прямым SQL. Это уже записано в CONTEXT.md, и сегодняшний опыт 1 объясняет, почему — загрузка агрегата ради цифры на экране берёт блокировки там, где ничего не пишется.
Обратная ошибка, о которой забывают

Агрегат без поведения не защищает ничего. Если снаружи можно написать hold.status = 'confirmed', то граница нарисована, а двери в ней нет: любой сервис приводит объект в невалидное состояние, не нарушив ни одного правила компиляции. Это anemic domain model, и M1-17 существует ровно против неё. Сегодняшняя карта границ — только половина работы; вторая половина — методы, через которые эти границы пересекаются.

Первоисточники

  • Читать в первую очередь: Vaughn Vernon, Effective Aggregate Design — три части, PDF, бесплатно. Часть I про то, почему большие агрегаты разваливаются, часть II — правило «ссылайся на другие агрегаты по id», часть III — что делать, когда согласованность всё-таки нужна между ними. Это самый короткий путь к тому, что сегодня делалось руками.
  • Eric Evans, Domain-Driven Design, глава 6 «The Life Cycle of a Domain Object», раздел Aggregates. Первоисточник термина. Там же про то, что инвариант — это правило, которое обязано выполняться при каждом изменении данных, а не «в целом по системе».
  • Martin Fowler, DDD_Aggregate — определение на одну страницу, годится как шпаргалка перед защитой.
  • Martin Fowler, AnemicDomainModel. Короткая заметка про то, во что превращается доменный слой без поведения. Прямой вход в M1-17.
  • PostgreSQL — Explicit Locking, раздел Row-Level Locks: какие блокировки берут FOR UPDATE и обычный UPDATE, и почему ожидание в опытах 1 и 4 выглядит одинаково, а стоит по-разному.
  • PostgreSQL — pg_stat_activity. Значения wait_event_type и wait_event перечислены там же; в M8 эта вьюха станет источником метрики, а сегодня это просто способ увидеть очередь глазами.
