Урок 0004 · этап M0 · наблюдаемость

Лог, подписанный чужим именем

Три урока подряд ты защищал данные от гонки. Сейчас ты увидишь ту же гонку там, где её никто не ждёт, — в собственных логах. И научишься механизму, который в M4 понадобится тебе снова, уже для транзакций.

≈ 25 минут Только Node, без Docker и без базы Ведёт к M0-04, M0-07, M4-05

Сначала вспомни

Без подглядывания в прошлые уроки.

Recall · 1 из 2

Почему правило «не больше двух VIP-мест на покупателя» не закрывается через UNIQUE?

UNIQUE отвечает на вопрос «было ли уже такое значение». Здесь значения разные — A1 и A2, — а нарушает правило их количество, которое не лежит ни в одной строке.

Recall · 2 из 2

Что даёт materializing conflicts такого, чего не дают первые два способа?

SERIALIZABLE и ручная блокировка защищают только тот код, который их применил. Материализованный счётчик с CHECK — это правило внутри базы: его не обойдёт ни миграция, ни скрипт, ни коллега, который через год не знал про лимит.

Задача на один абзац

Запрос POST /holds проходит три слоя: controller → service → repository. Где-то в репозитории пишется строка лога hold created. Через неделю приходит покупатель: «я нажал купить, деньги списались, места нет». У тебя есть его время с точностью до минуты, и в логах за эту минуту — четыре тысячи строк.

Тебе нужно, чтобы каждая строка, порождённая его запросом, была подписана одним и тем же requestId. Тогда вопрос «что случилось с этим заказом» превращается в один grep. Вот и весь M0-04.

Технически задача звучит обманчиво просто: доставить одно значение из middleware в репозиторий. Способов ровно три, и два из них плохие.

Способ первый: протащить параметром

createHold(dto, requestId), дальше insert(row, requestId), и так до самого низа. Работает. И отравляет каждую сигнатуру в проекте значением, которое не имеет отношения ни к домену, ни к бизнес-правилу: репозиторий начинает знать про HTTP. Через месяц у тебя половина методов принимает аргумент, который они только передают дальше. Именно это запрещено в DoD: «проброс id должен работать без ручной передачи логгера через все слои сервисов».

Способ второй: глобальная переменная

Очевидная идея: положить requestId в переменную модуля, все читают оттуда. Вот тут и начинается урок, потому что этот способ не просто плох — он врёт, и врёт молча.

Опыт 1: лог запроса A, подписанный именем B

Создай папку где угодно вне репозитория и положи туда файл. Никаких зависимостей, только Node.

global.mjs

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

let currentRequestId = null;

async function repository() {
  await sleep(10);
  console.log(`  repository: requestId = ${currentRequestId}`);
}

async function handleRequest(id, workMs) {
  currentRequestId = id;
  console.log(`controller: начал ${id}`);
  await sleep(workMs);
  await repository();
}

await Promise.all([handleRequest('req-A', 30), handleRequest('req-B', 5)]);

Два запроса пришли почти одновременно — A работает дольше, B быстрее. Запусти:

$ node global.mjs
controller: начал req-A
controller: начал req-B
  repository: requestId = req-B
  repository: requestId = req-B
Смотри внимательно

Контроллер отчитался о двух разных запросах. Репозиторий отработал дважды. А в логе оба раза стоит req-B. Строка от запроса A существует — и подписана чужим именем.

Разбери по шагам, это того стоит:

  1. handleRequest('req-A') пишет currentRequestId = 'req-A' и уходит в await sleep(30). Управление возвращается в event loop.
  2. handleRequest('req-B') пишет currentRequestId = 'req-B' — поверх — и уходит в await sleep(5).
  3. Через 5 мс просыпается B, зовёт репозиторий, тот ждёт ещё 10 мс и печатает req-B. Верно.
  4. Через 30 мс просыпается A, зовёт репозиторий, тот печатает то, что лежит в переменной сейчас, — req-B. Неверно, и никто об этом не узнает.

Это ровно та же ошибка, что в уроке 0001, только вместо остатка билетов — переменная в памяти процесса. Node однопоточный, но однопоточный не значит «по одному запросу за раз»: каждый await — это точка, в которой твой обработчик отпускает управление и в те же данные заходит чужой. Разница с уроком 0001 в одном: там за тебя вступилась база с CHECK, а здесь не вступится никто. Битый лог выглядит как здоровый лог.

Почему это хуже, чем кажется

Сломанный лог не падает и не отдаёт 500. Ты узнаешь о нём в тот единственный момент, когда он нужен: в разборе инцидента, когда по requestId пострадавшего покупателя ты соберёшь чужую историю и будешь час искать ошибку не в том месте.

Проверка · 1 из 3

Почему глобальная переменная подписала лог запроса A именем запроса B?

Переменная одна на процесс, а обработчиков в полёте — сколько угодно. Значение привязано к моменту времени, а нужно, чтобы оно было привязано к цепочке вызовов. Ровно это и делает AsyncLocalStorage.

Способ третий: AsyncLocalStorage

Встроенный модуль node:async_hooks. Модель такая:

storage.run(значение, fn) — выполняет fn, и всё, что из fn вызвано, включая асинхронные продолжения после каждого await, видит это значение через storage.getStore(). Параллельные цепочки видят каждая своё.

То есть это переменная, привязанная не к процессу, а к цепочке асинхронных вызовов. Node сам протаскивает её через await, setTimeout, коллбэки и промисы — то, что руками пришлось бы делать параметром.

Тот же файл, три изменённые строки:

als.mjs

import { AsyncLocalStorage } from 'node:async_hooks';

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

const storage = new AsyncLocalStorage();

async function repository() {
  await sleep(10);
  console.log(`  repository: requestId = ${storage.getStore()?.requestId}`);
}

async function handleRequest(id, workMs) {
  await storage.run({ requestId: id }, async () => {
    console.log(`controller: начал ${id}`);
    await sleep(workMs);
    await repository();
  });
}

await Promise.all([handleRequest('req-A', 30), handleRequest('req-B', 5)]);
$ node als.mjs
controller: начал req-A
controller: начал req-B
  repository: requestId = req-B
  repository: requestId = req-A
Вот он, наблюдаемый результат

Порядок строк остался прежним — B успел раньше. Но каждая строка теперь подписана своим именем. Репозиторий по-прежнему ничего не знает про HTTP, про id и про то, кто его позвал: его сигнатура не изменилась ни на символ.

Почему не request-scoped провайдер Nest

У Nest есть свой ответ: @Injectable({ scope: Scope.REQUEST }). Он работает, и знать про него надо, но у него есть цена, которую в документации называют bubbling: scope поднимается вверх по графу зависимостей. Сделал request-scoped логгер — request-scoped становится и сервис, который его инжектит, и контроллер над ним. Дальше Nest создаёт новое дерево провайдеров на каждый запрос вместо одного синглтона на процесс.

Для нашего проекта это плохая сделка по двум причинам. Первая — цена на горячем пути: билеты продаются пиками, а не ровным фоном. Вторая важнее: DI достаёт только то, что живёт внутри графа Nest. А логировать надо и из мест, куда DI не дотягивается, — из обработчика необработанного промиса, из коллбэка драйвера БД, из фонового воркера. AsyncLocalStorage — это механизм Node, а не Nest, и он работает везде, где работает Node.

Складываем с Pino: храни логгер, а не строку

Наивная связка — положить в store строку id и подставлять её в каждый вызов: logger.info({ requestId: store.requestId }, 'hold created'). Это тот же «протащить параметром», только через глобальную дверь: про requestId опять обязан помнить каждый вызывающий, и забытая подстановка — это молча потерянная строка.

Правильный ход: класть в store уже обогащённый child-логгер. logger.child({ requestId }) пинит пару к логгеру, и она печатается в каждой строке этого child сама. Слои получают логгер, который уже всё про себя знает.

pino-demo.mjs · npm i pino

import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';
import pino from 'pino';

const root = pino({
  base: null,
  redact: ['req.headers.authorization', 'password', '*.password'],
});

const storage = new AsyncLocalStorage();
const log = () => storage.getStore() ?? root;   // вне запроса — корневой логгер

function repository() {
  log().info({ seatId: 'A12' }, 'hold created');
}

function handleRequest(headerValue) {
  const requestId = headerValue ?? randomUUID();
  storage.run(root.child({ requestId }), () => {
    log().info({ user: { email: 'a@b.c', password: 'hunter2' } }, 'request received');
    repository();
  });
}

handleRequest('from-client-1');   // клиент прислал x-request-id
handleRequest(undefined);         // не прислал — генерируем свой
$ node pino-demo.mjs
{"level":30,"time":...,"requestId":"from-client-1","user":{"email":"a@b.c","password":"[Redacted]"},"msg":"request received"}
{"level":30,"time":...,"requestId":"from-client-1","seatId":"A12","msg":"hold created"}
{"level":30,"time":...,"requestId":"92289369-4f10-4367-ab7e-612b02f3d0b6","user":{...},"msg":"request received"}
{"level":30,"time":...,"requestId":"92289369-4f10-4367-ab7e-612b02f3d0b6","seatId":"A12","msg":"hold created"}

Четыре строки, две пары, в каждой паре свой id. Строка из репозитория подписана, хотя repository() про id не знает. password заменён на [Redacted] — это сделала опция redact, а не ты в месте вызова, и в этом вся её ценность: она работает и на том коде, который напишут после тебя.

Заметил, что проехало?

email попал в лог открытым: в redact его нет. Это не баг демо — это ровно та дыра, которую закрывает M0-07, и хороший повод понять, почему redaction вынесен в отдельный issue: список полей — это политика, и она меняется без единой правки в логгере.

Проверка · 2 из 3

Что мы положили в AsyncLocalStorage и почему именно это?

Если в store лежит строка, про неё обязан помнить каждый вызывающий — а забыть можно молча. Если лежит child-логгер, то забыть нечего: requestId привязан к самому логгеру и печатается всегда.

Три ловушки, на которых спотыкаются

Первая: enterWith() вместо run(). В документации есть метод enterWith(store), который «включает» контекст и не требует колбэка — выглядит удобнее. Но он не ограничен рамками функции: контекст остаётся жить до конца текущей цепочки, и в долгоживущих обработчиках даёт ровно ту же утечку через границы запросов, с которой мы начали урок. В документации Node у него прямое предупреждение. Бери run().

Вторая: контекст не «догоняет» задним числом. Значение видят те вызовы, которые начались внутри run(). Коллбэк, зарегистрированный до входа в run(), отработает без контекста, и getStore() вернёт undefined. Поэтому в коде выше ?? root — не украшение, а обязательная часть: логгер должен уметь работать и вне запроса.

Третья: store мутабелен, и этим злоупотребляют. Технически в store можно дописывать поля по ходу запроса, и очень быстро он превращается в свалку «глобальных переменных на запрос»: userId, фича-флаги, черновик ответа. Держи правило: в store едет контекст наблюдаемости, а не данные домена. Данные домена ходят параметрами — их видно в сигнатуре, их проверяет компилятор.

Проверка · 3 из 3

В каком случае getStore() вернёт undefined внутри запроса?

Контекст наследуется в момент создания асинхронной операции. Слушатель, повешенный на событие до run(), унаследовал контекст того места, где его вешали, — то есть никакого. Глубина вложенности и факт отправки ответа роли не играют.

Зачем это на самом деле — мост в M4

Ты сейчас выучил не «как приделать id к логам». Ты выучил единственный в Node способ иметь контекст запроса, невидимый в сигнатурах. И через несколько этапов он понадобится тебе для вещи посерьёзнее логов.

В M4 встанет вопрос: HoldService зовёт два репозитория, и оба должны попасть в одну транзакцию. Варианта опять три, и они те же самые: протащить клиент БД параметром через все методы; держать его в переменной (и получить ту самую гонку, только теперь она разъедет транзакции покупателей); либо положить активный клиент в AsyncLocalStorage и дать репозиториям доставать его оттуда.

Разница в цене ошибки. Здесь она — лог с чужой подписью. Там — COMMIT половины изменений и два человека на одном кресле. Поэтому механизм и разбирается здесь, в M0, где он ничего не стоит.

Первоисточники

  • Читать в первую очередь: Node.js Docs — Asynchronous context tracking. Разделы asyncLocalStorage.run(), getStore() и предупреждение к enterWith(). Страница короткая, прочти целиком.
  • Pino — Child loggers: «key-value pairs can be pinned to a logger causing them to be output on every log line». Там же бенчмарки создания child — порядка 230 мс на 10 000 штук, то есть на запрос это не расход.
  • Pino — Redaction: пути, [Redacted], переопределение в child. Понадобится целиком в M0-07.
  • Pino — Asynchronous logging: буферизация и minLength — почему Pino не делает syscall на каждую строку, в отличие от console.log.
  • NestJS — Injection scopes, раздел «Scope hierarchy» (bubbling) и предупреждение про производительность. Это обоснование, почему мы не берём request scope.
  • Глубже, если понравилось: исходник nestjs-pino — найди там AsyncLocalStorage и посмотри, как то же самое сделано за тебя.
