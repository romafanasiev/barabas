Recall · 1 из 2

Что именно делает SELECT ... FOR UPDATE со второй транзакцией?

Блокировка — это ожидание. Вторая транзакция висит до COMMIT или ROLLBACK первой, потом перечитывает строку уже в новом состоянии.

Recall · 2 из 2

Почему CHECK надёжнее условия WHERE available > 0?

Условие в WHERE живёт ровно в одном запросе. CHECK живёт в схеме и не зависит от того, вспомнил ли автор следующего эндпоинта про инвариант.

Что ты нашёл

Ты открыл обе транзакции на REPEATABLE READ, повторил сценарий без всякой блокировки — и получил:

ERROR:  could not serialize access due to concurrent update

Код ошибки — 40001, имя — serialization_failure. Овербукинга не случилось. И заметь: ты не просил никакой блокировки. База отказала сама.

Механика такая. На REPEATABLE READ транзакция Бориса работает со снимком данных, сделанным в момент её начала. Когда её UPDATE добирается до строки, которую Аня успела изменить и закоммитить, у базы есть ровно два выхода: перечитать строку — но это разрушит снимок, ради которого уровень и выбран, — либо сдаться. PostgreSQL сдаётся. Правило называется first-updater-wins: кто закоммитил первым, тот и прав, второй аварийно завершается.¹

Ровно та же ситуация, три разных исхода

Read Committed без блокировки — тишина и испорченные данные.
Read Committed с FOR UPDATE — ожидание, потом честный отказ.
Repeatable Read — громкая ошибка 40001.

Из трёх исходов опасен именно первый: он единственный не оставляет следов.

Цена, которую ты только что купил

Ошибка вместо тихой порчи данных — это улучшение. Но обрати внимание, что произошло с точки зрения покупателя: Борис получил пятисотку. Не «мест нет», а «что-то сломалось». Между тем место, возможно, было — просто в этот момент его трогал кто-то другой.

Значит, выбрав этот уровень изоляции, ты обязан написать ретрай. Не «хорошо бы», а обязан: 40001 — это часть контракта уровня, а не поломка.

Главная ошибка на этом месте

Повторять надо всю транзакцию с самого BEGIN, а не упавший запрос. После 40001 транзакция мертва: любая следующая команда в ней вернёт current transaction is aborted. И это правильно — снимок данных, на котором она строила решения, уже недействителен. Нужен новый BEGIN, новое чтение, новое решение.

Проверь руками

Подними полигон, если убрал, и верни остаток в единицу:

docker run --rm -d --name tix-lab -e POSTGRES_PASSWORD=lab -p 5433:5432 postgres:18
docker exec -i tix-lab psql -U postgres <<'SQL'
CREATE TABLE IF NOT EXISTS inventory (ticket_type_id int PRIMARY KEY, available int NOT NULL);
INSERT INTO inventory VALUES (1, 1) ON CONFLICT (ticket_type_id) DO UPDATE SET available = 1;
SQL

Повтори свой сценарий до ошибки, а потом — в том же терминале B — сделай то, что сделал бы ретрай:

Терминал B · после 40001

-- транзакция мертва, проверь:
SELECT 1;
-- ERROR: current transaction
--        is aborted

ROLLBACK;

-- ретрай = всё заново
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT available
  FROM inventory
 WHERE ticket_type_id = 1;
-- available = 0
-- честный отказ: "мест нет"
COMMIT;

Что здесь важно

1. Первая же команда после
   40001 тоже падает.
   Транзакция не «немного
   сломана» — она мертва.

2. ROLLBACK обязателен.

3. Новый BEGIN делает новый
   снимок. Только поэтому
   Борис видит честный 0,
   а не устаревшую 1.

4. Ретрай вернул не билет,
   а корректный ответ.
   Это и есть успех.
Проверь себя

Сколько раз имеет смысл повторять транзакцию, упавшую с 40001?

Бесконечный ретрай под нагрузкой превращается в самоподдерживающийся шторм: все повторяются одновременно и снова конфликтуют. Отсюда exponential backoff и jitter — случайный разброс, чтобы клиенты не синхронизировались. Предел попыток нужен, чтобы после него честно ответить 503, а не висеть вечно.

Что REPEATABLE READ всё ещё не спасает

Оба сценария выше трогали одну строку. Именно поэтому база смогла заметить конфликт.

Теперь представь правило: «один покупатель — не больше двух VIP-мест». Аня одновременно в двух вкладках берёт по одному VIP-месту. Обе транзакции считают её текущие места, обе видят «ноль», обе разрешают покупку, обе пишут в разные строки. Конфликта записи нет — базе не за что зацепиться. Правило нарушено, ошибки не будет.

Это write skew, и от него REPEATABLE READ не защищает. Нужен SERIALIZABLE — либо явная материализация правила в схеме. Об этом следующий урок по конкурентности.
